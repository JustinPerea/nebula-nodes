# Studios and resources (Volume 7)

Saved assets that studios edit and bridge nodes read. This volume starts with the Moodboard; of the Character only its edits are written up (section 2); then Styles (section 3). Cinema and the video editors are not written up yet.

**Oracle:** `backend/services/moodboard_store.py`, `backend/services/moodboard_edits.py`, `backend/services/moodboard_layout.py`, `backend/services/moodboard_brief.py`, `backend/services/moodboard_analysis.py`, `backend/handlers/moodboard.py`, `backend/services/moodboard_reader.py`, `backend/services/moodboard_reader_stream.py`, `backend/data/moodboard_reader_models.json`, `/api/moodboards/*` in `backend/main.py`; for Styles (3) `backend/services/preset_store.py`, `backend/style_client.py` and `/api/presets/*` in `backend/main.py`

## 1. Moodboard

A board is one JSON file under the moodboard root (`NEBULA_MOODBOARD_ROOT`, default `~/.nebula/moodboards/<scope>/<id>.json`; scope is `_global` or a canvas project's id, see 1.8).

### 1.1 Saved fields

| Field | Type | Who writes it | Notes |
|-------|------|---------------|-------|
| `id`, `createdAt`, `projectId` | string | store | Fixed after create |
| `name`, `notes`, `mode`, `strength`, `images` | — | person or agent | `mode` is `look`, `world` or `subject`; each image has `id`, `url`, `weight`, `notes`, `privateNote`, `excluded` and `placements` |
| `images[].excluded` | boolean | person or agent | The **Set aside** switch. A set-aside image stays on the board with its weight, notes and cards and is still read (measured) for its colours, but never steers: it adds nothing to the palette, accents, `sources`, keywords, summary, brief, negatives or representative images, and no generator or node output gets it (1.4). The key and its place in `source_hash` are as before, so no board is rewritten and no analysis or hand-written brief goes out of date. Wherever a board is shown (Moodboard Studio, `nebula moodboard show`, `moodboard_get`), weight 0 shows as set aside too: an image steers only when it isn't set aside and its weight is above 0 (`moodboard_analysis.steers`). Turning it on keeps the weight; turning it off on a weight-0 image also sets the weight its card shows (its largest card's, or 1 with no card) |
| `images[].privateNote` | string | person or agent | The person's own label for the image ("PAINTERLY (liked)"), up to 2000 characters. Shown wherever the board is inspected (Moodboard Studio, `nebula moodboard show`, `moodboard_get`), never sent anywhere: it isn't in `source_hash`, the analysis, `brief`, the negative prompt or the Moodboard node's outputs (`moodboard_store.output_image`). Changing it keeps the analysis. A board saved before it existed reads with `""`. `images[].notes` is the note that steers |
| `images[].placements` | object[] | board edits; the store, for a new image | The image's cards on the board canvas, 1 to 8, at most one per frame: `{id, frameId, x, y, w, h, weight, placedBy, placedAt}`. Coordinates are absolute board pixels (at most 1,000,000 from the origin). `frameId` is the frame (look) the card is in, or null; a card in no frame must be the image's only one. `w × h = weight × 129,600` (full weight is a 480×270 card), rounded to whole pixels at the image's aspect ratio (its file, upright; else the analysis's measurement; else 4:3); card weights run from 0.05 to 1. The server writes `w`, `h`, `placedBy` (`person`, `agent` or `analyze`, from who asked) and `placedAt`. The layout steers nothing: it isn't in `source_hash`, `brief_basis`, `brief` or the node's outputs, so moving or resizing a card keeps the analysis (`moodboard_layout.py`) |
| `layoutVersion` | integer | store | `1` once the board's layout is saved. Absent on an old board, which reads with a layout (1.5) |
| `frames` | object[] | board edits | The board's frames (looks): `{id (12 hex), name, kind: "look" or "unsorted", x, y, w, h, createdBy, namedBy, createdAt}`. At most 100, one Unsorted, names 1 to 60 characters and unique ignoring case, sides at least 160 px. Reads as `[]` when absent |
| `suggestions`, `readings`, `lastRead` | — | Analyze | Reserved for Analyze (item 6): `suggestions` (at most 200) and `readings` (one per image, at most 2 KB each) read as `[]` and `{}` when absent. Nothing writes them yet |
| `analysis` | object or null | Analyze | Colour reading of the images. Set to null when the images, weights, mode, strength or notes change (not an image's `privateNote`). Its own `styleBrief` and `negativePrompt` are the analyzer's; generators get `brief` (1.2), so change the brief through `briefOverride`, not here |
| `direction` | string | person or agent | What the board is for, in positive words. Up to 4000 characters |
| `avoid` | string[] | person or agent | Things to keep out of the image. Trimmed, de-duplicated (case-insensitive), at most 40 items of 200 characters |
| `pinnedColors` | `{include: hex[], exclude: hex[]}` | person or agent | Colours that must appear or must stay out. Hex is stored as `#rrggbb`; at most 12 per list; a colour can't be in both |
| `briefOverride` | `{text, basis, updatedAt, by}` or null | person or agent (text); store (`basis`, `updatedAt`, `by`) | A hand-written brief that replaces the generated one. `by` is `person` or `agent`, from the person gate (`services/person_gate.py`); none (an override the migration moved) counts as `person`. Only the person may replace, remove or Keep text the person wrote (1.3) |
| `briefVersion` | integer | store | `1` once the board has the fields above (see 1.5) |
| `coverImageId` | string or null | person or agent | The board's cover: the id of the image it opens on, wherever one image stands for the board (the Moodboard node's card, the board lists in Moodboard Studio and the Assets panel, the asset picker, `nebula moodboard show` and `list`, `moodboard_get` and `moodboard_list`). null, or absent on a board saved before it existed, means no cover: the board opens on #1, as before, and reading it writes nothing. A pick, not a reorder: `images` keep their order, so #n stays the same image, and the cover steers nothing. It isn't in `source_hash`, `brief_basis`, the analysis, `brief` or the node's outputs, so setting it keeps the analysis and a hand-written brief's basis, and every generator's request is the same bytes with any cover (`backend/tests/test_moodboard_cover_requests.py`). It must name an image on the board (else 422: "coverImageId names no image on this board ..."). A set-aside or weight-0 image can be the cover, and setting the cover aside keeps it. Taking the cover image off the board clears it (the board opens on #1 again), and undoing that brings back the image and the cover. A saved id that names no image (a file edited by hand) reads as null |
| `thumbnail` | string | store | The cover image's url, else #1's (`moodboard_store.board_thumbnail`), written with every save and computed again on read |
| `version`, `updatedAt` | — | store | |

**Layout is written only by board edits and by the server placing new images.** `layoutVersion`, `frames`, `suggestions`, `readings` and `lastRead` are refused (422) on create and on `PUT`. An image's `placements` are taken only for an image new to the board; on an image already there, the saved cards stay whatever the client sends (1.3). A saved layout that is out of bounds is logged, and the board still opens as saved. A file edited into an odd shape (`placements` or `frames` that aren't lists, numbers too big for a float) still lists, opens and saves: what can't be read as a card counts as none, and an image with no card that can be drawn is placed again.

`direction`, `avoid`, `pinnedColors` and `briefOverride` live on the board, not inside `analysis`, so analyzing again never drops them. Changing them does not clear the analysis.

### 1.2 The brief (`brief`, computed)

Every moodboard API response adds `brief`, computed on each read and never saved (`moodboard_brief.compose`):

| Key | Meaning |
|-----|---------|
| `styleBrief` | The override text when there is one, else `generatedStyleBrief` |
| `generatedStyleBrief` | Direction first, then mode intent, palette (minus kept-out and left-out colours, 1.11), accents, "Make sure these colors appear", visual cues, any reader fields (`motifs`, `materials`, `textures`), notes (only when sent, 1.11). Empty until the board is analyzed |
| `negativePrompt` | `blurry, low-detail artifacts` plus the Avoid list. Defects only: content intent goes in the brief as positive words |
| `avoid`, `direction`, `pinnedColors` | The saved fields |
| `avoidPrompt` | `Keep these out of the image: <avoid>, colors close to <kept-out hex>.` or empty |
| `palette`, `accents` | The analysis colours, minus any within dE00 5 of a kept-out colour, minus those left out (1.11) |
| `override` | `{active, stale}`: `stale` is true when the board changed after the override was written |
| `needsAnalysis` | No saved analysis yet |

### 1.3 API

| Call | Body | Effect |
|------|------|--------|
| `POST /api/moodboards` | `name`, `images`, … plus optional `direction`, `avoid`, `pinnedColors`, `briefOverride: {text}`, `coverImageId` | Create. `coverImageId` must be the id of one of the images sent (422 otherwise). Each image is placed where its `placements` ask, else after the one before; the board is saved with `layoutVersion: 1` |
| `GET /api/moodboards/{id}` | — | The board, laid out (an old board reads with its grid, 1.5). Reading writes nothing. `GET /api/moodboards` (the list) doesn't lay boards out |
| `PUT /api/moodboards/{id}` | Any subset, including the four brief fields, plus optional `baseVersion` | Update. `briefOverride: {text}` sets the override; `briefOverride: null` removes it (the brief goes back to generated). Send only `text`: `basis` and `updatedAt` are refused (422). `images` merges by id (below). `coverImageId: "<image id>"` picks the cover and `coverImageId: null` clears it (an image not on the board is a 422); leaving the key out keeps it. With `baseVersion`, a board saved since is a 409 (1.12). A layout field is refused with a 422 that names `POST /api/moodboards/{id}/edits` |
| `POST /api/moodboards/{id}/edits` | `{ops, baseVersion?, say?}` | Checked board edits, applied whole or not at all (1.12). Answers `{board, version, applied, undo}` |
| `POST /api/moodboards/{id}/brief-override/keep` | — | Keep the override for the board as it is now (clears `stale`). 404 for an unknown board; 409 when there is no override (the message says to set one with `PUT`); 403 when an agent asks to keep the person's text |
| `POST /api/moodboards/{id}/analyze` | — | Analyze again. Keeps the brief fields and the override. Saved against the version it read: an edit while it ran that changes what it reads makes it analyse the new board, one that doesn't keeps the analysis; 409 `version_conflict` (with the board) after 3 saves lost to edits |
| `POST /api/moodboards/{id}/analyze/dry-run` | optional `{thresholds: {accentMinChroma, accentSeparation, mergeDeltaE}}` | What Analyze would give, saving nothing (1.8). 422 for a threshold out of range or an unknown key |

The board keeps no history, so replacing or removing the person's hand-written brief can't be undone. A `PUT` that would replace or remove an override with `by: "person"` (or no `by`), or a Keep of one, is refused unless it comes from the person: 403 with the person gate's `code` (`agent_refused` for an agent marker, `person_required` without this launch's person token), and nothing in that request is saved. An agent may still change every other field, which marks the override stale for the person to answer, and may change an override an agent wrote.

**Images on `PUT` merge by id.** Each image in `images` is matched with the saved image of the same id:

- A key the client leaves out keeps its saved value. Before item 6, a left-out key was reset to its default, so a client that didn't send `privateNote` erased it; now it keeps it.
- On an image already on the board, `placements` are ignored: the saved cards stay, so a stale tab or a CLI that sends back what it read can't undo a layout edit. Everything `GET` returns may be sent back.
- A `weight` that changes scales the image's cards by the same factor, so the largest equals the new weight (smaller ones stop at 0.05); weight 0 keeps them as they are. Each card keeps its top-left corner and nothing else moves, so a card that grows may cover its neighbour, as a resize in the Board view can.
- An image new to the board (no id, or one the board doesn't have) takes the `placements` it sends, checked (frames must exist, at most 8, one per frame, ids unique), with `w`/`h` written from each card's `weight` (or from `w × h` when no weight is sent). With no weight sent, the image's weight is its largest card's. Without `placements`, Nebula places it after the last-added card: in that card's row when there is room (24 px from every card and frame, within six full-weight cards' width, and fewer than six cards in the row up to that card), else at the start of a new row under the board. The six-card rule keeps an old board's 6-column grid 6 wide when its cards are portrait or square. Never on top of anything.
- An image left out of `images` is removed, as before.

**Every write bumps `version`**, the board's compare-and-set token, and a write of a saved board (create, `PUT`, edits, Keep, Analyze) tells open canvases with `storedAssetChanged` (1.12). Opening or reading a board writes nothing, and a `PUT` or edit batch that changes nothing writes nothing and keeps the version. Moodboard Studio sends board fields only on `PUT` (`name`, `notes`, `mode`, `strength`, the brief fields, the 1.11 fields, and `analysis` only as `null`), always with `baseVersion`, and every image change, the cover included (`cover`, 1.12), through `/edits`. `PUT` keeps taking `images` for the CLI, MCP and API callers, and its image changes are journaled the same way (1.12).

Sending the same override text again keeps its original `basis`, so a client that saves the whole board on every change doesn't hide the "changed since you edited this" state. New text is stamped with the board as it is after the update.

### 1.3a The analysis's colours (version 5)

`analysis.palette` and `analysis.accents` are hex lists in rank order. `analysis.colors` holds the same colours with detail:

| Key | Meaning |
|-----|---------|
| `hex`, `role` | The colour, `dominant` (palette) or `accent` |
| `share` | The part of the weighted board it covers: the sum over images of (image weight ÷ total weight) × its share of the image |
| `images` | How many images it comes from |
| `sources` | Each image it comes from, largest contribution first (then board number): `number` (the image's place among all the board's images, 1-based, set-aside ones included, as Moodboard Studio and `nebula moodboard show` number them), `id`, `share` (the colour's share of that image; two colours of one image that merge add up) and `contribution` (that image's part of `share`) |

`analysis.images[]` lists each image with a URL, set-aside ones included, with its `number`, `weight`, `status` (`analyzed`, `unresolved` or `error`), `colors` (`hex`, `share`, `accent`), `palette` and `accents`. A set-aside image's entry has `setAside: true` (version 5 on; the key is absent otherwise) and its colours as measured, the same as if it steered. Set-aside and weight-0 images never appear in `sources` and add nothing to any share. A set-aside image that can't be read says so in its own entry's `status`; `warnings` stay those of the images that count. When no image steers (every one set aside or at weight 0), `warnings` holds "Every reference is set aside, so none of them shapes the board."

`summary` counts the images that steer: weight 0 is left out like the switch (2026-10-20; it counted before). A board with images, none of which steers, reads "No reference image steers this board: every one is set aside." ("Empty moodboard; ..." is for a board with no images). An analysis saved before this still describes its board (same hash), so it stays current, and every read gives its summary with the new count, in memory (`moodboard_analysis.with_steering_count`, from the store's read); the file isn't written. `analysis.version` stays 5.

Version 5 changed nothing that steers, and the source hash is the same, so a version 4 or 3 analysis stays current until the board changes; it just doesn't list set-aside images. Analyses before version 4 have no `sources` or `number`; the Studio and CLI say to analyze again to see the sources.

### 1.4 How a board reaches a generator

The `nebula-moodboard` node emits a `Moodboard` bundle (`kind: "nebula_moodboard"`) carrying `styleBrief`, `negativePrompt`, `avoid`, `avoidPrompt`, `direction`, `pinnedColors`, `briefOverride` (`{active, stale}`), `palette`, `accents`, `images`, `representativeImages`, `analysis` and `providerHints`, plus what 1.11 adds (no notes unless sent, the left-out lists). Each bundle image has exactly `id`, `url`, `weight`, `notes` and `excluded` (never the private note or the layout), and its `notes` is empty unless the board's notes are sent (1.11); set-aside images, switched aside or at weight 0 (2026-10-20; weight 0 was kept before), are left out, and so are their entries in `analysis.images` and their place in `analysis.summary`'s count, so the bundle carries no set-aside image or its colours and Krea 2's style references never include one. `representativeImages` (the bundle's, the analysis's and Krea's hint) keep only images that steer as well: an analysis from version 2 on never ranked a weight-0 image, but a version 1 analysis (before 2026-10-18), still current while its board is unchanged, did, and Krea 2 skipped it only because the bundle's images gave its weight as 0. No generator request changed with weight 0 leaving the bundle: Krea 2 already skipped weight 0 and the brief's colours and cues come from steering images only (`backend/tests/test_moodboard_weight_zero.py` pins GPT Image, Nano Banana, FLUX.2 [pro] and Krea 2, and a version 1 analysis that lists a weight-0 image). On such a board the `representative_images` port no longer carries the weight-0 image. The Preview doesn't count or draw a set-aside image either. A stale override is still used, and the run gets a note saying so. The node is not output-cached: its params name the board, not its contents.

Image generators take it on an optional `moodboard` input port (`dataType: "Moodboard"`; Krea 2's was `Any` until 2026-10-20). The engine folds it in before the handler runs (Volume 2, section 7a, "Moodboard fold"), as the node's adapter entry says (1.16).

**Strength 0 turns the board off for every node it's wired into** (Q36 a, Justin 2026-10-20): no brief, Avoid, negatives or images, on every generator, with the run note "Board strength is 0: board not sent". A second board wired into the same node still goes. To keep the text and send no images, use the node's "Send board images" switch (`_boardImages`, plan §5.7.8; until it ships, content-slot nodes already get text only). The Moodboard node's own outputs (`style_brief`, `negative_prompt`, `palette`, `representative_images`, and the bundle itself) are unchanged at strength 0: wiring one of them is the person's choice, and the bundle's `strength` is what the receiving generator reads. Moodboard Studio's slider reads "Strength 0.00 · board off: wired nodes get none of it" at 0, and `nebula moodboard show` heads the brief "Brief (generated), not sent: board strength is 0, so no node it's wired into gets the board:" instead of "Brief sent to generators"; `moodboard_get`'s description says the same.

Krea 2 (`krea-2-generate`) also takes the board's images as `image_style_references`, and their strengths share out the board's strength (Q21 b, 2026-10-20): the images that go (Krea's hints' `representativeImages`, else the bundle's, else the images ranked heaviest first; deduped, weight-0 and set-aside never, capped at 10 minus the wired references) get `strength x weight / sum(weight)` over those images, at 4 decimals by largest remainder (`services/moodboard_weights.py` `native_strengths`), so they add up to exactly `strength`. A URL missing from `images` counts as weight 1. Wired references, Krea `moodboards` and `styles` keep their own strengths. At strength 0 the engine has already taken the board out (above), so Krea 2 gets none of its images; a direct call to the handler sends none and posts the same note. An image whose share rounds to 0 is left out with a note; every run that sends board images notes each one's strength ("Board 'Dusk' sent 5 images; their strengths add up to the board's 0.70 (#1 0.19, ...)", `#n` the board number) and, with wired references, what they add on top. Both Krea routes send the same body. Before this, each image went at `strength x weight`; run records keep what they sent, and a canvas replay of a record from before 2026-10-20 notes that it can differ (`runReplayNotes` in `frontend/src/lib/savedParamsUpgrades.ts`; no params version change).

### 1.5 Migration of older boards

Boards saved before the brief fields (no `briefVersion`) are migrated once at backend startup, and in memory on any read before that:

- Negatives in `analysis.negativePrompt` beyond the old defaults move to `avoid`.
- An `analysis.styleBrief` that differs from what that analysis generated becomes `briefOverride`. If the board changed since that analysis, the override starts out stale.
- Each changed file is copied first to `<moodboard root>/../moodboard-backups/brief-fields-<UTC time>/<scope>/`, with `migration-log.json` listing what moved. A file that can't be backed up is not rewritten.
- Moved text is kept within the limits in 1.1, so the board can still be saved. Anything cut is in the log (`avoidClipped`, `overrideClipped`) and whole in the backup.
- Nothing is lost: the saved `analysis` keeps its old `styleBrief` and `negativePrompt`, and the backup holds the file as it was. A backup copied back is migrated again on the next start, with the same result.
- Running the migration again changes nothing. A file that can't be read is logged and left alone. A board with a higher `briefVersion` (saved by a newer Nebula) is left as it is. A board file edited by hand into an odd shape still lists and opens (its `brief` is `null` if it can't be composed), and a failing migration never stops the backend from starting.

**Old boards read with a layout (item 6).** A board saved before layouts (no `layoutVersion`) is not migrated on disk: there is no startup step and no backup, and its file keeps its bytes, `version` and `updatedAt` until someone edits it.

- `GET /api/moodboards/{id}` (and the store's `get` and `update`) lays it out in memory as a grid in number order: 6 columns, 40 px between cells, each column as wide as its widest card and each row as tall as its tallest, every card centred in its cell. A card's area is its weight (at least 0.05; weight 0 shows at full size) at the image's aspect ratio. `placedBy` is `person`, since the order was theirs, and each card's id is derived from the board and image, so every read gives the same layout. `frames`, `suggestions` and `readings` read as empty.
- The list (`GET /api/moodboards`) doesn't lay boards out, so the rail stays cheap.
- The first write (any `PUT`, Analyze's save, a Keep, the CLI or MCP) saves that same layout and stamps `layoutVersion: 1`. Nothing moves. A write stamps `layoutVersion` only when every image has a card, so if laying the board out fails, the next read lays it out again.
- A board with `layoutVersion` where no image has a card reads with the same grid. An older Nebula leaves that when it edits a laid-out board (it drops image keys it doesn't know, `placements` among them, and keeps board keys). A board whose grid was saved comes back unchanged; cards placed or moved since are lost.
- An image whose url can't be read, or can't even be resolved (an unknown `~user`, a null byte), lays out at the analysis's size, else 4:3.
- Reading writes nothing. Moving a board, Recently deleted and its restore, the brief-fields migration and the re-home at start move or copy the file as it is, so they never write a layout either.
- The layout never enters `source_hash` or `brief_basis`, so every saved analysis and hand-written brief stays current. The brief and the node's outputs for old boards are pinned by `backend/tests/test_moodboard_golden.py`.
- Reading an image's aspect ratio runs the protected-path check (`services/file_access.py`), about 2 ms an image. The answer is kept per URL and agent workspace while one stat shows the same file unchanged, so later reads cost about 3 ms for 300 images. The `GET` route reads off the event loop.

### 1.6 From the CLI and MCP

`nebula moodboard show --json` and `moodboard_get` also return the layout: each image's `placements` and the board's `frames` (1.1). Lists and the results of edits leave it out to stay short. A board named by name is read again by id, so it comes with its layout. A change that only moves or resizes cards never counts as a content change: the client compares only `url`, `weight`, `notes` and `excluded` (`moodboard_client.STEERING_KEYS`) to decide whether to clear the analysis, and so does Moodboard Studio (`moodboard-studio/steering.ts`).

`nebula moodboard` and the `moodboard_*` MCP tools (`backend/moodboard_client.py`) return each board with `direction`, `avoid`, `pinnedColors`, `briefOverride` (`{text, by, updatedAt, stale}` or null; `by` is `agent` only when stamped so, else `person`) and `brief`, the backend's computed brief from 1.2 passed on as it came. On a backend that doesn't send `brief`, it is `null`: the client never rebuilds it, and never offers `analysis.styleBrief` in its place.

`nebula moodboard set` and `moodboard_update` change the brief fields: Direction (`""` clears), Avoid (replace, add, remove), pinned colours (replace both lists, add to either, remove from either), the override (set, or `""` for the generated brief), and Keep (`--keep-brief` / `keep_brief`, then `POST .../brief-override/keep`). Values are checked against the limits in 1.1 before anything is sent; nothing is cut short. Brief fields keep the analysis; changes to images, notes, mode or strength that change a value clear it. A 403 for the person's override (the person wrote it after the call read the board) comes back in the CLI and MCP's own words, naming the argument to leave out; any other 403 comes back as the backend's sentence, without the canvas-tab advice in the gate's `person_required` text.

The result's `previous` undoes the call when passed as the same call's arguments. It holds only what the call changed, as it was before: the settings, `direction`, `avoid`, `pinned_colors`, `brief_override` (the agent's own text, or `""` for none) and so on that its `PUT` changed, and, for each image it changed, only the image settings it changed (`{}` when the call changed nothing). It also holds `undo`, the checked way back (1.12): one `restore` made of the batch's own `undo` (image settings, the cards a weight rescaled, images it took off) and a `fields` slice for every field its `PUT` changed (what it changed along the way too, such as a colour pinned out leaving Keep anyway), each expecting what the call wrote. Passed back (`undo_board`, `update_board(undo=...)`, `moodboard_update(**previous)`, `set --restore`), it goes as one write; a setting someone changed again since is left as they set it and reported in plain words in `skipped` ("Direction changed since, left as is", "#2's weight changed since, left as is"; the CLI prints each line), and the rest goes back. Images the call took off come back with their cards and notes. The other keys of `previous` are what an older Nebula, without board edits, puts back instead, unchecked; such a Nebula's own `previous` has no `undo`. So undoing it leaves alone what anyone changed since, in what the call changed too. `brief_override` is there only when the change touched the override, so undoing anything else never touches a brief the person wrote since. A call that would replace, clear or Keep the person's override, or Keep with no override, is refused before anything is sent and changes nothing; the message says to leave that argument out. Keep loses nothing, so its refusal gives its own reason: keeping clears the person's notice that the board changed, which is theirs to answer. If the person writes or removes their brief while the call runs, a Keep refused after the other changes were saved says so and hands back `previous` for them (`MoodboardError.previous`; in the MCP error's text; on the CLI's stderr). `nebula moodboard set --restore <file>` sends a saved `previous` (or the whole `set --json` output) back as one change (its `undo` when it has one; `--json` then adds `skipped`); it refuses other flags with it and keys `previous` never has (`moodboard_update` with `undo` likewise refuses `remove`, the list changes and the Keep and clash arguments beside it). A `previous` without `undo` (saved before it existed) is put back as arguments, as before: images the change removed aren't in it, and the result's `removed` URLs add them back. A Keep that got no answer (connect or timeout) says the brief may or may not have been kept, not that it wasn't.

Each image in the client's view carries `setAside` (`excluded` or weight 0, 1.1) beside `excluded`. `nebula moodboard set --set-aside N` and `--use N` flip the switch (`--exclude` and `--include` are their old names and still work; naming one image in both, by number or id, is refused); `show` marks an image "set aside", or "set aside (weight 0)", and `list` counts them beside the image count ("(5 images, 1 set aside, look, ...)"); the Moodboard node card, the Studio's board list and the Assets panel read "5 images · 1 set aside · look" (`frontend/src/lib/moodboardCount.ts`). The count is every image on the board, so a Preview of a run, which counts only the images that steer (`frontend/src/lib/moodboardBundle.ts`, the same `isSetAside` rule), reads one fewer for each set-aside image, switched aside or at weight 0: "5 images · 2 set aside" on the card, "3 images" in the Preview. The node card's count stays on one line, cut with an ellipsis when long, with the whole line as its tooltip; a status in its place ("#id was deleted for good or never existed") wraps, so it is never cut. In `moodboard_update` an image edit's `excluded` is the switch, and `setAside` is the same key (the two must agree); two edits of one change that set one image's switch both ways are refused, with nothing written. Using an image again (`--use`, `excluded: false`) on a weight-0 image sets the weight its card shows, unless the same change sets a weight; the result's `previous` gives the old weight and switch back.

The cover (1.1): `nebula moodboard set <board> --cover <#n|id>` and `moodboard_update(cover=...)` (a number, `#n` or an id) pick it, sent as one `cover` op (1.12) with the call's other image changes; `--clear-cover` and `cover=""` go back to #1. An image not on the board is refused before anything is sent ("no image '9' on this board: use its number (1-3) or id from `nebula moodboard show`"; the `cover` op itself answers 422 "no image #9 on this board (it has 3)"), and so is a call that makes an image the cover and removes it. `show` prints "Cover: #3 (id)", or "Cover: #1, the first image (none chosen)", and marks the cover's row; `list` adds ", cover #3" when one is chosen; `--json`, `moodboard_get` and `moodboard_list` carry `cover: {number, id}` only when one is chosen. `previous` has `cover` (the old id, or `""` for none) and the `undo` carries it as a `fields` slice. On a Nebula without covers the call is refused, with nothing changed.

Each image carries `privateNote` (1.1). `--private-note IMAGE=TEXT` and `{"image": ..., "privateNote": ...}` in `moodboard_update` set it, `show` prints it marked private, `--json` and `previous` include it, and a change to it alone keeps the analysis. On a backend whose images have no `privateNote`, setting one is refused before anything is sent, and `previous` has none.

### 1.7 Opening a board in Moodboard Studio

`#moodboard/<id>` opens Moodboard Studio on that board (`frontend/src/hooks/useMoodboardDeepLink.ts`). The scope it opens with is a hint; the board's own `projectId` decides where the Studio and its rail land. While the Studio shows a saved board the hash names it (replaced in place, no history entries), and leaving the Studio clears it. Loading the app with the link goes into the open project; with none it waits on Projects. Double-clicking a Moodboard (or Character) node, double-clicking an item in the Assets panel, the node's Open button and the Studio's rail all open a board without changing the graph; only "Add to canvas" or a drag from the Assets panel adds a node.

**Board and List (preview).** A Board / List switch in the Studio's header picks how the board shows; the choice is the viewer's own, kept in this browser (`localStorage` `nebula:moodboard-view`, read and written in try/catch; List when there is none). List is the image grid as before, with the cover (1.1): the cover's tile carries a Cover mark (quiet while the board opens on #1 by default), every tile offers Use as cover, the chosen one Back to #1, and the preview beside the board's fields shows the cover with its caption; a pick is a `cover` op (1.12). Board (`components/moodboard-studio/BoardCanvas.tsx`) draws each card (`images[].placements`, 1.1) where the server placed it, at its saved size, in board order (a later number on top), on a second React Flow canvas with its own provider: it never touches the main canvas's graph, camera or selection. Opening a board in either view writes nothing. A card shows the 512 px thumbnail (`?thumb=1`) unless it is wider than about 480 css px on screen, and only the cards in view are drawn. Cards carry no badges yet, the cover's mark included (they come with PR6); the cover is picked in List. Beside the canvas, a panel holds the selected reference's notes, colours, Set aside and weight; with nothing selected, the board's fields, Direction and the rest of the brief fields, the brief and the analysis.

On the board a person drags cards (one `place` op per card a drag moved, sent when the drag ends, not 600 ms later), nudges them with the arrow keys (sent 400 ms after the last key), drops image files (each an `add` with `at`, the first centred at the pointer and the rest in a row beside it; "Add images" puts them in the middle of the view), and removes the selected references with Delete or Backspace. Shift+1 fits the board. Selection and the camera are kept per board for the visit, in memory.

**The Studio's keys and undo** (both views). Cmd+Z and Shift+Cmd+Z (or Cmd+Y) undo and redo the person's own image and card changes in this tab; Cmd+S saves now. All three, and Delete, are skipped in text fields and dialogs, and Cmd+S never reaches the canvas's graph save. Each thing the person did is one step (a drag, a Set aside switch, a note while it is typed, a weight, a cover pick, a removal, a drop; cover picks made before the step is sent join it) and goes to `/edits` as its own batch, so the batch's `undo` (1.12) is that step's. An Undo pressed while a step is still saving waits for it to land, so it undoes that step. Undo sends it without `baseVersion`; what changed since is left and the toast names it ("#2 changed since, left as is"). Redo sends the `restore` the undo answered with, checked the same way, never the step's ops again; an undo that put nothing back (all of it changed since) leaves nothing to redo. A removal shows a toast with Undo. The steps are this tab's, at most 50 per board, and go when the Studio leaves the board (another board, a delete, leaving the Studio). Board fields (name, notes, brief fields) are not steps yet; agents' and Analyze's batches join the stack in later parts.

### 1.8 Dry run

`POST /api/moodboards/{id}/analyze/dry-run` (`moodboard_analysis.dry_run`) runs the same analysis as Analyze and saves nothing: no board write, no `updatedAt` or `version` change, no broadcast. Anyone may call it, agents included. It returns:

| Key | Meaning |
|-----|---------|
| `dryRun`, `id`, `name` | `true`, and the board |
| `thresholds`, `defaults` | The thresholds used and the defaults |
| `saved` | `{analyzed, current}`: whether the board has a saved analysis and whether it still describes the board. When it is out of date, `changes` include edits to the board, not only the thresholds |
| `analysis` | The analysis it would save (1.3a) |
| `brief` | `compose` (1.2) with that analysis: what generators would get |
| `changes.palette`, `changes.accents` | `{before, after, added, removed, nudged, reordered, changed}`. `nudged` pairs a removed and an added colour within dE00 2 (`{from, to}`); `reordered` compares the colours on both lists |
| `changes.brief`, `changes.generatedBrief`, `changes.negativePrompt` | `{before, after, changed}` against the saved board's `brief` |

`thresholds` are Commons' measurement constants (`commons/measure.py`), for this call only: `accentMinChroma` (CIELAB chroma 0–150, default 40), `accentSeparation` (dE00 0–100, default 10) and `mergeDeltaE` (dE00 0–50, default 5; it also sets the board roll-up's merge). One left out or null keeps its default. Nothing saves custom thresholds, and Analyze always uses the defaults. The pinned-colour rule ("within dE00 5 of a kept-out colour") is not a threshold here.

It is a route of its own, not a flag on `/analyze`: an older backend ignores a body it doesn't know and would analyze and save; this route is missing there (404), and the CLI and MCP then say so rather than analyze.

`nebula moodboard analyze <board> --dry-run [--accent-min-chroma N --accent-separation N --merge-delta-e N] [--json]` and `moodboard_analyze(dry_run=True, accent_min_chroma=…, accent_separation=…, merge_delta_e=…)` call it; thresholds without the dry run are refused. `nebula moodboard show` prints each palette and accent colour with its share and source images (`#4 0.35%, #5 0.26%`: image number and the colour's share of it).

### 1.9 Projects: which project an asset is in

Moodboards, Characters and project Styles share one meaning of "project": a **canvas project** from the project catalog (`GET /api/projects`), never the backend's working folder. "This project" or "current" is the one open on the canvas (the catalog's `activeProjectId`).

- `GET /api/project` returns `{id, name}` of the open canvas project, or 404 `"No project is open."`. The app doesn't call it: it reads the open project from its own project store (`frontend/src/lib/currentProject.ts`), which the CLI's and MCP's `current` also resolve to.
- `POST /api/moodboards`, `POST /api/characters`, and `POST /api/presets` with `scope: "project"` take a `projectId` only if it's a canvas project: an unknown id is 422 (`"No project has the id '<id>'. Use the id of a project from GET /api/projects ..."`), a project in Recently deleted is 422 (`"The project “<name>” is in Recently deleted. Restore it first, ..."`), an unsafe id is 400. Leaving `projectId` out saves the asset as Global. Lists still take any safe id.
- An asset never refuses to work outside its project. A Moodboard or Character node names its asset by id, so a node copied, pasted or imported into another project shows the asset, runs, and opens the Studio on it. Saving it from there keeps its `projectId`: it stays where it lives.
- In the app the Project tabs (Assets panel, both Studio rails, the Styles library, Recently deleted, the node pickers) list the open project's assets and relist when the project changes, a `storedAssetChanged` event arrives or the socket comes back after it was closed (`socketReconnected`, 1.12). With no project open the Project tab says `"Open a project to see its moodboards."` (or Characters, Styles) and New is off. A Studio opened on an asset from another project lands on the Project tab with `"This board is in <name>."` (`"This Character is in <name>."`) above the open project's list (`frontend/src/lib/assetHome.ts`). A draft started in one project is never saved into another: the save is dropped if the open project changed.

**Re-home of old-style assets (every start; `backend/services/asset_project_rehome.py`).** Before this, project assets were filed under the working-folder project (`nebula_nodes`, `NEBULA_PROJECT_ID`, ...), which no canvas project could see, and an older build or the desktop app on the same `~/.nebula` can still write one. Every folder under the moodboard, Character and preset roots (each store's own `store_root()`) that isn't `_global`, a canvas project's id or a project in Recently deleted is old-style. Each asset in one is moved by use (Justin picked this rule on 2026-10-19):

| Asset | Goes to |
|-------|---------|
| A Moodboard or Character used by nodes in exactly one canvas project (saved snapshots, and the open canvas for the open project; trashed projects don't count) | That project |
| One used in no project, or in two or more | Global |
| A Style (preset) | Global |

Assets in Recently deleted move too (their trash record's `projectId` and `scopeDir` change, so a restore lands in the new place). Only `projectId` changes (and a preset's `scope`, to `global`). It runs on every start; a start with nothing old-style writes nothing. Each moved file is first copied to `<root>/../<kind>-backups/project-rehome-<UTC time>/`, with `migration-log.json` listing every asset, where it went and why. An id already present in the target is skipped and logged once: `<state dir>/migrations/asset-project-rehome.json` remembers each skip by path, size and mtime, so the same skip isn't logged again, a changed file is, and the move happens on the first start after the collision is gone. Nothing changes while the catalog can't be read, or while there are old-style assets and an open canvas but no projects yet. It never stops the backend from starting, and prints one line only when it moved something or found a new skip; `NEBULA_NO_ASSET_REHOME=1` turns it off. To undo a re-home, stop the backend, copy the backup folder's files back over the root, delete the moved copies the log names (`file`), and start with `NEBULA_NO_ASSET_REHOME=1` (otherwise it moves them again). `move_asset(kind, root, source, target)` in the same module moves one asset between scopes with the same checks; 1.10 builds on it.

### 1.10 Moving a board or Character between Global and a project

Justin's call P4 (2026-10-19): a re-home that guessed wrong can be put right, and a board made in one project can become house style.

| Call | Body | Effect |
|------|------|--------|
| `POST /api/moodboards/{id}/move` | `{projectId: string \| null}` (required; null = Global) | File the board under that canvas project, or Global |
| `POST /api/characters/{id}/move` | same | Same for a Character |

- **Answer.** `{status, kind, id, from, to, fromName, toName, asset, detail}` plus `movedBy` when it moved. `status` is `moved`, or `unchanged` (200) when it was already there: nothing is written or broadcast. `from` / `to` are project ids (null = Global), the names are the catalog's (`Global` for none). `asset` is the asset as `GET` returns it.
- **Refusals.** An unsafe `projectId` (`""` included) is 400; a body without `projectId`, or with other keys, 422; a target that isn't a live canvas project is 422 with the create routes' sentences (1.9); no such asset is 404; one in Recently deleted is 409 (`code: "in_trash"`, "Restore it first ..., then move it."); two live copies of the id (a re-home that skipped a collision leaves one in an old folder), or a copy already in the target, is 409 and changes nothing.
- **What changes.** Only the file's folder and `projectId` (`asset_project_rehome.move_asset`). `id`, contents, `version` and `updatedAt` stay: a move isn't an edit, so it bumps no `version`, and a Studio's checked write (1.12, 2.1) made after a move still holds. A node in any project still names it by id, so it shows and runs as before. `storedAssetChanged` is broadcast, so cards, both Studio rails and the Assets panel relist.
- **Who.** Anyone, agents included: moving it back undoes it. Boards and Characters keep no "changed by" field, so `movedBy` (`actor_record`, as Recently deleted's `deletedBy`) is in the answer only; nothing is journaled.
- **Studio.** Moodboard Studio and Character Studio show **Move** beside Delete for a saved asset, a menu with "Move to Global" (when it's in a project) and "Move to <open project>" (when it's Global or in another project; off, saying why, with no project open). Unsaved edits are saved first, as Delete does; a failed save stops the move. During the move the draft's save slot is held, so no autosave sends the old `projectId`; edits typed meanwhile are kept and saved after. Then the draft's `projectId` changes, the draft moves to its new scope's key (`assetStudioDraftKey`, `copyTo`, as on create), and the Studio opens the asset in its new scope, so the rail switches tab and its "This board is in <X>" notice follows (`frontend/src/hooks/useStudioAssetMove.ts`, `lib/assetMove.ts`, `components/asset-move/AssetMoveMenu.tsx`). A board's `PUT` still refuses a `projectId` change (422), which is why the draft must carry the new one.
- **CLI and MCP.** `nebula moodboard move <board> --to global|current|<project id or exact name> [--json]`, `nebula character move <character> --to ... [--json]`, `moodboard_move(board, to)`, `character_move(character, to)` (`moodboard_client.resolve_move_target` / `move_asset`, `character_client.py`). `current` with no project open, an unknown project, a name two live projects share, or a project in Recently deleted is refused before anything is sent. On a Nebula without the route they say so and move nothing.
- **Not here.** Styles (presets) have no Move; P4 named boards and Characters.

### 1.11 When the words and the measured colours disagree, and board notes

Design-canvas gap 18 (Justin's calls P1-P4, 2026-10-19). Where two parts of a board disagree, the higher wins; where it says nothing, the lower fills in: (1) the hand-written brief, as is, no check; (2) pinned colours: "must appear" always go, even against Avoid (the clash is listed), "keep out" drops near measured colours; (3) Direction and Avoid, through the colour check; (4) board notes, only when opted in; (5) what Nebula measured.

**Saved fields** (all optional; a board without them reads with the defaults and is never rewritten on read):

| Field | Type | Who writes it | Notes |
|-------|------|---------------|-------|
| `clashMode` | `leave-out` \| `flag` \| `no-measured` \| `keep-all` | person or agent | What a clash does. `leave-out` (default): a conflicting colour leaves the brief, listed with its reason; a warning stays, listed as "may clash". `flag`: nothing leaves unless the person says so; every clash is listed. `no-measured`: once there is a Direction, no measured colour goes (each listed, "Measured colors are off for this board"); without one it acts as `leave-out`. `keep-all`: as before this change; the check still runs and is saved, nothing is listed or applied, choices are ignored. Anything else is 422 |
| `colorChoices` | `{keep: hex[], leaveOut: hex[]}` | person or agent | The person's Keep anyway and Leave out. At most 24 per list, `#rrggbb`, a colour in one list only, and Keep anyway can't hold a colour pinned to keep out (422). Matched to measured colours within dE00 5, nearest first, so a choice survives a re-analysis that nudges the hex. Keep anyway doesn't pin: the colour goes back with its share and role. Pinning a colour to keep out drops it from `keep` when `colorChoices` isn't sent |
| `sendNotes` | boolean | person (on), anyone (off) | Board notes and image notes to generators. Off by default, on every board. Strictly `true`/`false` (422 otherwise). Turning it on (create with `true`, or `false` to `true`) is the person's: 403 with the person gate's `code` and a sentence about notes, and nothing in that request is saved. Sending `true` again when it is already on passes. An agent asks with `propose_asset_change(kind="moodboard", id, change={"sendNotes": true})` (`POST /api/asset-proposals`); the person decides in Moodboard Studio under the switch, and Accept sets it as a `PUT` from the person would (MCP-SETUP, Proposals outside the canvas) |
| `colorCheck` | `{version, basis, checks: {words: {version}}, findings}` | store | The saved check. Refreshed on every create and update (Analyze included) whose basis moved, and at startup for every board whose saved one is missing or stale (boards saved before it, a `LEXICON_VERSION` bump; only `colorCheck` is written, no backup): Direction, Avoid, pinned "must appear", the measured colours (hex, role, share), `LEXICON_VERSION` and the check's own version. A sent one is ignored |

**The check** (`services/moodboard_colour_words.py`, deterministic, no model, no cost). The Direction and Avoid text is parsed into colour terms with their modifiers, negation ("no", "without", "avoid"; it covers the noun phrase it governs, so it ends at "but" or at a comma or "and" after its noun: "No people, red flowers" allows red, "no red or orange flowers" excludes both) and scope (an object such as "flowers", a cast, or the whole palette), then matched in OKLCH by hue arcs and chroma gates; a hex written in the text matches within dE00 5. A cast term tests the share-weighted palette mean, so one warm accent on a cool board is only a warning. A Direction allowance that names the colour ("cornflower blue", a hue within its modifiers' gates, a hex) turns an Avoid conflict into a warning; one the colour only shares a hue arc with ("pale blue" for a saturated blue), and any temperature word ("warm", "cool"), leaves the conflict as it is. "Brown" conflicts from C 0.08 like any hue (only soft-colour words such as sage and lilac conflict from C 0.03), so near-black shadows are at most a warning. The allowance also flags a colour of that hue that is clearly more saturated than the reference. The numbers sit in one table and are retuned by bumping `LEXICON_VERSION`, which refreshes saved checks. Each finding: `{hex (null for the whole palette), role (palette, accent, pinned), share, level (conflict or warning), source (avoid or direction), clause, rule, reason, foundBy}`. A `reason` starts "Avoid: <the item>" or "Direction: <the person's words>" and quotes only whole words as written (any letters; a hyphenated word is one word). When a Direction allowance makes a clash a warning it adds the allowance's words in quotes through their noun phrase, plus "in the <noun>" for a list item that takes its head's noun: "Direction: sun-faded. This color is more saturated than that, though the Direction also asks for “Warm late-summer light”." and "Avoid: blue flowers. The Direction also asks for “cornflower blue”, so it may clash." (`LEXICON_VERSION` 3, 2026-10-20; version 2 quoted the first noun alone, "allows Warm for the late"). `foundBy` is `words` today. A second check (one that looks at the images) adds `checks.<name>` and its findings under the same basis; `compose` uses a saved check whose basis matches, else runs the words check in memory without saving.

**`brief` adds** (1.2): `leftOut` (colours generators don't get), `mayClash` (still sent), `kept` (Keep anyway), `pinnedClashes` (pinned colours that clash; they still go), `paletteClashes` (whole-palette findings, such as a cast), each item `{hex, role, share, level, reason, reasons, foundBy, why}` with `why` `check`, `choice` or `mode`, and `level` `off` for one left out by `no-measured`; `clashMode`; `notesSent`. `palette`, `accents` and the brief's colour sentences are what generators get. The lists are computed with an override active too, since they shape `palette`.

**Notes.** Without the opt-in the brief has no `Notes:` sentence and its visual cues are only the measured ones (`MEASURED_CUES`: palette-led, the mode cues, the palette labels), not words lifted from the notes. Agents and the person still read notes everywhere. A board at strength 0 sends nothing, opted-in notes included (1.4, Q36 a).

**The node.** `nebula-moodboard` gains `send_notes`: `board` (default; follows `sendNotes`), `yes` or `no`. A node saved before it reads `board`. Moving it toward sending (`no` to `board`, anything to `yes`, a new node on `yes`, or pointing a node on `yes` at another board) is the person's: an agent's edit, create or apply gets 403 naming `send_notes` and `propose_change`. Its bundle: `notes` and `images[].notes` are `""` unless sent; `notesSent`, `leftOut`, `mayClash`, `kept`, `pinnedClashes`, `paletteClashes` and `clashMode` are added; `analysis` is the generator's view (measured keywords only, `summary` and `tasteProfile` rebuilt from the brief's colours without notes, `subjectBias` `[]`, `styleBrief` without notes, `images[].notes` `""`, `providerHints.generic.palette`/`accents` the brief's). Its colour lists are the brief's too: `palette`, `accents` and `colors` hold only what generators get, and each image's `palette`/`accents`/`colors` drop colours within dE00 5 of one left out or pinned to keep out, so an LLM node reading the bundle can't put one back. `leftOut` says which went and why. The saved analysis is never changed.

**CLI and MCP.** `show` prints "Left out of the brief:" (each with `Keep it: nebula moodboard set <id> --keep-anyway "#hex"`), "Kept anyway", "May clash (still sent):", "Pinned colors that clash (still sent):", "Notes: not sent to generators" (or "sent") and "Clash check: <mode>" when not the default. Each line gives every reason (`reasons`, joined with "; "; Studio joins them with " · "), so a colour off for `no-measured` still shows its clash. `set` takes `--keep-anyway`, `--leave-out`, `--leave-out-flagged`, `--reset-color`, `--clash-mode`, `--send-notes` / `--no-send-notes`; `moodboard_update` takes `keep_anyway`, `leave_out`, `leave_out_flagged`, `reset_colors`, `color_choices`, `clash_mode`, `send_notes`. `--json` and the MCP tools carry `clashMode`, `colorChoices`, `sendNotes` and `colorCheck`. `previous` has `clash_mode` and `color_choices`, and `send_notes` when the change touched it. An agent's `--send-notes` is refused in the CLI's own words and nothing in the call is saved.

**Studio.** Under "Brief sent to generators": "Left out of the brief" (Keep anyway, or Undo for one the person left out), "Kept anyway" (Undo), "May clash" (Leave out), or in `flag` mode one "Flagged" list with Leave out all flagged, and "Pinned, so it still goes". `keep-all` shows "Clash check is off for this board." The swatches dim a left-out colour, with the reason in its tooltip. `BriefFields` has an Advanced disclosure with the four modes; under Notes, a "Send these notes to generators" switch, off. The Studio shows the backend's lists and never recomputes them.

### 1.12 Board edits

`POST /api/moodboards/{id}/edits` (`services/moodboard_edits.py`, moodboard canvas plan section 5.1). The body is `{ops, baseVersion?, say?}`: 1 to 500 ops, the version the caller read, and up to 140 characters of what an agent is doing (trimmed, for the journal). The ops are staged on a copy of the board, each checked as it applies, and saved once with `version + 1`; an op that fails refuses the whole batch with 422 naming it ("op 3 (place): ..."), and nothing is saved. 404 for an unknown board or one in Recently deleted. Anyone may send edits, agents included: every batch is undoable and journaled.

**Ops are absolute sets** ("image 3 weighs 0.5", "card c1 at 200, 40"), so a batch sent twice changes nothing the second time. Names: an image by its id or its number (`#n`, as the board was before the batch, so numbers in one batch don't shift as images go); a frame by id or name (ignoring case); a card by its placement id, `image@frame`, or the image when it has one card.

| Op | Keys | Effect |
|----|------|--------|
| `add` | `urls` or `images` (`{url, id?, weight?, notes?, privateNote?, excluded?, placements?}`), `index?`, `at?: {x, y}`, `in?: frame`, `size?: weight or "WxH"`, `unique?` | Adds images at `index` (default last). Placed by the server (1.3) unless they send `placements`; `at` is the top-left, `in` lays them out in the frame (it grows to fit). With `unique`, a url already on the board is skipped; an id already on the board is always skipped. `applied[i]` has `added` (ids) and `skipped` |
| `remove` | `images` (or `image`) | Removes them; one already gone is `unchanged` |
| `place` | `placement` (the card) or `image`, `x`, `y`, `frameId?` | Moves a card. `frameId` moves it into that frame (refused with "Already in <frame>" when the image has a copy there) or, with `null`, out of its frame: the copy is removed when the image has another, else it becomes loose |
| `resize` | `placement` or `image`, `weight` or `w` and `h` | Card weight 0.05 to 1; `w × h` keeps the card's aspect. The image's weight becomes its largest card's |
| `link` | `image`, `frameId`, `x?`, `y?`, `weight?` | A copy of the image in a frame (at most 8 cards, one per frame; "Already in <frame>" otherwise). A loose card joins the frame instead of making a copy |
| `unlink` | `placement` (a card in a frame), or `image` and `frameId` | Takes the image out of that frame: the copy goes, or, when it is the image's only card, it stays as a loose card |
| `setAside` | `image` or `images`, `value` | The Set aside switch (1.1). Off on a weight-0 image also sets the weight its card shows |
| `weight` | `image` or `images`, `value` | 0 to 1; the cards scale as on `PUT` (1.3) |
| `note` | `image`, `notes?`, `privateNote?` | Either or both |
| `frame.create` | `name?` (default "Look N"), `kind?`, `x, y, w, h` or `rect`, or `around: [cards]`; `id?` | A frame (at most 100, names unique ignoring case, sides at least 160). `around` fits the cards with a margin and moves them in; a rectangle takes the loose cards wholly inside it |
| `frame.update` | `frame`, `name?`, `x, y, w, h` or `rect` | Rename or move/resize; a move moves its cards, and it can't shrink to cut one off |
| `frame.delete` | `frame` | Its cards stay where they are, loose (a copy whose image has another card goes) |
| `frame.merge` | `frame`, `into` | The cards move into `into`, which grows to hold both; where an image is in both, the heavier copy stays |
| `cover` | `image` (number, id, or null) | Makes the image the board's cover (1.1), or with null opens the board on #1 again. Moves no image and keeps the analysis; an image not on the board is refused, and so is a batch whose last `cover` op picks an image the batch takes off the board (422 "image #2 can't be the cover and come off the board in one batch: pick one"); an earlier pick that a later `cover` op replaces or clears doesn't count |
| `restore` | `slices` | An undo (below) |

`arrange`, `look.set`, `look.inherit`, `suggestion.accept`, `suggestion.dismiss` and `realPerson` are refused by name: they come with later parts of the board canvas.

**The answer** is `{board, version, applied, undo}`. `applied` has one entry per op: `{index, op, status: "applied" | "unchanged", ...}`. `undo` is `{ops: [{op: "restore", slices}]}` (or `{ops: []}` when nothing changed): each slice holds the before value of one frame, image, image's settings or image's cards, or of the board's own fields, and the `expect`ed after value. Sent back as edits, a slice whose part changed since is skipped and reported (`applied[0].skipped`, each `{part, image or frame or field, number?, reason, message}` with `message` such as "#4 changed since, left as is"), so one stale reference doesn't stop the rest; a `restore` has its own `undo`, and its `applied` entry also lists `removed`, the image ids it took off the board. Image settings go back one by one: one that changed since is left ("#2's weight changed since, left as is", with `settings` naming it) and the others go back; the image's card slices aren't reported again then. A `fields` slice (`{part: "fields", before, expect}`) holds `name`, `notes`, `mode`, `strength`, `direction`, `avoid`, `pinnedColors`, `clashMode`, `colorChoices`, `sendNotes`, `briefOverride` (its text, `""` for none) and `coverImageId` (an id or null), as a write reads them (the brief fields normalized); each field is checked on its own, against the board as the restore found it, and set as a `PUT` sets it, last in the restore, so a hand-written brief is stamped with the board as it ends up. One changed since is left ("Direction changed since, left as is"), so is one whose going back would undo a colour choice made since, unless the slice puts `colorChoices` back too ("The pinned colours would undo a colour choice made since, left as is"), and so is one only the person may set this way when an agent sends it ("Send notes to generators is the person's to turn on, left as is"; "The hand-written brief is the person's to change"); a value a `PUT` would refuse is a 422. Every batch's diff carries a `fields` slice when the board's fields changed, so a `restore` that put fields back has an undo for them too. Putting back the board's mode, strength or notes clears the analysis, as a `PUT` does. What a slice puts back is checked as the ops and `PUT` check it (422): a `before` names the same image, frame or card as its slice, an image record has a url, and settings are a weight from 0 to 1, text notes, a private note of at most 2,000 characters and a true/false switch. A frame a restore touched grows to hold its cards, so a partial undo never leaves a frame smaller than a card still in it. The whole-board analysis is cleared when what it reads changed (each image's url, weight, notes and switch, and their order); moving or resizing a card without changing the image's weight, frames and private notes keep it.

**`baseVersion`.** On `/edits` and `PUT`, a `baseVersion` that isn't the board's version is a 409: `{detail, code: "version_conflict", version, board}`, with the board as it is now, so the caller rebases on it and sends again. Without it a write applies to whatever is saved. Writes to one board are serialized, so two writers racing never lose an edit: ops apply to the board as saved, and only a `PUT` that sends `images` (the whole list) can still undo another writer's image change, which `baseVersion` prevents.

**The broadcast.** After a board write that changed something, `storedAssetChanged` adds `version`, `edit: {actor, tab?}` (`_graph_edit_origin`: `tab` only with this launch's person token, so an agent can't pass for a tab), `touched: {images, frames, looks}` and `undo` (null for a `PUT`, or for a batch over 200 ops). An `undo` that holds private-note text (a private note changed, or an image with one added or removed) goes whole only to the person's canvas sockets; every other listener (CLI, MCP) gets `undo: null`. Keep and Analyze send `version` and `edit` with nothing touched.

**The journal** (`canvas_events`, as for the canvas). Each batch, and each `PUT`, that changes one of these is one event in the actor's name, tagged with the open canvas project: `board.added`, `board.removed`, `board.frame`, `board.grouped` (a card into or out of a frame), `board.setAside`, `board.resized`, `board.noted` (an image's notes), `board.moved` or `board.cover` ("made #3 the cover of board Dusk", "set the cover of board Dusk back to #1"), first of those that applies (a cover picked with another change isn't listed in that change's summary: the Agent log adds "made #2 the cover" after it); `data.kinds` lists every kind in it, with `refs` (`{number, id}` per image) and the board's id, name and scope. A move under 8 px isn't journaled. The board's own fields are one `board.fields` event per write (Q91, 2026-10-21), after the event above when the same write changed images too: `data.fields` names the fields that changed (`name`, `notes`, `mode`, `strength`, `direction`, `avoid`, `pinnedColors`, `clashMode`, `colorChoices`, `sendNotes`, `briefOverride`, in that order; the cover stays `board.cover`), with the board's id, name and scope, and never a value (no text, colour, number or on/off): "changed Direction and the Avoid list on board Dusk". A write that changes no field writes none. A setting an older image was saved without compares as its default, so saving that default isn't a change. Never any note text: a private note change reads "private note changed". An agent's batch or `PUT` is also one Agent log line in these words (1.13). `board.sorted`, `board.arranged` and `board.suggested` are reserved for Analyze.

**Clients.** `moodboard_client.edit_board(api, ref, ops, base_version=, say=)` sends a batch; a 409 comes back as "the board changed since you read it (it is at version N): read it again ...". Agents send any of these ops with MCP `moodboard_edit(board, ops, base_version?, say?)` and CLI `nebula moodboard edit <board>` (`--place CARD=X,Y`, `--resize CARD=WEIGHT|WxH`, `--in CARD=LOOK`: a loose card joins the look, a card in another look moves there as a `link` with its weight plus an `unlink` of the old card; `--link IMAGE=LOOK`, `--set-aside`, `--use`, `--note`, `--private-note`, `--ops FILE|-`, `--base-version`, `--say`; `moodboard_client.edit_ops` turns the flags into ops). Both answer with the board in the layout view (`placements`, `frames`), `version`, `applied` and `undo`; sending the `undo` back (`moodboard_edit(board, undo.ops)`, `edit --undo FILE|-`) is the checked undo, and the CLI prints what it skipped and the command that undoes an edit. The client's layout view (`moodboard_get`, `show --json`, `moodboard_edit`, `edit --json`) carries `version`. `add_to_board` sends one `add` op with `unique` (a PUT on an older backend) and returns the batch's `undo`; `update_board` (`nebula moodboard set`, `moodboard_update`) sends its image changes and removals as one batch of absolute ops by image id, then the board's own fields with a `PUT` of only the fields the call sets, with `baseVersion` (the whole image list, unchecked, on an older backend; a backend that refuses the `baseVersion` key gets the same `PUT` again without it). On a 409 it reads the board again and sends the fields again, at most 3 tries in all: a value given outright goes as given, a change to a list (`avoid_add`, `pin_colors`, `keep_anyway`...) goes on the list as it is now. A field given outright that someone else changed since the read, to anything but the same value, is never sent over theirs: the call stops with "<field> was changed by someone else after this call read the board, so it wasn't set. Nothing more was written" (and `previous` when the image changes were already saved); running it again reads their value and then wins. Three conflicts in a row stop with "The board kept changing while this ran (3 tries)". `previous` holds only what the call changed (fields as the board the `PUT` replaced had them, image settings as read) plus `undo` (1.6), and is left out of an error when that is nothing. `undo_board(api, ref, undo, fallback=)` sends an `undo` and returns `(board, removed, previous, skipped)`; on a backend without `/edits` it runs `update_board(**fallback)`. An image op on an image someone else took off the board since the read is refused by the batch, and `update_board` says so by the number the caller read: "Image N was taken off the board by someone else after this call read it, so nothing was changed". After a 409, a call left with nothing to send returns the board as it read it again; `nebula moodboard add --json` and `moodboard_add` return `addedIds` and `undo`, and the CLI prints how to take them off again. Moodboard Studio (`lib/moodboardEdits.ts`) applies each image change to its draft at once and queues it as an op (one per thing set: typing a note queues one), sent 600 ms after the last change or when a field loses focus (a drag, a drop or a removal at once), with the version it last read, one batch per undo step (1.7). On a `storedAssetChanged` for the open board with a newer version and no tab of its own, it reads the board again and replays its queue on top, dropping a queued op on an image that is no longer there; board fields the person changed since keep their value, the rest take the board's. The backend doesn't replay what it broadcast while a tab's socket was closed (a backend restart, a sleeping laptop), so when the socket opens again the client says `socketReconnected` (`lib/wsClient.ts`, client-only, never the backend) and the open Studio reads the board the same way (kept only if its version is newer), while the canvas cards (`storedAssetsStore`), both Studio rails, the Assets panel, the node pickers and Recently deleted read or list again. After a `PUT`, the fields it sent count as read with the values the person sent, not the ones the server cleaned (trimmed, lowercased), so a later outside edit of them still shows. A 409 does the same, then sends again. A draft kept from an earlier visit opens without a fetch, so the read the Studio makes for its brief also follows the board when it is newer: an edit made while the Studio was closed shows once it opens. Kept drafts follow a move made while the socket was closed too: on `socketReconnected` each kept Studio draft (Moodboard or Character, with a saved id) reads its asset and takes its `projectId` and key (`lib/keptDraftMoves.ts`, as the move broadcast does, 1.10); a draft whose asset is gone or can't be read then is left as it is.

### 1.13 Reading references

Plan v2.4, PR4 (§5.6, §5.6.1; Justin's calls Q11, Q16, Q17, Q29), with plan v2.6's reading source (§5.6.2). A vision model reads the board's references and says how Analyze would sort them into looks. Only the dry run exists: it is paid, it saves nothing and moves nothing (no board write, no `version` or `updatedAt` change, `readings` untouched, no `lastRead`). PR10 adds applying it and the Studio's own confirm.

**Reading sources** (`services/moodboard_reader.py`). The provider call sits behind one interface, `ReadingSource`: `identity` (`{kind: "reader", id, name, color, model?, provider, source: "model" | "agent"}`), `priced` ("Nebula pays": true for Argon even with no list price, false only for an agent, PR10c), `streams`, `thoughts`, `async read(task, sink) -> {closed, truncated, cause?}`, `async sort(task, sink) -> {value | cause, truncated}` and `can_widen(task)`. Shared code builds every task (`ReadTask`, `SortTask`: labels, image parts, instructions and schema, notes per `sendNotes`, never `privateNote`), so a source can't add or drop an instruction. A source hands each item to `sink.focus(label)` and `sink.item(raw)`, which run the shared item check and write the trace; it never writes a line itself. Also shared: the reason trim and strip, the new-look-name check, the retry for missing refs (split in two halves only when the source reports `truncated`), the sort rules, the trace and its templates. `GeminiSource` is Argon's: it wraps the Gemini request and stream parser below, reports `truncated` for `finishReason: MAX_TOKENS`, and `can_widen` says whether a lone cut-off image (or the sort) can go again at a raised output cap. The estimate and the spend gate run only when `source.priced` (`read_estimate`, `gate_items`); a source Nebula doesn't pay for gets `{model, reader, count, targets, unreadable, batches, billedTo: "agent", usd: null}` and no gate. Today every route uses `GeminiSource`.

**Readers.** `backend/data/moodboard_reader_models.json`, one entry per reader, checked at load (`moodboard_reader.validate_models`). Today one: `gemini-4-argon` (Google, `GOOGLE_API_KEY`, `definitionId` `gemini-chat`, streams, `thoughtSummaries` `"unconfirmed"`, `defaultThinkingLevel` `medium`). Each entry holds the thinking allowance per level (`low` 2048, `medium` 6144, `high` 16384 tokens; `allowancesUnconfirmed` until the probe), `answerTokens` `{perImage: 450, base: 300}`, `sortTokens`, `imageTokens` (1120, Google's default for an image on Gemini 4), `timeBounds` per level, dated `prices` rows (`{from, until, inputPerMTok, outputPerMTok}`, no gaps; Argon: $2.00 / $10.00 through 2026-11-30, then $4.00 / $20.00, thinking billed as output), `sources` (the pages and the quotes they hold) and `checked` (2026-10-20). `thoughtSummaries` is `true`, `false` or `"unconfirmed"`; only `true` sends `includeThoughts`.

**Body** (both routes; `MoodboardReadRequest`, extra keys 422): `{model, imageIds?, thinkingLevel?}`. `model` is a reader's key, `imageIds` the images to read (all when left out; an unknown id is 422), `thinkingLevel` `low`, `medium` or `high` (the reader's default when left out).

**`POST /api/moodboards/{id}/read/estimate`** sends nothing and returns:

| Key | Meaning |
|-----|---------|
| `model`, `reader`, `thinkingLevel` | The reader and level the read would use |
| `count`, `targets`, `unreadable` | Images that would be read; images asked for; numbers of those that aren't a file on this computer (skipped) |
| `batches` | Requests in phase 1 (6 images each) |
| `low`, `high` | USD. `low`: every image at `imageTokens`, prompt text at 4 characters a token, at today's input price, plus each request's output cap at today's output price. `high`: text at 3 characters a token, one split retry per batch, the sort's retry at twice its cap, at the higher of today's and the next row's prices. `null` when the reader has no price |
| `unpriced`, `unconfirmed`, `allowancesUnconfirmed` | No price row covers today; the price is not a list price; the thinking allowances are not measured yet |
| `price` | `{low, high, units}`: the rows used |
| `perBatch`, `phase2` | Per request: `inputTokens [low, high]`, `maxOutputTokens`, retry tokens, `low`, `high` |
| `shares` | The high estimate split per request (`batch:N`, `retry:N`, `sort`, `sort-retry`), which add up to `high` |
| `sources`, `checked`, `thoughtSummaries`, `streams` | From the reader's entry |
| `available` | Whether the reader's key is set |

**`POST /api/moodboards/{id}/read?dryRun=1[&stream=1]`.** Without `dryRun` it is 422 and nothing is sent. Nothing readable is 422. A missing key is 400 and nothing is charged.

- *Phase 1.* Batches of 6, at most 2 in flight, each image the longest edge 1024 px as JPEG. The images are labelled A to F in the batch; prompts never carry board numbers. Board and image notes go only when `sendNotes` is on (1.11); `privateNote` never. The answer is JSON in `generationConfig.responseFormat.text` (`{mimeType: "APPLICATION_JSON", schema}`; `responseSchema` is deprecated), one item per image with `ref` first and `reason` last. Items are parsed as the stream arrives, so each reading is a line as soon as it closes, and a reader that doesn't stream gives the same lines. A wrong or repeated `ref` is dropped (the first wins). Missing images get one retry, in two halves after `MAX_TOKENS`; a single image left can't split, so its retry goes at twice the cap (up to the model's output limit), and when the cap can't grow the retry isn't sent (the same request again) and the image is couldn't read; the same holds for the sort's retry; 400, 401, 403 and 404 are not retried. Bounds per request (first byte, quiet stretch, total): 60/60/180 s at low and medium, 120/120/300 s at high. Reasons and thought text lose image labels and `#n` (also ranges like "images A–C" or "A to C", and a bare "(B)") and are cut to 120 characters at a word.
- *Phase 2.* One request sorts the readings into looks (the board's frames, matched ignoring case, plus new ones). Nebula enforces the rules, not the model: a best fit below 0.5 is Unsorted; at most 8 new looks; "Unsorted" is never a look; a second fit of 0.5 or more is an `alsoIn` suggestion; 3 or more images sharing the same two looks become one hybrid suggestion "A × B". A new look's name must pass the look-name check (`check_look_name`). It is normalized first (`normalize_look_name`: composed to NFC, ’ ‘ ʼ to `'`, – — ‐ ‑ to `-`, nothing else mapped, spaces collapsed), and the normalized form is what is stored and shown. Then: no compatibility characters (fullwidth, mathematical, superscript, circled, ligatures; refused, not folded), 1 to 60 characters, checked whole and never cut, at most 4 words (a word is a run with a letter or digit, so a lone `&` or `-` doesn't count), only letters, decimal digits, spaces and `&-'`, and no `#n`, batch or sort label in any case (`Image B` or `image b`, but not the article in `Photo a day`; `R3`, `r3` or `R 3` as a word; or a name whose every word is a batch label: `B`, `b`, `'B'`, `A & C`, though one letter repeated, `B&B`, is a phrase), link or `@`. A letter glued to `&`, `/`, `-` or `'` and more of a word (`B&W`, `B/W`, `B-movie`) is never a label, in a name or when labels are stripped from a reason or thought (the join before it goes with the stripped label). The label and link checks read other scripts' look-alikes as the letter they copy (`skeletons`, a UTS #39 confusables subset for the characters those checks match: Cyrillic `Image В` and `г3` are refused; for `#n` and sort labels any script's decimal digit stays a digit, `R١`, and a look-alike of 1 or 0 is that digit, `RӀ2`), while the name keeps its own letters (`Тёмный` passes). A name that fails is dropped: an image whose best look it was is Unsorted ("its look's name was refused"), not moved to its second look, and it is never a second look or in a suggestion. Looks match the board's frames on the normalized name, ignoring case; when two frames share it, the one whose name is exactly the one given wins, else the first on the board. The board's own frame names aren't checked. The sort task carries only the sort source's own readings: `build_sort_task(…, reader=…)` raises `MixedReadersError` for a reading by any other reader. Two spellings of one new look become the first one given. If the sort fails after its retry, each image keeps its reading's own look under the same check (a reading's look names are composed and then kept up to 120 characters, so an over-long one is refused rather than cut to fit) and `sortError` says why. A `reading` trace line adds "→ name" and `look`/`fit` only when the reading's first look is a board frame or passes the check.

**Answer.** Without `stream` it returns the result with its `trace` and the `estimate`. With `stream=1` it is NDJSON: one `moodboardReadTrace` row per line as it is written, then one `moodboardReadResult` (the result without `trace`), or a `moodboardReadError` `{detail}` if it fails after the stream started.

A trace line: `{type: "moodboardReadTrace", boardId, jobId, seq, kind, source, text, refs, phase, batch?, attempt?, look?, fit?, at}`. `seq` counts from 1 with no gaps; `text` is at most 200 characters; `refs` are `{imageId, number}`; `source` is `nebula` or `reader`. `kind` is one of `batch`, `focus`, `reading`, `retry`, `skipped`, `error`, `thought`, `result`, `suggestion` or `done`. Thought text from the reader is merged into lines of at least 250 ms and cleaned like reasons.

The result: `{dryRun: true, applied: false, runId, boardId, reader, requestedBy, model, thinkingLevel, thoughtSummaries, results, suggestions, newLooks, readings, summary, spent, sent, sortError, ignored, trace}`. `reader` is the source's `identity` (`source: "model"` for Argon); `model` is the reader's key (`gemini-4-argon`). Each of `readings` (by image id, never saved by the dry run) is `{model, reader, readerName, at, url, readerVersion, medium, style, light, motifs, looks, reason}`, with `reader` the identity's id without `reader:` and `readerName` its name (1.1's `readings`). Each of `results`: `{number, id, status, look, frameId, fit, newLook, why, reason}`. `spent` (`{inputTokens, outputTokens, thoughtsTokens, requests, requestsWithoutUsage, usd}`; null for a source Nebula doesn't pay for) is the USD the usage reported comes to at today's row. It is a minimum: a request that ended without `usageMetadata` (a 5xx, a time bound) counts in `requests` and in `requestsWithoutUsage` but adds nothing to `usd`, and Google may still bill it; the CLI says so under its spent line. `sent` lists the requests that started.

**Spend gate.** A read that isn't the person's goes through `agent_spend.decide` as one run of `gemini-chat` (item `_moodboard-read`), priced at `[low, high]` from the estimate, so the Gemini chat node's per-run and session limits in Settings > Agent spending apply. A refusal is 403 with the price and how to ask (raise the limit, or price it with `--estimate`). An allowed read is held at its high estimate, split into the per-request `shares`; the share of every request that never started is given back (a started one stays charged, since whether an aborted stream is billed is unconfirmed). A read with no price is refused under any USD limit. The person's own reads skip the gate.

**CLI and MCP.** `nebula moodboard analyze <board> --read-with gemini-4-argon (--dry-run | --estimate) [--only 3,5] [--thinking-level L] [--quiet] [--json]` and `moodboard_analyze(board, read_with=…, dry_run=True | estimate_only=True, only=[…], thinking_level=…, include_thoughts=…)`. The CLI prints the estimate, then each line as it streams (`#21  clouds under a halftone screen → Dither (0.82)`), the done line ("Dry run: would sort N into M looks (K new) · U Unsorted · nothing moved") and what it spent; `--quiet` prints only the done and spent lines. `--read-with` without `--dry-run` or `--estimate` is refused, and so are the reader flags without `--read-with`. The MCP answer has the results, the last 20 lines that aren't `focus` or `thought`, and the thought lines only with `include_thoughts`.

**Probe.** `backend/scripts/moodboard_reader_probe.py` makes the one real request the plan describes (paid; it refuses without `--yes-spend` and prints the estimate first): one batch of up to 6, once with summaries off and once with `includeThoughts`, reporting chunk times, first byte, first item, usage and whether summaries came back with the schema held. Its numbers set `thoughtSummaries` and the thinking allowances.

### 1.13 An agent's board writes in the Agent log

When an identified agent (an agent token or `X-Nebula-Agent`, the same identity that names its cursor) makes, changes, analyzes, keeps the brief of, moves, deletes or restores (from Recently deleted) a board, the route broadcasts an `agentPresence` event with no `target` after the write is saved (`main._say_agent_action`): "Made board Dusk with 4 images", "Analyzed board Dusk", "Kept the brief on board Dusk", "Moved board Dusk to Global", "Deleted board Dusk", "Restored board Dusk" (`services/moodboard_actions.py`). Every line names the board as the journal's summaries do (`moodboard_edits.board_where`: "board" and the name, cut to 60 characters), so the log and the journal never name one board two ways.

A change to the board, an edit batch (1.12: `moodboard_edit`, `nebula moodboard edit`, `moodboard_add`, `nebula moodboard add`, `moodboard_update`'s image changes, an undo) or a `PUT`, is one event per batch or `PUT` that changed something (`main._say_agent_board_change`). Its `say` is the agent's own `say` when the batch sent one, else the journal's summary of the change (1.12, `moodboard_edits.journal_entry`), so the Agent log and the journal word one change the same way: "Set aside #1 on board Dusk", "Added #3, #4 to board Dusk", "Private note changed on #2 on board Dusk", "Made #3 the cover of board Dusk". Another change that clears the cover by taking its image off says so: "Removed #3 from board Dusk; the cover is #1 again". A batch of `restore` ops (an undo) is marked: "Undo: Removed #3 from board Dusk". The board's own fields, which the journal leaves out, are named by their labels: "Changed Direction and the Avoid list on board Dusk", "Set aside #1 on board Dusk; changed Direction", and the board's notes when the summary is about something else ("Added #3 to board Dusk; changed the board's notes"). Never the text written. A setting an older image was saved without reads as its default (weight 1, not set aside, no notes), so the store saving that default is not a change. The `PUT`'s line compares the board the store changed with the result (`MoodboardStore.update_with_before`), with no second read.

The browser lists the event in the Agent log under the agent's name and colour; with no target no cursor moves, and `nebula look` lists no cursor for it. The person's own writes, a refused write, a batch or `PUT` that changed nothing and the dry run (1.8) send nothing.

### 1.16 Moodboard adapters

How each node takes a wired board lives in one table, not in the node definitions (plan section 5.7, A5): `backend/data/moodboard_adapters.json` (hand-written, entries sorted by node id, plus the `census`) and `backend/data/moodboard_adapters_krea.json` (written by `scripts/sync-krea-catalog.py` from the Krea catalog's port names and request schemas, `generatedBy`, never edited by hand; empty until Krea catalog nodes get a Moodboard port). `backend/services/moodboard_adapters.py` reads both, refuses an id in both, and rereads them when either file changes. `GET /api/moodboard/adapters` serves `{entries}` unresolved; the frontend store (`store/moodboardAdapterStore.ts`) loads it once per session.

**An entry** names its `channel` (`weighted-style`, `style-object`, `refs`, `role-slots`, `views`, `texture-style`, `music` or `text-only`), and for a channel that takes images its `default` (`images`, `text` or `never`), `slots` (`{port, max, roles?, sharesLimitWith?}`; `sharesLimitWith` names wired ports the handler sends in the same request field, so they count against `max`), `never` (frames, edit targets, masks, identity, non-image `Any` ports), `needsWired` (must be wired first; may name a slot port, as GPT Image edits' `images`), `weight` (`native` with Krea's `range` and `schema` `{source: "krea-catalog", endpoints, field}`, normalized `sum-to-strength`; `at-creation` `sum-to-one`; `select` `rank`; `global` with the person's `param`), `order: "weight"`, `syntax` (`"Image {n}"`, `"plain"` or `null` with a `syntaxReason`) and `costPerRef` (`priced`, `free`, `plus`, `unknown`; required with `default: "images"`). Every entry has `textSlot` (`{port}` or `{param}`), `text` (`brief` or `music-direction`), dated `sources` (`{url, quote, checked}` or `{code: "path:line", quote}`), `checked` and, for what no source says, `unconfirmed`. `text-only` and `default: "never"` need a `reason`. `byModel` (`"param=value"`: enum values of the node) and `byRoute` (route ids from `node_route.routes_of`) replace the fields they name, model first; a result that is `text-only` drops the image fields and its former slots join `never`.

**The dispatcher (steps 1, 2 and 8 of plan section 5.7.3).** `apply_to_generator` drops a strength-0 board (1.4), resolves the node's entry for its effective params and the route its run takes (`run_route`: the same choice as the dual-route handler and the cache key, a Krea-only setting that arrives by wire included; none for a single-route node), sends the text fold to the entry's `textSlot` port, and drops the `moodboard` input unless the entry's `handler` is `reads-board` (Krea 2 only). Everything a generator receives is what it received before the table (`tests/fixtures/moodboard_dispatch_before_adapters.json` pins 688 cases). A node with a Moodboard port and no entry (a broken install) still gets the text fold, with the run note "This node has no moodboard adapter entry, so the board went as text only." The other steps (board images on content slots, the switch, text into params, music direction, negatives from the route, palette, `exclusive`, `needsWired`, face policy) are PR14's; their fields are validated now and read by nothing yet.

**On the card.** A node whose Moodboard port carries a Nebula board (the wire's origin, through reroutes, is an output declared `Moodboard`; not Krea's own Moodboard nodes or an old Text wire into Krea 2) shows one line under its ports (`components/nodes/MoodboardAdapterRow.tsx`, deferred): "This model takes the brief as text." for a text-only entry, "Board images: on · up to 10 to Image Style Refs" (the first slot's max and port label) for `default: "images"`, else "Board images: off · the brief goes as text". The line resolves `byModel` for the node's params and `byRoute` for the route its next run takes with the person's keys. No switch yet (PR14).

**For agents.** `describe_node` (`moodboardAdapter`) and `nebula info` (`MOODBOARD:`) read the same entry through `moodboard_adapters.describe`: resolved at the node's defaults on the route a run takes here, the card's `line` (`card_line`, the backend copy of `adapterLine`), and the `byModel`/`byRoute` `variants` that change it (a `byModel` value is resolved on the route a run with it takes, named as the variant's `route` when it differs).

**The contract (plan section 5.7.10)**, checked by `table_problems` in the backend suite and by `scripts/check-node-contracts.mjs` (`scripts/moodboard-adapter-contract.mjs`, the same messages in the same order; a test runs both on the same broken tables):

1. Every node with an input port `id: "moodboard"` has an entry, and the port is `dataType: "Moodboard"` (the JSON registry here; the TS one in `frontend/tests/moodboardAdapters.test.ts`).
2. Every entry's node exists and has that port.
3. Named ports exist; no port is in both `slots` and `never`, or `never` and `needsWired`.
4. Every `Image` or `Any` input is in `slots`, `never` or `needsWired`.
5. A port whose id or label says first, last, start, end, tail, frame(s) or keyframe(s) is `never`.
6. A slot's `max` is within the port's `maxConnections` and every route's `rules.ports` max; `byModel` and `byRoute` keys are real. Each resolved variant is checked on its own.
7. `text-only` and `never` need a reason; `syntax: null` needs a `syntaxReason`.
8. A collage goes into one single-image slot that isn't an edit target.
9. Sources are dated (`checked` not in the future), URLs are https and code paths exist.
10. The generated file is what `sync-krea-catalog.py` writes (`--check` fails otherwise), and no generated entry defaults to images on a style field unless its model is in the script's `STYLE_VERIFIED` (Krea 2 medium, large and medium-turbo; Ideogram 3), each with its source. Every `Image` or `Any` input of a Krea generation model is classified in the script (`SLOT_FIELDS` or `NEVER_FIELDS`), or `--check` fails.
11. A maker route that refuses a start image with references needs `exclusive`: the test runs each maker route with HTTP mocked and finds BytePlus Seedance 2, MiniMax Hailuo 3 and Google Gemini Omni Flash 1.1 refusing; none has a Moodboard port yet.
12. Every image, video and audio generator with a `prompt` port or param has a Moodboard port or is listed in `census.excluded` (with a reason) or `census.pending` (with the PR that gives it one).
13. `native` needs `sum-to-strength` (`none` in test fixtures only), `at-creation` `sum-to-one`, `select` `rank`; a native `range` equals the Krea catalog's item schema; a Krea field whose items require `strength` must be `native`.

**Krea 2's port type.** It changed from `Any` to `Moodboard` so the contract sees it. It still takes a Nebula moodboard and Krea's Moodboard node's `moodboard` output (`Any`). A saved project, imported graph or restored graph that wired something else valid under `Any` (text, such as Krea's Moodboard node's `moodboard_id`) keeps the edge (`port_contracts.RETYPED_PORTS`); a new wire like it is refused, and a run refuses it with "... put a Krea moodboard id in the node's Moodboard ID setting instead." No saved graph in the repo's fixtures wires one.

### 1.17 Updates (what an agent or the reader noticed)

(Sections 1.14 and 1.15 are reserved for the moodboard canvas and looks.) On screen they are "Updates"; one item is "an update". In code they keep the name `agentNotes` (`services/agent_notes.py`, `lib/agentNotes.ts`, `store/agentNotesStore.ts`, `components/agent-notes/`), because "notes" on its own means image notes. An agent's own action stays at its cursor (`say`, 6 s, never saved); what it noticed, a report or a suggestion goes in an update, which is saved.

**The record.** `{id: "an_<12hex>", author: {kind: "agent" | "reader", id, name, color, verified?}, source: "agent" | "nebula", requestedBy?, about, at, text, parts, refs, actions, readAt, dismissedAt, actedAt, actedBy, actedWith}`. `about` is one of `sinceLastTurn`, `analyze`, `suggestion`, `removedLook`, `changedWords`, `proposal`, `other`, and the header label comes from it, never from the agent. `text` is one plain line of at most 240 characters. `refs` (at most 12) are node ids on the main canvas, checked against the open project's graph, and image ids on a board; unknown ones are dropped and listed in the answer's `dropped`. On a board a `#n` in the text is saved as that image's id and drawn with its current number (`parts`), "(removed)" once the image is gone; a `#n` not on the board refuses the update (422). `actions` (at most 2) are edit actions from a closed set (`suggestion.accept`, `suggestion.dismiss`, `run.undo`, `history.restore`, `proposal.accept`, `proposal.reject`), stored only on updates Nebula writes (`source: "nebula"`); an agent's update carries none. "Show" is never stored: the list draws it from `refs`. `actedWith` is the label of the action that ran, so the list can say "Frame made", "Undone", "Accepted" and so on.

**Where they are kept.** Main canvas: on the project record, `catalog["projects"][id]["agentNotes"]`, outside `snapshot`, written in one `store.transaction()` like pins; autosave never drops them, trash moves them with the project, and with no project open a post is refused like a pin. Board: `MOODBOARD_ROOT/.notes/<boardId>.json` (`{boardId, notes}`), a side file. Posting, reading or dismissing never writes the board file, never bumps its `version` and never makes the Studio rebase. It is keyed by id, so it survives a move and a trash restore, and it is purged with the board. The start-up scans walk only board folders and `.trash` (`moodboard_store.board_scopes`), so they never touch `.notes`.

**Limits.** 100 updates per board, 200 per project: over the cap the oldest read update goes first, then the oldest unread. 6 agent posts a minute per author per surface (429 `notes_rate_limited`); Nebula's own template updates skip the rate limit, not the caps. A newer `sinceLastTurn` update from the same author on the same surface replaces its unread one.

**Private notes are never quoted.** An agent update whose text, normalized (NFKC, case-folded, punctuation dropped, whitespace collapsed), holds a whole private note of 12 to 32 normalized characters, or any 32-character run of a longer one, is refused (422 `note_quotes_private_note`). A board update checks that board; a main-canvas update checks every board the project can see, its own and the Global ones. The main canvas keeps those notes normalized in a cache keyed by each board file's mtime and size (`PrivateNoteIndex`), so a post reads and normalizes only the boards that changed since. Measured with 40 boards of 300 images each (12,000 notes): 53 ms to fill the cache once, then about 9 ms per post. A private note under 12 characters can't be checked without false hits, so it isn't.

**API.**

| Route | Who | Does |
|---|---|---|
| `GET /api/canvas/agent-notes[?unread=1]` | anyone | `{projectId, notes, unread, keptWith: "project"}`, newest first |
| `POST /api/canvas/agent-notes` | an identified agent | `{text, refs?, about?}` → 201 `{note, dropped, removed, unread}` |
| `POST /api/canvas/agent-notes/read` | the person | `{upTo}` marks that update and every older one read; `{ids}` marks just those (a clicked card); both together is 422 `read_invalid` |
| `POST /api/canvas/agent-notes/{id}/dismiss` | the person | sets `dismissedAt`; the update stays in the list |
| the same four under `/api/moodboards/{id}/agent-notes` | as above | the board's list, `keptWith: "board"` |

`removed` lists the ids a post pushed out (the replaced `sinceLastTurn` update, or the cap). An agent never marks read or dismisses, so it can't hide an update from the person.

**Socket.** `{type: "agentNotes", surface: "canvas" | "board", projectId | boardId, op, unread, at}` with `op` one of `added` (`note`, `removed`), `read` (`ids`), `dismissed` (`ids`), `acted` (`note`) and `sync` (`notes`: sent to a socket right after `graphSync` and `canvasPins` when it connects, and to every socket when a project is opened or created, not on an import into the same project). Every tab follows read state through it. Each post is journaled as `note.posted` (`{surface, boardId?, noteId, about, refs}`, text cut to 160 characters), so `wait_for_canvas_change` sees other agents' updates; reading and dismissing are not journaled.

**From the CLI and MCP.** `post_note(text, board?, refs?, about?)` and `list_notes(board?, unread?)`; `nebula note "<text>" [--node nX]... [--board <board> --ref <#n or image id>...] [--since-last-turn]` and `nebula notes [--board] [--unread]`. The MCP instructions carry one line: "Your cursor's `say` is for your own action. What you noticed, a report or a suggestion goes in post_note; the person reads them in the Updates list in the top right, not at your cursor."

**The main canvas's corner.** A chip in its own fixed mount in the top right (`top: 24px`, level with the header pill): both authors' dots, "Updates" and the unread count, muted at 0, popping on a new one, with a ring in the newest author's colour while a card is up. A new update drops a card from the chip for about 4 s (hover or focus holds it; leaving by itself leaves it unread; a click on it marks only that one read with `{ids}`; × dismisses). Cards come one at a time. Four or more at once become one "4 new updates" card that opens the list: posts within 450 ms of each other count as at once (the first card waits at most 1.2 s), and a card already up folds into the summary when the ones waiting behind it bring the total to four, unless the pointer or focus is on it. A hidden tab drops no card. The chip opens the list (GM's still: header "N · all read" and "kept with this project", entries newest first with a 4 px stripe in the author's colour, the author's dot and name, the label, the clock time, the text and at most two buttons, edit actions first, then "Show on canvas"; a dismissed or acted entry is greyed with its state). Opening it marks every update read with `{upTo}`; one arriving while it is open joins the top, is marked read at once, and the header counts it as "k new". The footer says "Not now hides a suggestion for good" while an entry offers it, and ends with "See all actions →" while the Agent log is switched on, which expands the log (`uiStore.openAgentLog()`). Esc or a click outside closes the list. Show (a button, or a click on a row) moves the view as little as needed to bring the refs in, on a spring, and outlines them in the author's colour for 2.4 s; it selects nothing, so it writes nothing to the journal. A hovered row outlines its refs at once; a card's outlines come in 0.8 s after it, 0.25 s apart. The docked chat starts below the chip's row (`body.agent-notes-reserved`, `--chat-dock-top`), the card and the list sit left of the chat panel whenever its measured rect would meet them, and they stop above the proposal bar, the Agent log, the chat launcher, the toolbar, the project-switch toast and the minimap. Motion uses `lib/springs.ts` (response 0.42 s, damping 0.85 in; 0.3 s, damping 1 out); with reduced motion everything is an opacity change and outlines come without a stagger. The corner and the outline layer are deferred chunks (`lib/deferredChunks.ts`).

### 1.18 Every board in an agent's first answer

`GET /api/agent/start` (MCP `start_here`, `nebula context`; plan v2.7 PR26, MCP-SETUP.md) lists the person's boards in its `boards` part, so an agent needn't list each project's boards first; when there are any, `read` gives the call that reads one in full (`moodboard_get(board="<id or exact name>")`, or `nebula moodboard show <id>` with `via=cli`) and `use` gives the exact call that puts one on the canvas (a `nebula-moodboard` node, the board in its `moodboard` param, its `moodboard` port wired to a Preview's `input`; `nebula apply` flags with `via=cli`). It comes from `MoodboardStore.summaries()` (`backend/services/moodboard_store.py`), a walk of the store's folders: `_global` and each canvas project's folder; dot folders (`.trash`, `.notes`) and folders whose name isn't a safe project id are skipped. It reads each board's JSON for its name, image count, whether it has an analysis, Direction and `updatedAt`, never the images or any note.

```json
{"count": 41, "rows": [
  {"id": "mb_1", "name": "Good Machines", "where": "current", "images": 12, "analyzed": true, "direction": "quiet, warm, early light"}
], "truncated": true, "more": "moodboard_list(project_id=\"<project-id>\") lists a project's boards and Global's",
 "read": "moodboard_get(board=\"<id or exact name>\") gives one in full", "use": "To show one: edit_canvas(...)"}
```

- **`where`.** `current` for the open project (1.9), `global`, or the project's name from the catalog.
- **Left out.** Boards in Recently deleted, boards filed under a project that is in Recently deleted, and boards in a folder that isn't a project in the catalog (an old-style folder the re-home hasn't moved yet, 1.9).
- **Order and limits.** The current project's, then Global's, then the rest, each newest edit first; 30 rows at most, Direction cut to 80 characters, the whole part kept within 800 tokens (characters / 4). `count` is every board listed before the cut. `truncated` and `more` appear when rows were cut (a Direction cut short is in full in `read`'s answer). The `via=cli` answer says "`nebula moodboard list --project <project-id>` lists a project's boards and Global's" and "`nebula moodboard show <id>` gives one in full" instead.

## 2. Character

The rest of the Character (its fields, the node) isn't written up yet; 1.9 and 1.10 cover where it lives and moving it.

### 2.1 Character edits and the live Character Studio

`PUT /api/characters/{id}` takes `baseVersion`, the Character's `version` the caller read: any other is a 409 `{detail, code: "version_conflict", version, character}`, with the Character as it is now, and nothing is written; a `baseVersion` that isn't a whole number is a 422. Left out, the write applies to whatever is saved, as before (agents, the CLI, an older tab). A field left out of the body keeps its saved value. Writes to one Character are serialized (`services/character_store.py`, one lock per id), so a version check and its write can't interleave with another write. Every `PUT` broadcasts `storedAssetChanged` with the new `version` and `edit: {actor, tab?}` (as a board's, 1.12: `tab` only for the person's own tab); a move (1.10) still says `projectId` and no version.

Character Studio (`components/character-studio/CharacterStudioView.tsx`, `lib/characterEdits.ts`) keeps beside its draft the Character's fields as last read (`base`) and that `version`. A save sends only the fields the person changed since that read (the name trimmed), with `baseVersion`; on a 409 it takes the Character as it is, keeps the person's changed fields on it and sends again, at most 3 tries. On a `storedAssetChanged` for the open Character with a newer version that isn't this tab's echo, on `socketReconnected`, and once when a kept draft opens, it reads the Character again: every field the person hasn't changed since the last read takes the saved value, and the person's unsaved edits stay. When a save's answer lands, a field it sent counts as the person's again only if the draft moved off what was sent (an edit made while the save was out, even one back to the value last read, or a **Use theirs** clicked meanwhile, stays); the Moodboard Studio's board fields follow the same rule (1.12). A field both changed, to different values, keeps the person's value and the Studio says so above the fields: "Claude also changed the frozen trait string while you were editing it. Yours is kept." (the agent's name, "Another tab" for the person's other tab, "Someone else" when the change came while the socket was closed), with **Use theirs** (puts their value back, as an edit of the person's that saves like any other) and **Dismiss**. Fields: name, subject type, reference views (one field: their order is the identity, so they never merge), frozen trait string, seed and consistency strength. There is no MCP tool that edits a Character's fields; agents use the HTTP route.

### 2.2 Images on a Character or a Style

A Character's `referenceViews` (its `thumbnail` is the first one) and a Style's `refImages` and `thumbnail` are loaded by the app as images, so every write to them (`POST`/`PUT /api/characters`, `POST`/`PUT /api/presets`), the person's included, takes only Nebula's own files: an output or an upload as `/api/outputs/<path>` (what `POST /api/uploads` returns as `url`), a loopback URL to that route, the file's absolute path inside the output folder (`filePath` from `/api/uploads`, which Create's "Save current" sends), or a shipped Style thumbnail `/api/presets/thumbnails/<slug>`. The file must exist and pass the protected-file policy. Anything else, an `http(s)` link to another host, a protocol-relative link, a `data:` URI, a path outside the output folder or a missing file, is a 422 naming the field and index (`referenceViews[2] is an image link from outside Nebula (...)`) and what is allowed, and nothing is written. A Style's own image params (`_previewUrl` and its node's `file` params) refuse only outside links; a local path there is checked when it runs. A value the Character or Style already holds isn't checked again, so one saved before this check still loads and saves (`services/stored_image_refs.py`, `main.py` `_check_stored_images`).

The app draws a Character's or Style's image only when it is one of those files (`lib/storedImage.ts`): the Assets panel, Create's Style cards and reference tray, the Character node, Character Studio's rail, cover and views, and Recently deleted. An outside link gets the placeholder and the line "Image link from outside Nebula"; it is never fetched. Applying a Style in Create leaves an outside link out of the references and says so ("1 image link from outside Nebula in this Style was left out."), and "Save current" refuses a reference that is one. A run of a Character node does the same with the bundle it sends (`handlers/character_node.py`): an outside view stays on the Character but goes in neither the run nor the Inspector's Last output, and the run notes "1 reference view of Character 'Old hero' is an image link from outside Nebula, so it was left out. ..."; when every view is one, the run stops and says to replace them in Character Studio. Outside links are read the way a browser reads them (tabs and newlines dropped, a backslash as a slash, `https:` with any number of slashes), so `http://host\@127.0.0.1/api/outputs/...` is refused as a link to `host`.

## 3. Styles (presets)

A Style is what the person saves from Create ("Save current") and finds in Create's Styles and the Assets panel's Styles tab: `{id, name, category, prompt, params, modelId, refImages, thumbnail, version, paramsVersion, scope, projectId, createdAt, updatedAt}` in `<preset root>/_global/<id>.json` or `<preset root>/<projectId>/<id>.json` (`backend/services/preset_store.py`). Applying one copies its prompt fragment and settings into Create; no saved graph points at a Style id, so deleting one breaks no node.

- **Routes.** `GET /api/presets?scope=global|project&projectId=`, `POST /api/presets`, `GET`/`PUT`/`DELETE /api/presets/{id}`. A `POST` without `paramsVersion` is read as version 0 (a bundle from before the marker); Create, `nebula style new` and the MCP's `style_create` send it. `PUT` takes `baseVersion` (the `version` read): another version is 409 `code: "version_conflict"` with the Style as it is now (`style`) and `version`; `modelId: ""` clears the model. A Style in Recently deleted answers `GET` and `PUT` with 404 `code: "in_trash"` and its trash record.
- **Who may write what.** Anyone may make, change and delete a Style, agents included. Applying a Style puts its settings on Create's draft, billing included, so nobody but the person may save one whose billing choice (`_provider` on a route-table model, `_kreaAuth` on a Krea model with both modes) differs from the model's default on a new Style, or from what the Style had on an update (403, the node routes' sentences with the propose_change advice swapped for "leave it out, or ask the person to pick it in Create", since a Style change can't be proposed; `main._refuse_agent_billing_change`). An agent may not write an internal `_` param it didn't read back unchanged (422); a `params` from an agent that leaves the Style's internal params out keeps them (`main._style_params_keeping_internal`), so `previous` undoes the update exactly. An agent's `modelId` must be a node in the catalog (400). Its `refImages`, `thumbnail` and image params take only Nebula's own files, for every caller (2.2).
- **Recently deleted (Justin's Q53 a, 2026-10-20).** `DELETE` moves the file untouched to `<preset root>/.trash/` with a record of kind `style` (`services/asset_trash.py`), returning `{status: "trashed", id, trashed}`; reads skip `.trash`. `GET /api/trash?kind=style`, `POST /api/trash/style/{id}/restore` (anyone; the same id and contents) and deleting for good (`DELETE /api/trash/style/{id}`, `POST /api/trash/empty`, person only) work as for boards and characters. No timer. The start-up re-home moves a trashed Style's record to Global (1.9). Starter Styles are seeded once (`<preset root>/.seeded`; an install from before the marker with any Global Style, live or in Recently deleted, counts as seeded), so deleting them, even for good, keeps them gone.
- **Telling the others.** Every write journals one event in the caller's name: `style.created`, `style.updated` (with `fields`), `style.deleted`, `style.restored`, `style.purged`, data `{styleId, styleName, scope}`, never a prompt or a value (`services/style_actions.py`). It broadcasts `storedAssetChanged` with `kind: "style"`, so the Assets panel, its Recently deleted and Create's Styles list again. An agent's write is also an Agent log line in the journal's words ("Changed the prompt of Style Dusk").
- **The app.** The Assets panel's Styles tab has Delete on the selected Style, the Undo toast ("Moved “Dusk” to Recently deleted · Undo") and Recently deleted under the list, as the Studios have (`components/asset-trash/AssetTrash.tsx`, `hooks/useAssetDelete.ts`).
- **CLI and MCP.** `nebula style list|show|new|set|delete`, `nebula trash list --kind style`, `nebula trash restore style <id>`; `style_list`, `style_get`, `style_create`, `style_update` (returns `previous`, which undoes it as one checked write), `style_delete`, and `list_trash` / `restore_from_trash` with kind `style` (`backend/style_client.py`).
