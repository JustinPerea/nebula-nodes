# Studios and resources (Volume 7)

Saved assets that studios edit and bridge nodes read. This volume starts with the Moodboard; Character, Cinema and the video editors are not written up yet.

**Oracle:** `backend/services/moodboard_store.py`, `backend/services/moodboard_edits.py`, `backend/services/moodboard_layout.py`, `backend/services/moodboard_brief.py`, `backend/services/moodboard_analysis.py`, `backend/handlers/moodboard.py`, `/api/moodboards/*` in `backend/main.py`

---

## 1. Moodboard

A board is one JSON file under the moodboard root (`NEBULA_MOODBOARD_ROOT`, default `~/.nebula/moodboards/<scope>/<id>.json`; scope is `_global` or a canvas project's id, see 1.8).

### 1.1 Saved fields

| Field | Type | Who writes it | Notes |
|-------|------|---------------|-------|
| `id`, `createdAt`, `projectId` | string | store | Fixed after create |
| `name`, `notes`, `mode`, `strength`, `images` | — | person or agent | `mode` is `look`, `world` or `subject`; each image has `id`, `url`, `weight`, `notes`, `privateNote`, `excluded` and `placements` |
| `images[].excluded` | boolean | person or agent | The **Set aside** switch. A set-aside image stays on the board with its weight, notes and cards and is still read (measured) for its colours, but never steers: it adds nothing to the palette, accents, `sources`, keywords, summary, brief, negatives or representative images, and no generator or node output gets it (1.4). The key and its place in `source_hash` are as before, so no board is rewritten and no analysis or hand-written brief goes out of date. Wherever a board is shown (Moodboard Studio, `nebula moodboard show`, `moodboard_get`), weight 0 shows as set aside too: an image steers only when it isn't set aside and its weight is above 0 (`moodboard_analysis.steers`). Turning it on keeps the weight; turning it off on a weight-0 image also sets the weight its card shows (its largest card's, or 1 with no card) |
| `images[].privateNote` | string | person or agent | The person's own label for the image ("PAINTERLY (liked)"), up to 2000 characters. Shown wherever the board is inspected (Moodboard Studio, `nebula moodboard show`, `moodboard_get`), never sent anywhere: it isn't in `source_hash`, the analysis, `brief`, the negative prompt or the Moodboard node's outputs (`moodboard_store.output_image`). Changing it keeps the analysis. A board saved before it existed reads with `""`. `images[].notes` is the note that steers |
| `images[].placements` | object[] | board edits; the store, for a new image | The image's cards on the board canvas, 1 to 8, at most one per frame: `{id, frameId, x, y, w, h, weight, placedBy, placedAt}`. Coordinates are absolute board pixels (at most 1,000,000 from the origin). `frameId` is the frame (look) the card is in, or null; a card in no frame must be the image's only one. `w × h = weight × 129,600` (full weight is a 480×270 card), rounded to whole pixels at the image's aspect ratio (its file, upright; else the analysis's measurement; else 4:3); card weights run from 0.05 to 1. The server writes `w`, `h`, `placedBy` (`person`, `agent` or `analyze`, from who asked) and `placedAt`. The layout steers nothing: it isn't in `source_hash`, `brief_basis`, `brief` or the node's outputs, so moving or resizing a card keeps the analysis (`moodboard_layout.py`) |
| `layoutVersion` | integer | store | `1` once the board's layout is saved. Absent on an old board, which reads with a layout (1.5) |
| `frames` | object[] | board edits | The board's frames (looks): `{id (12 hex), name, kind: "look" or "unsorted", x, y, w, h, createdBy, namedBy, createdAt}`. At most 100, one Unsorted, names 1 to 60 characters and unique ignoring case, sides at least 160 px. Reads as `[]` when absent |
| `suggestions`, `readings`, `lastRead` | — | Analyze | Reserved for Analyze (item 6): `suggestions` (at most 200) and `readings` (one per image, at most 2 KB each) read as `[]` and `{}` when absent. Nothing writes them yet |
| `analysis` | object or null | Analyze | Colour reading of the images. Set to null when the images, weights, mode, strength or notes change (not an image's `privateNote`). Its own `styleBrief` and `negativePrompt` are the analyzer's; generators get `brief` (1.2), so change the brief through `briefOverride`, not here |
| `direction` | string | person or agent | What the board is for, in positive words. Up to 4000 characters |
| `avoid` | string[] | person or agent | Things to keep out of the image. Trimmed, de-duplicated (case-insensitive), at most 40 items of 200 characters |
| `pinnedColors` | `{include: hex[], exclude: hex[]}` | person or agent | Colours that must appear or must stay out. Hex is stored as `#rrggbb`; at most 12 per list; a colour can't be in both |
| `briefOverride` | `{text, basis, updatedAt, by}` or null | person or agent (text); store (`basis`, `updatedAt`, `by`) | A hand-written brief that replaces the generated one. `by` is `person` or `agent`, from the person gate (`services/person_gate.py`); none (an override the migration moved) counts as `person`. Only the person may replace, remove or Keep text the person wrote (1.3) |
| `briefVersion` | integer | store | `1` once the board has the fields above (see 1.5) |
| `version`, `updatedAt`, `thumbnail` | — | store | |

**Layout is written only by board edits and by the server placing new images.** `layoutVersion`, `frames`, `suggestions`, `readings` and `lastRead` are refused (422) on create and on `PUT`. An image's `placements` are taken only for an image new to the board; on an image already there, the saved cards stay whatever the client sends (1.3). A saved layout that is out of bounds is logged, and the board still opens as saved. A file edited into an odd shape (`placements` or `frames` that aren't lists, numbers too big for a float) still lists, opens and saves: what can't be read as a card counts as none, and an image with no card that can be drawn is placed again.

`direction`, `avoid`, `pinnedColors` and `briefOverride` live on the board, not inside `analysis`, so analyzing again never drops them. Changing them does not clear the analysis.

### 1.2 The brief (`brief`, computed)

Every moodboard API response adds `brief`, computed on each read and never saved (`moodboard_brief.compose`):

| Key | Meaning |
|-----|---------|
| `styleBrief` | The override text when there is one, else `generatedStyleBrief` |
| `generatedStyleBrief` | Direction first, then mode intent, palette (minus kept-out and left-out colours, 1.11), accents, "Make sure these colors appear", visual cues, any reader fields (`motifs`, `materials`, `textures`), notes (only when sent, 1.11). Empty until the board is analyzed |
| `negativePrompt` | `blurry, low-detail artifacts` plus the Avoid list. Defects only: content intent goes in the brief as positive words |
| `avoid`, `direction`, `pinnedColors` | The saved fields |
| `avoidPrompt` | `Keep these out of the image: <avoid>, colors close to <kept-out hex>.` or empty |
| `palette`, `accents` | The analysis colours, minus any within dE00 5 of a kept-out colour, minus those left out (1.11) |
| `override` | `{active, stale}`: `stale` is true when the board changed after the override was written |
| `needsAnalysis` | No saved analysis yet |

### 1.3 API

| Call | Body | Effect |
|------|------|--------|
| `POST /api/moodboards` | `name`, `images`, … plus optional `direction`, `avoid`, `pinnedColors`, `briefOverride: {text}` | Create. Each image is placed where its `placements` ask, else after the one before; the board is saved with `layoutVersion: 1` |
| `GET /api/moodboards/{id}` | — | The board, laid out (an old board reads with its grid, 1.5). Reading writes nothing. `GET /api/moodboards` (the list) doesn't lay boards out |
| `PUT /api/moodboards/{id}` | Any subset, including the four brief fields, plus optional `baseVersion` | Update. `briefOverride: {text}` sets the override; `briefOverride: null` removes it (the brief goes back to generated). Send only `text`: `basis` and `updatedAt` are refused (422). `images` merges by id (below). With `baseVersion`, a board saved since is a 409 (1.12). A layout field is refused with a 422 that names `POST /api/moodboards/{id}/edits` |
| `POST /api/moodboards/{id}/edits` | `{ops, baseVersion?, say?}` | Checked board edits, applied whole or not at all (1.12). Answers `{board, version, applied, undo}` |
| `POST /api/moodboards/{id}/brief-override/keep` | — | Keep the override for the board as it is now (clears `stale`). 404 for an unknown board; 409 when there is no override (the message says to set one with `PUT`); 403 when an agent asks to keep the person's text |
| `POST /api/moodboards/{id}/analyze` | — | Analyze again. Keeps the brief fields and the override. Saved against the version it read: an edit while it ran that changes what it reads makes it analyse the new board, one that doesn't keeps the analysis; 409 `version_conflict` (with the board) after 3 saves lost to edits |
| `POST /api/moodboards/{id}/analyze/dry-run` | optional `{thresholds: {accentMinChroma, accentSeparation, mergeDeltaE}}` | What Analyze would give, saving nothing (1.8). 422 for a threshold out of range or an unknown key |

The board keeps no history, so replacing or removing the person's hand-written brief can't be undone. A `PUT` that would replace or remove an override with `by: "person"` (or no `by`), or a Keep of one, is refused unless it comes from the person: 403 with the person gate's `code` (`agent_refused` for an agent marker, `person_required` without this launch's person token), and nothing in that request is saved. An agent may still change every other field, which marks the override stale for the person to answer, and may change an override an agent wrote.

**Images on `PUT` merge by id.** Each image in `images` is matched with the saved image of the same id:

- A key the client leaves out keeps its saved value. Before item 6, a left-out key was reset to its default, so a client that didn't send `privateNote` erased it; now it keeps it.
- On an image already on the board, `placements` are ignored: the saved cards stay, so a stale tab or a CLI that sends back what it read can't undo a layout edit. Everything `GET` returns may be sent back.
- A `weight` that changes scales the image's cards by the same factor, so the largest equals the new weight (smaller ones stop at 0.05); weight 0 keeps them as they are. Each card keeps its top-left corner and nothing else moves, so a card that grows may cover its neighbour, as a resize in the Board view can.
- An image new to the board (no id, or one the board doesn't have) takes the `placements` it sends, checked (frames must exist, at most 8, one per frame, ids unique), with `w`/`h` written from each card's `weight` (or from `w × h` when no weight is sent). With no weight sent, the image's weight is its largest card's. Without `placements`, Nebula places it after the last-added card: in that card's row when there is room (24 px from every card and frame, within six full-weight cards' width, and fewer than six cards in the row up to that card), else at the start of a new row under the board. The six-card rule keeps an old board's 6-column grid 6 wide when its cards are portrait or square. Never on top of anything.
- An image left out of `images` is removed, as before.

**Every write bumps `version`**, the board's compare-and-set token, and a write of a saved board (create, `PUT`, edits, Keep, Analyze) tells open canvases with `storedAssetChanged` (1.12). Opening or reading a board writes nothing, and a `PUT` or edit batch that changes nothing writes nothing and keeps the version. Moodboard Studio sends board fields only on `PUT` (`name`, `notes`, `mode`, `strength`, the brief fields, the 1.11 fields, and `analysis` only as `null`), always with `baseVersion`, and every image change through `/edits`. `PUT` keeps taking `images` for the CLI, MCP and API callers, and its image changes are journaled the same way (1.12).

Sending the same override text again keeps its original `basis`, so a client that saves the whole board on every change doesn't hide the "changed since you edited this" state. New text is stamped with the board as it is after the update.

### 1.3a The analysis's colours (version 5)

`analysis.palette` and `analysis.accents` are hex lists in rank order. `analysis.colors` holds the same colours with detail:

| Key | Meaning |
|-----|---------|
| `hex`, `role` | The colour, `dominant` (palette) or `accent` |
| `share` | The part of the weighted board it covers: the sum over images of (image weight ÷ total weight) × its share of the image |
| `images` | How many images it comes from |
| `sources` | Each image it comes from, largest contribution first (then board number): `number` (the image's place among all the board's images, 1-based, set-aside ones included, as Moodboard Studio and `nebula moodboard show` number them), `id`, `share` (the colour's share of that image; two colours of one image that merge add up) and `contribution` (that image's part of `share`) |

`analysis.images[]` lists each image with a URL, set-aside ones included, with its `number`, `weight`, `status` (`analyzed`, `unresolved` or `error`), `colors` (`hex`, `share`, `accent`), `palette` and `accents`. A set-aside image's entry has `setAside: true` (version 5 on; the key is absent otherwise) and its colours as measured, the same as if it steered. Set-aside and weight-0 images never appear in `sources` and add nothing to any share. A set-aside image that can't be read says so in its own entry's `status`; `warnings` stay those of the images that count. When no image steers (every one set aside or at weight 0), `warnings` holds "Every reference is set aside, so none of them shapes the board."

`summary` counts the images that aren't set aside by the switch (weight 0 still counts, as it always has).

Version 5 changed nothing that steers, and the source hash is the same, so a version 4 or 3 analysis stays current until the board changes; it just doesn't list set-aside images. Analyses before version 4 have no `sources` or `number`; the Studio and CLI say to analyze again to see the sources.

### 1.4 How a board reaches a generator

The `nebula-moodboard` node emits a `Moodboard` bundle (`kind: "nebula_moodboard"`) carrying `styleBrief`, `negativePrompt`, `avoid`, `avoidPrompt`, `direction`, `pinnedColors`, `briefOverride` (`{active, stale}`), `palette`, `accents`, `images`, `representativeImages`, `analysis` and `providerHints`, plus what 1.11 adds (no notes unless sent, the left-out lists). Each bundle image has exactly `id`, `url`, `weight`, `notes` and `excluded` (never the private note or the layout), and its `notes` is empty unless the board's notes are sent (1.11); set-aside (excluded) images are left out, and so are their entries in `analysis.images`, so the bundle carries no set-aside image or its colours and Krea 2's style references never include one (`representativeImages` never did). A stale override is still used, and the run gets a note saying so. The node is not output-cached: its params name the board, not its contents.

Image generators take it on an optional `moodboard` input port. The engine folds it in before the handler runs (Volume 2, section 7a, "Moodboard fold").

Krea 2 (`krea-2-generate`) also takes the board's images as `image_style_references`, and their strengths share out the board's strength (Q21 b, 2026-10-20): the images that go (Krea's hints' `representativeImages`, else the bundle's, else the images ranked heaviest first; deduped, weight-0 and set-aside never, capped at 10 minus the wired references) get `strength x weight / sum(weight)` over those images, at 4 decimals by largest remainder (`services/moodboard_weights.py` `native_strengths`), so they add up to exactly `strength`. A URL missing from `images` counts as weight 1. Wired references, Krea `moodboards` and `styles` keep their own strengths. Strength 0 sends no board images, with the run note "Board strength is 0: no board images sent"; an image whose share rounds to 0 is left out with a note; every run that sends board images notes each one's strength ("Board 'Dusk' sent 5 images; their strengths add up to the board's 0.70 (#1 0.19, ...)", `#n` the board number) and, with wired references, what they add on top. Both Krea routes send the same body. Before this, each image went at `strength x weight`; run records keep what they sent, and a canvas replay of a record from before 2026-10-20 notes that it can differ (`runReplayNotes` in `frontend/src/lib/savedParamsUpgrades.ts`; no params version change).

### 1.5 Migration of older boards

Boards saved before the brief fields (no `briefVersion`) are migrated once at backend startup, and in memory on any read before that:

- Negatives in `analysis.negativePrompt` beyond the old defaults move to `avoid`.
- An `analysis.styleBrief` that differs from what that analysis generated becomes `briefOverride`. If the board changed since that analysis, the override starts out stale.
- Each changed file is copied first to `<moodboard root>/../moodboard-backups/brief-fields-<UTC time>/<scope>/`, with `migration-log.json` listing what moved. A file that can't be backed up is not rewritten.
- Moved text is kept within the limits in 1.1, so the board can still be saved. Anything cut is in the log (`avoidClipped`, `overrideClipped`) and whole in the backup.
- Nothing is lost: the saved `analysis` keeps its old `styleBrief` and `negativePrompt`, and the backup holds the file as it was. A backup copied back is migrated again on the next start, with the same result.
- Running the migration again changes nothing. A file that can't be read is logged and left alone. A board with a higher `briefVersion` (saved by a newer Nebula) is left as it is. A board file edited by hand into an odd shape still lists and opens (its `brief` is `null` if it can't be composed), and a failing migration never stops the backend from starting.

**Old boards read with a layout (item 6).** A board saved before layouts (no `layoutVersion`) is not migrated on disk: there is no startup step and no backup, and its file keeps its bytes, `version` and `updatedAt` until someone edits it.

- `GET /api/moodboards/{id}` (and the store's `get` and `update`) lays it out in memory as a grid in number order: 6 columns, 40 px between cells, each column as wide as its widest card and each row as tall as its tallest, every card centred in its cell. A card's area is its weight (at least 0.05; weight 0 shows at full size) at the image's aspect ratio. `placedBy` is `person`, since the order was theirs, and each card's id is derived from the board and image, so every read gives the same layout. `frames`, `suggestions` and `readings` read as empty.
- The list (`GET /api/moodboards`) doesn't lay boards out, so the rail stays cheap.
- The first write (any `PUT`, Analyze's save, a Keep, the CLI or MCP) saves that same layout and stamps `layoutVersion: 1`. Nothing moves. A write stamps `layoutVersion` only when every image has a card, so if laying the board out fails, the next read lays it out again.
- A board with `layoutVersion` where no image has a card reads with the same grid. An older Nebula leaves that when it edits a laid-out board (it drops image keys it doesn't know, `placements` among them, and keeps board keys). A board whose grid was saved comes back unchanged; cards placed or moved since are lost.
- An image whose url can't be read, or can't even be resolved (an unknown `~user`, a null byte), lays out at the analysis's size, else 4:3.
- Reading writes nothing. Moving a board, Recently deleted and its restore, the brief-fields migration and the re-home at start move or copy the file as it is, so they never write a layout either.
- The layout never enters `source_hash` or `brief_basis`, so every saved analysis and hand-written brief stays current. The brief and the node's outputs for old boards are pinned by `backend/tests/test_moodboard_golden.py`.
- Reading an image's aspect ratio runs the protected-path check (`services/file_access.py`), about 2 ms an image. The answer is kept per URL and agent workspace while one stat shows the same file unchanged, so later reads cost about 3 ms for 300 images. The `GET` route reads off the event loop.

### 1.6 From the CLI and MCP

`nebula moodboard show --json` and `moodboard_get` also return the layout: each image's `placements` and the board's `frames` (1.1). Lists and the results of edits leave it out to stay short. A board named by name is read again by id, so it comes with its layout. A change that only moves or resizes cards never counts as a content change: the client compares only `url`, `weight`, `notes` and `excluded` (`moodboard_client.STEERING_KEYS`) to decide whether to clear the analysis, and so does Moodboard Studio (`moodboard-studio/steering.ts`).

`nebula moodboard` and the `moodboard_*` MCP tools (`backend/moodboard_client.py`) return each board with `direction`, `avoid`, `pinnedColors`, `briefOverride` (`{text, by, updatedAt, stale}` or null; `by` is `agent` only when stamped so, else `person`) and `brief`, the backend's computed brief from 1.2 passed on as it came. On a backend that doesn't send `brief`, it is `null`: the client never rebuilds it, and never offers `analysis.styleBrief` in its place.

`nebula moodboard set` and `moodboard_update` change the brief fields: Direction (`""` clears), Avoid (replace, add, remove), pinned colours (replace both lists, add to either, remove from either), the override (set, or `""` for the generated brief), and Keep (`--keep-brief` / `keep_brief`, then `POST .../brief-override/keep`). Values are checked against the limits in 1.1 before anything is sent; nothing is cut short. Brief fields keep the analysis; changes to images, notes, mode or strength that change a value clear it. A 403 for the person's override (the person wrote it after the call read the board) comes back in the CLI and MCP's own words, naming the argument to leave out; any other 403 comes back as the backend's sentence, without the canvas-tab advice in the gate's `person_required` text.

The result's `previous` undoes the call when passed as the same call's arguments. It holds only what the call changed, as it was before: the settings, `direction`, `avoid`, `pinned_colors`, `brief_override` (the agent's own text, or `""` for none) and so on that its `PUT` changed, and, for each image it changed, only the image settings it changed (`{}` when the call changed nothing). It also holds `undo`, the checked way back (1.12): one `restore` made of the batch's own `undo` (image settings, the cards a weight rescaled, images it took off) and a `fields` slice for every field its `PUT` changed (what it changed along the way too, such as a colour pinned out leaving Keep anyway), each expecting what the call wrote. Passed back (`undo_board`, `update_board(undo=...)`, `moodboard_update(**previous)`, `set --restore`), it goes as one write; a setting someone changed again since is left as they set it and reported in plain words in `skipped` ("Direction changed since, left as is", "#2's weight changed since, left as is"; the CLI prints each line), and the rest goes back. Images the call took off come back with their cards and notes. The other keys of `previous` are what an older Nebula, without board edits, puts back instead, unchecked; such a Nebula's own `previous` has no `undo`. So undoing it leaves alone what anyone changed since, in what the call changed too. `brief_override` is there only when the change touched the override, so undoing anything else never touches a brief the person wrote since. A call that would replace, clear or Keep the person's override, or Keep with no override, is refused before anything is sent and changes nothing; the message says to leave that argument out. Keep loses nothing, so its refusal gives its own reason: keeping clears the person's notice that the board changed, which is theirs to answer. If the person writes or removes their brief while the call runs, a Keep refused after the other changes were saved says so and hands back `previous` for them (`MoodboardError.previous`; in the MCP error's text; on the CLI's stderr). `nebula moodboard set --restore <file>` sends a saved `previous` (or the whole `set --json` output) back as one change (its `undo` when it has one; `--json` then adds `skipped`); it refuses other flags with it and keys `previous` never has (`moodboard_update` with `undo` likewise refuses `remove`, the list changes and the Keep and clash arguments beside it). A `previous` without `undo` (saved before it existed) is put back as arguments, as before: images the change removed aren't in it, and the result's `removed` URLs add them back. A Keep that got no answer (connect or timeout) says the brief may or may not have been kept, not that it wasn't.

Each image in the client's view carries `setAside` (`excluded` or weight 0, 1.1) beside `excluded`. `nebula moodboard set --set-aside N` and `--use N` flip the switch (`--exclude` and `--include` are their old names and still work; naming one image in both, by number or id, is refused); `show` marks an image "set aside", or "set aside (weight 0)", and `list` counts them beside the image count ("(5 images, 1 set aside, look, ...)"); the Moodboard node card, the Studio's board list and the Assets panel read "5 images · 1 set aside · look" (`frontend/src/lib/moodboardCount.ts`). The count is every image on the board, so a Preview of a run, which counts only the images it sent, reads one fewer for each switched-aside image. In `moodboard_update` an image edit's `excluded` is the switch, and `setAside` is the same key (the two must agree); two edits of one change that set one image's switch both ways are refused, with nothing written. Using an image again (`--use`, `excluded: false`) on a weight-0 image sets the weight its card shows, unless the same change sets a weight; the result's `previous` gives the old weight and switch back.

Each image carries `privateNote` (1.1). `--private-note IMAGE=TEXT` and `{"image": ..., "privateNote": ...}` in `moodboard_update` set it, `show` prints it marked private, `--json` and `previous` include it, and a change to it alone keeps the analysis. On a backend whose images have no `privateNote`, setting one is refused before anything is sent, and `previous` has none.

### 1.7 Opening a board in Moodboard Studio

`#moodboard/<id>` opens Moodboard Studio on that board (`frontend/src/hooks/useMoodboardDeepLink.ts`). The scope it opens with is a hint; the board's own `projectId` decides where the Studio and its rail land. While the Studio shows a saved board the hash names it (replaced in place, no history entries), and leaving the Studio clears it. Loading the app with the link goes into the open project; with none it waits on Projects. Double-clicking a Moodboard (or Character) node, double-clicking an item in the Assets panel, the node's Open button and the Studio's rail all open a board without changing the graph; only "Add to canvas" or a drag from the Assets panel adds a node.

### 1.8 Dry run

`POST /api/moodboards/{id}/analyze/dry-run` (`moodboard_analysis.dry_run`) runs the same analysis as Analyze and saves nothing: no board write, no `updatedAt` or `version` change, no broadcast. Anyone may call it, agents included. It returns:

| Key | Meaning |
|-----|---------|
| `dryRun`, `id`, `name` | `true`, and the board |
| `thresholds`, `defaults` | The thresholds used and the defaults |
| `saved` | `{analyzed, current}`: whether the board has a saved analysis and whether it still describes the board. When it is out of date, `changes` include edits to the board, not only the thresholds |
| `analysis` | The analysis it would save (1.3a) |
| `brief` | `compose` (1.2) with that analysis: what generators would get |
| `changes.palette`, `changes.accents` | `{before, after, added, removed, nudged, reordered, changed}`. `nudged` pairs a removed and an added colour within dE00 2 (`{from, to}`); `reordered` compares the colours on both lists |
| `changes.brief`, `changes.generatedBrief`, `changes.negativePrompt` | `{before, after, changed}` against the saved board's `brief` |

`thresholds` are Commons' measurement constants (`commons/measure.py`), for this call only: `accentMinChroma` (CIELAB chroma 0–150, default 40), `accentSeparation` (dE00 0–100, default 10) and `mergeDeltaE` (dE00 0–50, default 5; it also sets the board roll-up's merge). One left out or null keeps its default. Nothing saves custom thresholds, and Analyze always uses the defaults. The pinned-colour rule ("within dE00 5 of a kept-out colour") is not a threshold here.

It is a route of its own, not a flag on `/analyze`: an older backend ignores a body it doesn't know and would analyze and save; this route is missing there (404), and the CLI and MCP then say so rather than analyze.

`nebula moodboard analyze <board> --dry-run [--accent-min-chroma N --accent-separation N --merge-delta-e N] [--json]` and `moodboard_analyze(dry_run=True, accent_min_chroma=…, accent_separation=…, merge_delta_e=…)` call it; thresholds without the dry run are refused. `nebula moodboard show` prints each palette and accent colour with its share and source images (`#4 0.35%, #5 0.26%`: image number and the colour's share of it).

### 1.9 Projects: which project an asset is in

Moodboards, Characters and project Styles share one meaning of "project": a **canvas project** from the project catalog (`GET /api/projects`), never the backend's working folder. "This project" or "current" is the one open on the canvas (the catalog's `activeProjectId`).

- `GET /api/project` returns `{id, name}` of the open canvas project, or 404 `"No project is open."`. The app doesn't call it: it reads the open project from its own project store (`frontend/src/lib/currentProject.ts`), which the CLI's and MCP's `current` also resolve to.
- `POST /api/moodboards`, `POST /api/characters`, and `POST /api/presets` with `scope: "project"` take a `projectId` only if it's a canvas project: an unknown id is 422 (`"No project has the id '<id>'. Use the id of a project from GET /api/projects ..."`), a project in Recently deleted is 422 (`"The project “<name>” is in Recently deleted. Restore it first, ..."`), an unsafe id is 400. Leaving `projectId` out saves the asset as Global. Lists still take any safe id.
- An asset never refuses to work outside its project. A Moodboard or Character node names its asset by id, so a node copied, pasted or imported into another project shows the asset, runs, and opens the Studio on it. Saving it from there keeps its `projectId`: it stays where it lives.
- In the app the Project tabs (Assets panel, both Studio rails, the Styles library, Recently deleted, the node pickers) list the open project's assets and relist when the project changes or a `storedAssetChanged` event arrives. With no project open the Project tab says `"Open a project to see its moodboards."` (or Characters, Styles) and New is off. A Studio opened on an asset from another project lands on the Project tab with `"This board is in <name>."` (`"This Character is in <name>."`) above the open project's list (`frontend/src/lib/assetHome.ts`). A draft started in one project is never saved into another: the save is dropped if the open project changed.

**Re-home of old-style assets (every start; `backend/services/asset_project_rehome.py`).** Before this, project assets were filed under the working-folder project (`nebula_nodes`, `NEBULA_PROJECT_ID`, ...), which no canvas project could see, and an older build or the desktop app on the same `~/.nebula` can still write one. Every folder under the moodboard, Character and preset roots (each store's own `store_root()`) that isn't `_global`, a canvas project's id or a project in Recently deleted is old-style. Each asset in one is moved by use (Justin picked this rule on 2026-10-19):

| Asset | Goes to |
|-------|---------|
| A Moodboard or Character used by nodes in exactly one canvas project (saved snapshots, and the open canvas for the open project; trashed projects don't count) | That project |
| One used in no project, or in two or more | Global |
| A Style (preset) | Global |

Assets in Recently deleted move too (their trash record's `projectId` and `scopeDir` change, so a restore lands in the new place). Only `projectId` changes (and a preset's `scope`, to `global`). It runs on every start; a start with nothing old-style writes nothing. Each moved file is first copied to `<root>/../<kind>-backups/project-rehome-<UTC time>/`, with `migration-log.json` listing every asset, where it went and why. An id already present in the target is skipped and logged once: `<state dir>/migrations/asset-project-rehome.json` remembers each skip by path, size and mtime, so the same skip isn't logged again, a changed file is, and the move happens on the first start after the collision is gone. Nothing changes while the catalog can't be read, or while there are old-style assets and an open canvas but no projects yet. It never stops the backend from starting, and prints one line only when it moved something or found a new skip; `NEBULA_NO_ASSET_REHOME=1` turns it off. To undo a re-home, stop the backend, copy the backup folder's files back over the root, delete the moved copies the log names (`file`), and start with `NEBULA_NO_ASSET_REHOME=1` (otherwise it moves them again). `move_asset(kind, root, source, target)` in the same module moves one asset between scopes with the same checks; 1.10 builds on it.

### 1.10 Moving a board or Character between Global and a project

Justin's call P4 (2026-10-19): a re-home that guessed wrong can be put right, and a board made in one project can become house style.

| Call | Body | Effect |
|------|------|--------|
| `POST /api/moodboards/{id}/move` | `{projectId: string \| null}` (required; null = Global) | File the board under that canvas project, or Global |
| `POST /api/characters/{id}/move` | same | Same for a Character |

- **Answer.** `{status, kind, id, from, to, fromName, toName, asset, detail}` plus `movedBy` when it moved. `status` is `moved`, or `unchanged` (200) when it was already there: nothing is written or broadcast. `from` / `to` are project ids (null = Global), the names are the catalog's (`Global` for none). `asset` is the asset as `GET` returns it.
- **Refusals.** An unsafe `projectId` (`""` included) is 400; a body without `projectId`, or with other keys, 422; a target that isn't a live canvas project is 422 with the create routes' sentences (1.9); no such asset is 404; one in Recently deleted is 409 (`code: "in_trash"`, "Restore it first ..., then move it."); two live copies of the id (a re-home that skipped a collision leaves one in an old folder), or a copy already in the target, is 409 and changes nothing.
- **What changes.** Only the file's folder and `projectId` (`asset_project_rehome.move_asset`). `id`, contents, `version` and `updatedAt` stay: a move isn't an edit, and nothing in the Studio or the nodes compares `version` or `updatedAt` (no stale-write guard reads them; saves are whole-draft `PUT`s). A node in any project still names it by id, so it shows and runs as before. `storedAssetChanged` is broadcast, so cards, both Studio rails and the Assets panel relist.
- **Who.** Anyone, agents included: moving it back undoes it. Boards and Characters keep no "changed by" field, so `movedBy` (`actor_record`, as Recently deleted's `deletedBy`) is in the answer only; nothing is journaled.
- **Studio.** Moodboard Studio and Character Studio show **Move** beside Delete for a saved asset, a menu with "Move to Global" (when it's in a project) and "Move to <open project>" (when it's Global or in another project; off, saying why, with no project open). Unsaved edits are saved first, as Delete does; a failed save stops the move. During the move the draft's save slot is held, so no autosave sends the old `projectId`; edits typed meanwhile are kept and saved after. Then the draft's `projectId` changes, the draft moves to its new scope's key (`assetStudioDraftKey`, `copyTo`, as on create), and the Studio opens the asset in its new scope, so the rail switches tab and its "This board is in <X>" notice follows (`frontend/src/hooks/useStudioAssetMove.ts`, `lib/assetMove.ts`, `components/asset-move/AssetMoveMenu.tsx`). A board's `PUT` still refuses a `projectId` change (422), which is why the draft must carry the new one.
- **CLI and MCP.** `nebula moodboard move <board> --to global|current|<project id or exact name> [--json]`, `nebula character move <character> --to ... [--json]`, `moodboard_move(board, to)`, `character_move(character, to)` (`moodboard_client.resolve_move_target` / `move_asset`, `character_client.py`). `current` with no project open, an unknown project, a name two live projects share, or a project in Recently deleted is refused before anything is sent. On a Nebula without the route they say so and move nothing.
- **Not here.** Styles (presets) have no Move; P4 named boards and Characters.

### 1.11 When the words and the measured colours disagree, and board notes

Design-canvas gap 18 (Justin's calls P1-P4, 2026-10-19). Where two parts of a board disagree, the higher wins; where it says nothing, the lower fills in: (1) the hand-written brief, as is, no check; (2) pinned colours: "must appear" always go, even against Avoid (the clash is listed), "keep out" drops near measured colours; (3) Direction and Avoid, through the colour check; (4) board notes, only when opted in; (5) what Nebula measured.

**Saved fields** (all optional; a board without them reads with the defaults and is never rewritten on read):

| Field | Type | Who writes it | Notes |
|-------|------|---------------|-------|
| `clashMode` | `leave-out` \| `flag` \| `no-measured` \| `keep-all` | person or agent | What a clash does. `leave-out` (default): a conflicting colour leaves the brief, listed with its reason; a warning stays, listed as "may clash". `flag`: nothing leaves unless the person says so; every clash is listed. `no-measured`: once there is a Direction, no measured colour goes (each listed, "Measured colors are off for this board"); without one it acts as `leave-out`. `keep-all`: as before this change; the check still runs and is saved, nothing is listed or applied, choices are ignored. Anything else is 422 |
| `colorChoices` | `{keep: hex[], leaveOut: hex[]}` | person or agent | The person's Keep anyway and Leave out. At most 24 per list, `#rrggbb`, a colour in one list only, and Keep anyway can't hold a colour pinned to keep out (422). Matched to measured colours within dE00 5, nearest first, so a choice survives a re-analysis that nudges the hex. Keep anyway doesn't pin: the colour goes back with its share and role. Pinning a colour to keep out drops it from `keep` when `colorChoices` isn't sent |
| `sendNotes` | boolean | person (on), anyone (off) | Board notes and image notes to generators. Off by default, on every board. Strictly `true`/`false` (422 otherwise). Turning it on (create with `true`, or `false` to `true`) is the person's: 403 with the person gate's `code` and a sentence about notes, and nothing in that request is saved. Sending `true` again when it is already on passes |
| `colorCheck` | `{version, basis, checks: {words: {version}}, findings}` | store | The saved check. Refreshed on every create and update (Analyze included) whose basis moved, and at startup for every board whose saved one is missing or stale (boards saved before it, a `LEXICON_VERSION` bump; only `colorCheck` is written, no backup): Direction, Avoid, pinned "must appear", the measured colours (hex, role, share), `LEXICON_VERSION` and the check's own version. A sent one is ignored |

**The check** (`services/moodboard_colour_words.py`, deterministic, no model, no cost). The Direction and Avoid text is parsed into colour terms with their modifiers, negation ("no", "without", "avoid"; it covers the noun phrase it governs, so it ends at "but" or at a comma or "and" after its noun: "No people, red flowers" allows red, "no red or orange flowers" excludes both) and scope (an object such as "flowers", a cast, or the whole palette), then matched in OKLCH by hue arcs and chroma gates; a hex written in the text matches within dE00 5. A cast term tests the share-weighted palette mean, so one warm accent on a cool board is only a warning. A Direction allowance that names the colour ("cornflower blue", a hue within its modifiers' gates, a hex) turns an Avoid conflict into a warning; one the colour only shares a hue arc with ("pale blue" for a saturated blue), and any temperature word ("warm", "cool"), leaves the conflict as it is. "Brown" conflicts from C 0.08 like any hue (only soft-colour words such as sage and lilac conflict from C 0.03), so near-black shadows are at most a warning. The allowance also flags a colour of that hue that is clearly more saturated than the reference. The numbers sit in one table and are retuned by bumping `LEXICON_VERSION`, which refreshes saved checks. Each finding: `{hex (null for the whole palette), role (palette, accent, pinned), share, level (conflict or warning), source (avoid or direction), clause, rule, reason, foundBy}`. A `reason` starts "Avoid: <the item>" or "Direction: <the person's words>" and quotes only whole words as written (any letters; a hyphenated word is one word). When a Direction allowance makes a clash a warning it adds the allowance's words in quotes through their noun phrase, plus "in the <noun>" for a list item that takes its head's noun: "Direction: sun-faded. This color is more saturated than that, though the Direction also asks for “Warm late-summer light”." and "Avoid: blue flowers. The Direction also asks for “cornflower blue”, so it may clash." (`LEXICON_VERSION` 3, 2026-10-20; version 2 quoted the first noun alone, "allows Warm for the late"). `foundBy` is `words` today. A second check (one that looks at the images) adds `checks.<name>` and its findings under the same basis; `compose` uses a saved check whose basis matches, else runs the words check in memory without saving.

**`brief` adds** (1.2): `leftOut` (colours generators don't get), `mayClash` (still sent), `kept` (Keep anyway), `pinnedClashes` (pinned colours that clash; they still go), `paletteClashes` (whole-palette findings, such as a cast), each item `{hex, role, share, level, reason, reasons, foundBy, why}` with `why` `check`, `choice` or `mode`, and `level` `off` for one left out by `no-measured`; `clashMode`; `notesSent`. `palette`, `accents` and the brief's colour sentences are what generators get. The lists are computed with an override active too, since they shape `palette`.

**Notes.** Without the opt-in the brief has no `Notes:` sentence and its visual cues are only the measured ones (`MEASURED_CUES`: palette-led, the mode cues, the palette labels), not words lifted from the notes. Agents and the person still read notes everywhere.

**The node.** `nebula-moodboard` gains `send_notes`: `board` (default; follows `sendNotes`), `yes` or `no`. A node saved before it reads `board`. Moving it toward sending (`no` to `board`, anything to `yes`, a new node on `yes`, or pointing a node on `yes` at another board) is the person's: an agent's edit, create or apply gets 403 naming `send_notes` and `propose_change`. Its bundle: `notes` and `images[].notes` are `""` unless sent; `notesSent`, `leftOut`, `mayClash`, `kept`, `pinnedClashes`, `paletteClashes` and `clashMode` are added; `analysis` is the generator's view (measured keywords only, `summary` and `tasteProfile` rebuilt from the brief's colours without notes, `subjectBias` `[]`, `styleBrief` without notes, `images[].notes` `""`, `providerHints.generic.palette`/`accents` the brief's). Its colour lists are the brief's too: `palette`, `accents` and `colors` hold only what generators get, and each image's `palette`/`accents`/`colors` drop colours within dE00 5 of one left out or pinned to keep out, so an LLM node reading the bundle can't put one back. `leftOut` says which went and why. The saved analysis is never changed.

**CLI and MCP.** `show` prints "Left out of the brief:" (each with `Keep it: nebula moodboard set <id> --keep-anyway "#hex"`), "Kept anyway", "May clash (still sent):", "Pinned colors that clash (still sent):", "Notes: not sent to generators" (or "sent") and "Clash check: <mode>" when not the default. Each line gives every reason (`reasons`, joined with "; "; Studio joins them with " · "), so a colour off for `no-measured` still shows its clash. `set` takes `--keep-anyway`, `--leave-out`, `--leave-out-flagged`, `--reset-color`, `--clash-mode`, `--send-notes` / `--no-send-notes`; `moodboard_update` takes `keep_anyway`, `leave_out`, `leave_out_flagged`, `reset_colors`, `color_choices`, `clash_mode`, `send_notes`. `--json` and the MCP tools carry `clashMode`, `colorChoices`, `sendNotes` and `colorCheck`. `previous` has `clash_mode` and `color_choices`, and `send_notes` when the change touched it. An agent's `--send-notes` is refused in the CLI's own words and nothing in the call is saved.

**Studio.** Under "Brief sent to generators": "Left out of the brief" (Keep anyway, or Undo for one the person left out), "Kept anyway" (Undo), "May clash" (Leave out), or in `flag` mode one "Flagged" list with Leave out all flagged, and "Pinned, so it still goes". `keep-all` shows "Clash check is off for this board." The swatches dim a left-out colour, with the reason in its tooltip. `BriefFields` has an Advanced disclosure with the four modes; under Notes, a "Send these notes to generators" switch, off. The Studio shows the backend's lists and never recomputes them.

### 1.12 Board edits

`POST /api/moodboards/{id}/edits` (`services/moodboard_edits.py`, moodboard canvas plan section 5.1). The body is `{ops, baseVersion?, say?}`: 1 to 500 ops, the version the caller read, and up to 140 characters of what an agent is doing (trimmed, for the journal). The ops are staged on a copy of the board, each checked as it applies, and saved once with `version + 1`; an op that fails refuses the whole batch with 422 naming it ("op 3 (place): ..."), and nothing is saved. 404 for an unknown board or one in Recently deleted. Anyone may send edits, agents included: every batch is undoable and journaled.

**Ops are absolute sets** ("image 3 weighs 0.5", "card c1 at 200, 40"), so a batch sent twice changes nothing the second time. Names: an image by its id or its number (`#n`, as the board was before the batch, so numbers in one batch don't shift as images go); a frame by id or name (ignoring case); a card by its placement id, `image@frame`, or the image when it has one card.

| Op | Keys | Effect |
|----|------|--------|
| `add` | `urls` or `images` (`{url, id?, weight?, notes?, privateNote?, excluded?, placements?}`), `index?`, `at?: {x, y}`, `in?: frame`, `size?: weight or "WxH"`, `unique?` | Adds images at `index` (default last). Placed by the server (1.3) unless they send `placements`; `at` is the top-left, `in` lays them out in the frame (it grows to fit). With `unique`, a url already on the board is skipped; an id already on the board is always skipped. `applied[i]` has `added` (ids) and `skipped` |
| `remove` | `images` (or `image`) | Removes them; one already gone is `unchanged` |
| `place` | `placement` (the card) or `image`, `x`, `y`, `frameId?` | Moves a card. `frameId` moves it into that frame (refused with "Already in <frame>" when the image has a copy there) or, with `null`, out of its frame: the copy is removed when the image has another, else it becomes loose |
| `resize` | `placement` or `image`, `weight` or `w` and `h` | Card weight 0.05 to 1; `w × h` keeps the card's aspect. The image's weight becomes its largest card's |
| `link` | `image`, `frameId`, `x?`, `y?`, `weight?` | A copy of the image in a frame (at most 8 cards, one per frame; "Already in <frame>" otherwise). A loose card joins the frame instead of making a copy |
| `unlink` | `placement` (a card in a frame), or `image` and `frameId` | Takes the image out of that frame: the copy goes, or, when it is the image's only card, it stays as a loose card |
| `setAside` | `image` or `images`, `value` | The Set aside switch (1.1). Off on a weight-0 image also sets the weight its card shows |
| `weight` | `image` or `images`, `value` | 0 to 1; the cards scale as on `PUT` (1.3) |
| `note` | `image`, `notes?`, `privateNote?` | Either or both |
| `frame.create` | `name?` (default "Look N"), `kind?`, `x, y, w, h` or `rect`, or `around: [cards]`; `id?` | A frame (at most 100, names unique ignoring case, sides at least 160). `around` fits the cards with a margin and moves them in; a rectangle takes the loose cards wholly inside it |
| `frame.update` | `frame`, `name?`, `x, y, w, h` or `rect` | Rename or move/resize; a move moves its cards, and it can't shrink to cut one off |
| `frame.delete` | `frame` | Its cards stay where they are, loose (a copy whose image has another card goes) |
| `frame.merge` | `frame`, `into` | The cards move into `into`, which grows to hold both; where an image is in both, the heavier copy stays |
| `restore` | `slices` | An undo (below) |

`arrange`, `look.set`, `look.inherit`, `suggestion.accept`, `suggestion.dismiss` and `realPerson` are refused by name: they come with later parts of the board canvas.

**The answer** is `{board, version, applied, undo}`. `applied` has one entry per op: `{index, op, status: "applied" | "unchanged", ...}`. `undo` is `{ops: [{op: "restore", slices}]}` (or `{ops: []}` when nothing changed): each slice holds the before value of one frame, image, image's settings or image's cards, or of the board's own fields, and the `expect`ed after value. Sent back as edits, a slice whose part changed since is skipped and reported (`applied[0].skipped`, each `{part, image or frame or field, number?, reason, message}` with `message` such as "#4 changed since, left as is"), so one stale reference doesn't stop the rest; a `restore` has its own `undo`, and its `applied` entry also lists `removed`, the image ids it took off the board. Image settings go back one by one: one that changed since is left ("#2's weight changed since, left as is", with `settings` naming it) and the others go back; the image's card slices aren't reported again then. A `fields` slice (`{part: "fields", before, expect}`) holds `name`, `notes`, `mode`, `strength`, `direction`, `avoid`, `pinnedColors`, `clashMode`, `colorChoices`, `sendNotes` and `briefOverride` (its text, `""` for none), as a write reads them (the brief fields normalized); each field is checked on its own, against the board as the restore found it, and set as a `PUT` sets it, last in the restore, so a hand-written brief is stamped with the board as it ends up. One changed since is left ("Direction changed since, left as is"), so is one whose going back would undo a colour choice made since, unless the slice puts `colorChoices` back too ("The pinned colours would undo a colour choice made since, left as is"), and so is one only the person may set this way when an agent sends it ("Send notes to generators is the person's to turn on, left as is"; "The hand-written brief is the person's to change"); a value a `PUT` would refuse is a 422. Every batch's diff carries a `fields` slice when the board's fields changed, so a `restore` that put fields back has an undo for them too. Putting back the board's mode, strength or notes clears the analysis, as a `PUT` does. What a slice puts back is checked as the ops and `PUT` check it (422): a `before` names the same image, frame or card as its slice, an image record has a url, and settings are a weight from 0 to 1, text notes, a private note of at most 2,000 characters and a true/false switch. A frame a restore touched grows to hold its cards, so a partial undo never leaves a frame smaller than a card still in it. The whole-board analysis is cleared when what it reads changed (each image's url, weight, notes and switch, and their order); moving or resizing a card without changing the image's weight, frames and private notes keep it.

**`baseVersion`.** On `/edits` and `PUT`, a `baseVersion` that isn't the board's version is a 409: `{detail, code: "version_conflict", version, board}`, with the board as it is now, so the caller rebases on it and sends again. Without it a write applies to whatever is saved. Writes to one board are serialized, so two writers racing never lose an edit: ops apply to the board as saved, and only a `PUT` that sends `images` (the whole list) can still undo another writer's image change, which `baseVersion` prevents.

**The broadcast.** After a board write that changed something, `storedAssetChanged` adds `version`, `edit: {actor, tab?}` (`_graph_edit_origin`: `tab` only with this launch's person token, so an agent can't pass for a tab), `touched: {images, frames, looks}` and `undo` (null for a `PUT`, or for a batch over 200 ops). An `undo` that holds private-note text (a private note changed, or an image with one added or removed) goes whole only to the person's canvas sockets; every other listener (CLI, MCP) gets `undo: null`. Keep and Analyze send `version` and `edit` with nothing touched.

**The journal** (`canvas_events`, as for the canvas). Each batch, and each `PUT`, that changes one of these is one event in the actor's name, tagged with the open canvas project: `board.added`, `board.removed`, `board.frame`, `board.grouped` (a card into or out of a frame), `board.setAside`, `board.resized`, `board.noted` (an image's notes, or the board's) or `board.moved`, first of those that applies; `data.kinds` lists every kind in it, with `refs` (`{number, id}` per image) and the board's id, name and scope. A move under 8 px, a rename and the brief fields aren't journaled. Never any note text: a private note change reads "private note changed". `board.sorted`, `board.arranged` and `board.suggested` are reserved for Analyze.

**Clients.** `moodboard_client.edit_board(api, ref, ops, base_version=, say=)` sends a batch; a 409 comes back as "the board changed since you read it (it is at version N): read it again ...". `add_to_board` sends one `add` op with `unique` (a PUT on an older backend) and returns the batch's `undo`; `update_board` (`nebula moodboard set`, `moodboard_update`) sends its image changes and removals as one batch of absolute ops by image id, then the board's own fields with a `PUT` of only the fields the call sets, with `baseVersion` (the whole image list, unchecked, on an older backend; a backend that refuses the `baseVersion` key gets the same `PUT` again without it). On a 409 it reads the board again and sends the fields again, at most 3 tries in all: a value given outright goes as given, a change to a list (`avoid_add`, `pin_colors`, `keep_anyway`...) goes on the list as it is now. A field given outright that someone else changed since the read, to anything but the same value, is never sent over theirs: the call stops with "<field> was changed by someone else after this call read the board, so it wasn't set. Nothing more was written" (and `previous` when the image changes were already saved); running it again reads their value and then wins. Three conflicts in a row stop with "The board kept changing while this ran (3 tries)". `previous` holds only what the call changed (fields as the board the `PUT` replaced had them, image settings as read) plus `undo` (1.6), and is left out of an error when that is nothing. `undo_board(api, ref, undo, fallback=)` sends an `undo` and returns `(board, removed, previous, skipped)`; on a backend without `/edits` it runs `update_board(**fallback)`. An image op on an image someone else took off the board since the read is refused by the batch, and `update_board` says so by the number the caller read: "Image N was taken off the board by someone else after this call read it, so nothing was changed". After a 409, a call left with nothing to send returns the board as it read it again; `nebula moodboard add --json` and `moodboard_add` return `addedIds` and `undo`, and the CLI prints how to take them off again. Moodboard Studio (`lib/moodboardEdits.ts`) applies each image change to its draft at once and queues it as an op (one per thing set: typing a note queues one), sent 600 ms after the last change or when a field loses focus, with the version it last read. On a `storedAssetChanged` for the open board with a newer version and no tab of its own, it reads the board again and replays its queue on top, dropping a queued op on an image that is no longer there; board fields the person changed since keep their value, the rest take the board's. After a `PUT`, the fields it sent count as read with the values the person sent, not the ones the server cleaned (trimmed, lowercased), so a later outside edit of them still shows. A 409 does the same, then sends again.
