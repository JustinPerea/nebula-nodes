## 2026-10-09

- Startup will show a project home instead of immediately entering the last canvas. Preserve the existing canvas as a migrated saved project; opening home must not clear it or submit generation.
- Store project documents in the backend's existing per-user state directory, outside the repository. Include graph outputs, immutable run history and the canvas viewport. Local media stays in the existing output store; portable exports remain the existing file action.
- Project switches must save the outgoing project first, preserve node IDs and connections, reset transient editor/selection state, and honor the existing execution/import/paid-provider guards. Failed saves or activation must leave the current project available.
- Use the current monochrome interface, matching node corner radii. The home screen provides recent projects, search, names, and an explicit New project action; project workspaces have a clear return to Projects.
- New projects open immediately as blank canvases named Untitled project; the home card supports inline renaming. Every cold page load opens Home. Resuming the already loaded project can retain its studio; activating a different project always enters Canvas.
- Run history now uses a project-specific browser cache in addition to the authoritative project document. The legacy global cache is retired only after its migration save succeeds, preventing obsolete running records from recreating ownership on later reloads.
- A workspace revision fences delayed mutations and results. Switching waits for pending writes, uploads, creation acknowledgements, running jobs and unresolved paid-provider records. Opening a saved project never submits a provider operation.
- If another window changes the active project while this window has unsaved edits, Retry first saves an inactive recovered copy with an idempotency ID, then reloads Projects. Failed recovery leaves the local canvas available. Restored upload metadata reports interruption rather than an endless spinner.
- That is for the person's own switch in another window. When an agent (or a script that isn't the person's canvas) opens or makes a project, the open window follows it instead: its last unsaved changes go into the project that was open (through the backend's `handoff`, which stays open until the next switch so an autosave already in flight doesn't block the last save), or into a recovered copy if that fails, and a toast names the agent and offers a way back (2026-10-18).
- Storage is an owner-only atomic catalog with a 16 MiB limit per project and 128 MiB overall limit. The catalog and legacy CLI graph cache are separate atomic writes; switching prepares both and rolls back the cache on catalog failure before adopting live memory. A catastrophic rollback failure is surfaced explicitly. Local project saves retain media references in the existing output store; portable asset copies remain the .nebula.zip export.

## 2026-10-10 — Deleting projects

- Each card has a trash button beside rename. (Superseded the same day: see Recently deleted below.)
- `DELETE /api/projects/{id}` requires the current `workspaceRevision`, so a stale view can't delete anything. Generated media stays in the output store; only the catalog entry goes.
- Deleting an inactive project leaves the live canvas and revision untouched and broadcasts nothing. (Since 2026-10-20 it sends `projectsChanged` for the Projects list, still no graph sync: see below.)
- Deleting the open project carries the same run and paid-start fences as switching. It empties the live graph (so `GET /api/projects` won't re-adopt it as a Recovered canvas), clears `activeProjectId`, issues a new revision and broadcasts `canvas.replaced` with reason `project-delete`. The browser skips the outgoing save (it's being thrown away), waits for any in-flight save, and drops that project's Creator draft.
- Recovery no longer needs the source project to exist. A tab with unsaved edits to a project deleted in another window saves them as "Deleted project (recovered)" instead of failing on every retry.

## 2026-10-10 — Recently deleted (trash and undo)

- Delete is now a soft delete. `move_to_trash` moves the whole project record, pins included, from `catalog["projects"]` to `catalog["trash"]` with a `deletedAt`, in the same atomic catalog commit. Restoring moves it back unchanged. It comes back closed, even if it was open when deleted.
- Trash lives in `catalog.json` beside projects, so it counts toward the 128 MiB catalog limit and survives restarts. Entries older than 30 days (`TRASH_RETENTION`) are swept on `GET /api/projects` and before any restore, so an expired entry can't be restored even before a sweep.
- Routes: `POST /api/projects/{id}/restore`, `DELETE /api/projects/trash/{id}` and `POST /api/projects/trash/empty`. None of them touch the live canvas, so unlike delete they don't take a workspace revision; a missing entry is a 404. Restore still honours the 500-project limit (413).
  - 2026-10-18: `DELETE /api/projects/trash/{id}` and `POST /api/projects/trash/empty` are person-only now (deleting for good can't be undone; agents get a 403 that says they can restore). Trash entries also record `deletedBy`. Projects share `GET /api/trash` and `nebula trash` with moodboards and characters (see implementation-notes.md and docs/MCP-SETUP.md, Recently deleted).
- `GET /api/projects` now returns `trash` (newest first, each with `deletedAt` and `purgeAt`). A corrupt trash entry fails the catalog read (507), the same as a corrupt project, instead of being dropped.
- UI: the trash button deletes in one click (it's reversible now) and shows an Undo toast for 8 s, held while the toast is hovered or focused. A collapsed **Recently deleted** section below the grid lists entries with Restore and a two-step Delete forever, plus Empty. The toast enters on a computed spring (`linear()` from k 380, c 30, m 1) and is static under reduced motion.
- Recovery of a stale tab's edits now names the copy after the trashed project when the source is still in the trash.

## 2026-10-17 — Tabs from before a params upgrade

- A tab whose bundle was built for another saved-params version (`backend/services/saved_graph_upgrades.py`) is stale even with the current revision. Every request from the canvas sends `X-Nebula-Params-Version`; a request with a lower or higher version, or with none when it carries the revision header or comes from a browser (`Origin` or `Sec-Fetch-Site`; an old tab can reach the canvas with no project context, so the revision alone doesn't cover it), gets 409 `{code: "params_outdated"}` on the graph, execute, cinema and quick routes, every project write except `/api/projects/recover`, and preset writes. Requests with none of these headers (agents, CLI, MCP, curl, Node scripts) pass.
- A boot that finds the catalog or state.json saved before the current version rotates `workspaceRevision` once and writes the catalog at once, so tabs from before the restart ignore graph syncs and go to the existing conflict flow (recover if dirty, then Retry).
- `paramsVersion` is in graphSync, `GET /api/projects` and the create and open replies; a backend that sends none predates the gate and counts as version 0. A tab that sees another version stops saving and running, recovers unsaved work once (a Run the backend refused isn't unsaved work), and reloads when the backend is newer; it reloads at most once per backend version (sessionStorage), and otherwise says to rebuild the frontend, restart the backend, or (with sessionStorage blocked) reload the tab. Details in implementation-notes.md, "Justin's answers 2026-10-17, round 2", item 3.
- The desktop app checks the same thing at launch, before a stale bundle can open: every frontend build writes `nebula-build.json` (`{"paramsVersion": N}`), `/api/health` reports `paramsVersion`, and `desktop/frontend-build.mjs` refuses a build with no stamp or another version than the healthy sidecar's, stops the sidecar and names the rebuild command. Dev mode skips it; the in-tab gate stays as the backstop. Details in implementation-notes.md, "Desktop launch params check (2026-10-17)".

## 2026-10-20 — Projects follows changes made elsewhere

- Every change to the saved-project list (create, open, save or rename, cover, delete, restore, delete for good, emptying Recently deleted, a recovered copy) sends `projectsChanged` (`{change, projectId}`) over the socket after it commits, whoever made it. A refused change sends nothing. Projects lists again on it; off Projects the list is marked stale and `goHome` lists again. A tab with no project open takes the listing's workspace revision, so its next New project or Open isn't refused.
- An agent's `new_project` / `open_project` is followed from Projects too, with or without a project loaded (with none, only from the revision the tab listed), and opens the canvas, as the tools say. A sync with a revision a no-project tab never listed (a reconnect's first sync after missed events) lists again instead.
- The switch toast's way back follows the list: renamed, or gone once that project is deleted, on the canvas too.
- On Projects, the person's own switch in another window, or a delete of the loaded project, no longer stops the screen with a conflict when nothing is unsaved and no run is going: the tab lets go of the loaded project and lists again. With unsaved work it's still the recover-then-Retry conflict above. Details in implementation-notes.md, 2026-10-20.
- A listing that fails on Projects is retried quietly 1, 2, 4, 8 and 16 s later, then on window focus, coming back online or a socket reconnect; never off Projects (goHome lists again).
- A project that opens reads "Saved" until someone changes it. The camera the canvas places itself when it mounts (React Flow's start on an empty canvas, or its first fit of a project saved without a view, including the fit a canvas that mounted empty runs when a followed project's graph arrives) isn't an unsaved change; it is saved with the next real change. Params the backend upgrades on read aren't either: the open commits them. Details in implementation-notes.md, 2026-10-20 follow-up.
