# 2026-10-21 — `nebula` CLI twins for #121's project and settings reads

Branch `feat/cli-project-reads`, base PR #121's head `be1aca4d` (feat/mcp-projects-and-reads, open, waiting on Justin's merge OK).

- **What changed and why.** Justin (2026-10-20): "Every feature we add needs to make sure we include MCP support for agents", and the repo's rule that each MCP tool has its `nebula` twin where the CLI covers the area. #121 added `rename_project`, `get_project`, `get_settings`, `provider_status` and `list_trash`'s `scope`/`project_id` with no CLI twins. Now:
  - `nebula project rename <id|current> <name>`: PUT /api/projects/{id} `{name}`, the header's rename. Prints `"old" → "new"` and the exact command that puts the old name back (`nebula project rename <id> 'Old name'`); the same name again says "already named". The route journals `project.renamed` under `$NEBULA_AGENT_NAME`. `--json` is rename_project's result.
  - `nebula project show <id|current>`: GET /api/projects/{id}?view=agent (get_project). Compact text: a PROJECT line (open or closed, updated), who made it, the cover, nodes in `nebula look`'s format (with a universal node's `ports` line and the error with any quoted key already hidden by the server), WIRES, RUN HISTORY (status, trigger, start, duration, `ran`, `made`; never values). `--json` is get_project's result.
  - `nebula trash list --scope global|project --project <id|current>`: list_trash's three parameters (`--project-id`, the tool's name, works too, hidden). `--project` alone means scope project, as in the tool. The header says where it looked ("in Global", "in project Boards (<id>)").
  - `nebula keys` is the get_settings twin: set or not set, plus a SETTINGS line (execution mode, batch cap, Krea connection, export folder, routing). `--json` is get_settings' result.
  - `nebula providers [--refresh] [--json]` is the provider_status twin: each provider's status, when it was checked and its detail, then the Krea account (a pending sign-in says "waiting for the person", never the link).
  - `nebula projects --json` is list_projects' result (with `cover`), the one #121 change to an existing tool the CLI had no way to read.
  - **One implementation.** The shaping that lived inside mcp_server.py (a project's "current", the cover's links, settings to booleans, the health rows, Krea's link left out) moved to `backend/project_client.py`, like style_client/moodboard_client. The MCP tools and the CLI both call it with their own headers (`X-Nebula-Agent`, the token from nebula_api), so `--json` equals the tool's result by construction. A `via` argument words the two hints in each surface's own calls (`rename_project('<id>', 'Old')` vs `` `nebula project rename <id> Old` ``), as GET /api/agent/start does. `NebulaClient.shared()` runs one of these with the CLI's identity and turns a refusal into `error: <detail>`, exit 1.
- **Decisions not in the spec.**
  - *`nebula keys` stays the settings read and `nebula providers` is new*, rather than one command with a flag. The CLI names a read by its noun (`projects`, `pins`, `proposals`, `notes`, `spend`); "which keys are set" and "do they work" are different questions with different costs (`providers` may probe providers over the network, `keys` never does), matching get_settings vs provider_status.
  - *The CLI never prints a key's ending, whatever the route sends.* Q55 a (Justin: "Only the app (your person token) gets the endings. Everything else learns which providers are set, and nothing more") already gives the CLI a bare `***`, but `nebula keys` used to print whatever string came back. It now prints from get_settings' booleans, so even a reply carrying an ending (a test forces the person headers onto the CLI's requests) prints none. The help says the CLI has no person token. It prints "set", not `***`, so nobody reads a mask as an ending.
  - *`nebula look` gained the `ports` line too.* The node lines are one function (`_node_lines`) shared by `look` and `project show`; before, `look` dropped a universal node's ports that look_at_canvas has had since #132.
  - *The in-app Claude primer* (services/chat_session.CLAUDE_CLI_PRIMER) listed `nebula keys` as something the MCP tools don't cover. Since #121 get_settings covers it, so it's dropped from that list. The first-turn MCP INSTRUCTIONS are unchanged (2,994 of 3,000 characters).
  - *`nebula context` is unchanged.* It doesn't list commands: its NEXT hints are fixed first-build steps, and start_here doesn't mention rename/get_project either. The command list lives in `nebula --help`, SKILL.md and MCP-SETUP.md, which now name the new commands.
- **Tradeoffs.** The shared module calls the routes with the MCP's 10 s timeout (60 s for health probes) for the CLI too, where it used to wait 300 s; these are quick reads. `nebula trash list --project` makes one extra GET /api/projects to name the project in its header. `project show`'s human format shows at most 4 cover links and cuts errors at 300 characters; `--json` has everything.
