# 2026-10-21 — A proposal that can't run here is kept, and the agent is told to withdraw it before proposing something else

Branch `fix/unrunnable-proposal-withdraw-first`, from origin/main `cc5797ad` (after #150). Uncommitted (the coordinator commits). No paid provider call, no package installed, no frontend file changed.

- **What changed and why.** Q109 asked: "An agent proposes a model that can't run here (no key for it). Refuse the proposal?" Justin's answer: "b) Keep it with the warning, and tell the agent to withdraw it before proposing something else." (He chose this over the recommended a, refuse it.) The trigger was the Q104 rerun (PR #150, run B3): a CLI agent proposed FLUX.2 [pro] with no BFL or fal key, got the warning, then proposed Nano Banana and left the first proposal open, so the person had two to answer. The proposal and its warning stay exactly as they were. What changed is what the agent is told:
  - **The warning names the withdraw call.** `canvas_proposals.readiness_warning` now ends with "If you propose something else instead, withdraw this one first: `<call>`." The reply also carries `withdrawWith`, the call on its own. Each surface names its own call. MCP gets `withdraw_proposal(proposal_id="p_…")`. The CLI gets `nebula proposal withdraw p_…`, plus `--as <name>` when the agent named itself with `--as`, because withdrawing needs the same name. HTTP gets `DELETE /api/canvas/proposals/p_…`. The forms are `WITHDRAW_MCP`, `WITHDRAW_CLI` and `WITHDRAW_HTTP` in the shared service.
  - **A reminder when it matters.** Say the same agent makes a new proposal while it still has an open proposal on the same canvas (project) that can't run. The new reply then lists those proposals in `stillOpen` (`[{id, note, withdrawWith}]`) and adds `reminder`: "Your proposal p_x is still open and can't run here; withdraw it if this one replaces it: `<call>`." `nebula propose` prints it as a `reminder:` line, and `--json` and `--json --wait` include both fields. `ProposalBook.open_unrunnable` finds these proposals. Nothing is withdrawn for the agent: Justin chose to tell it, not to decide for it. Other agents' proposals, and the agent's own proposals that can run, don't count.
  - **One wording function.** `canvas_proposals.agent_wording(response, lister=, withdraw=)` builds `warning`, `withdrawWith`, `stillOpen` and `reminder` for one surface. `main.create_canvas_proposal` calls it for HTTP. `mcp_server._worded_for_mcp` and `cli/commands/proposals.run_propose` call it again with their own lister and withdraw call. So the text is written in one place.
  - **Coming back later (task item 4).** `nebula context`, `start_here` and `nebula look` already listed open proposals, but they didn't say whether one could run. That was cheap to add. `ProposalBook.brief` now carries `cantRun` (how many of the run's nodes can't run here, present only when it's above 0), and the text formatters add "; 1 node can't run here" inside the expiry brackets. I marked every open proposal, not only the caller's own: the mark is about the proposal, and the brief has no caller.
  - **Docs.** The `propose_change` and `withdraw_proposal` docstrings, docs/MCP-SETUP.md (the tools list, plus a new "Withdraw it before proposing something else" paragraph in Proposals) and skills/nebula/SKILL.md (the propose part). The first-turn MCP INSTRUCTIONS are untouched.
- **Decisions not in the spec.**
  - "Can't run" means `cost.notReady` as read when the proposal was made, the same data the canvas bar draws from. Suppose the person adds the key after the first proposal. The canvas bar re-checks keys live, but the reminder and `cantRun` still count that proposal as unable to run. Re-staging every open proposal on each new proposal to re-check them would cost far more than this hint is worth.
  - "Same canvas" means the same `project_id`. Opening another project already invalidates every open proposal, so in practice this means "open now".
  - `nebula propose --as X` names withdraw with `--as X` (shell-quoted). With `NEBULA_AGENT_NAME`, the call is the plain one.
- **Surprise (fixed).** The warning had a double full stop for route-table nodes ("…in Settings > Providers.. Tell the person…"), because the route message ends with its own period. It showed up in the first failing run of the new FLUX.2 test. `readiness_warning` now strips a trailing period from each line, and a test pins it.
- **Tradeoffs.** The reminder repeats each still-open proposal's id and call. An agent can have at most 3 open proposals, so that's at most two sentences. A proposal that can't run, made right after another that can't, carries both its own warning and the reminder. That's intended, since both apply.

- **Review.** One finding, confirmed and fixed. `nebula propose --json --wait` printed the agent lines it had at create time, whatever happened during the wait. So after the person rejected the proposal (or it expired), the output still carried `withdrawWith` and "withdraw this one first", and that call would get a 409. `stillOpen`/`reminder` could also name an earlier proposal that closed during the wait.
  - The fix is `_lines_after_wait` in backend/cli/commands/proposals.py. Once the proposal is closed, `withdrawWith` goes, and the warning is reworded without its withdraw step, so it still says why an accepted run fails. `stillOpen` is checked again with one `GET /api/canvas/proposals` and keeps only proposals that are still open. On a timeout the proposal is still open, so its call stays.
  - I used the open list rather than one `GET` per id, because a missing id makes the CLI client exit with an error after the person has already decided.
  - Text mode prints the reminder before the wait, which was true when printed. MCP `get_proposal` carries no agent lines, so neither needed a change.
