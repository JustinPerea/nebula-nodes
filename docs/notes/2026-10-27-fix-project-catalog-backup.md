# 2026-10-27: a damaged project catalog restores its last good copy

Branch `fix/project-catalog-backup`, cut from origin/main at c1e7338c. Justin approved the fix on 2026-10-27; GM's brief: "keep a last good copy of the catalog and restore from it, with a line saying it did."

- **The problem.** `projects/catalog.json` is read fresh on every request. A file that wouldn't parse or validate answered 507 to every project read and run start, through restarts, and the person couldn't repair it.
- **What the layout is (it changes the brief).** Every project lives whole inside catalog.json: name, dates, cover and pin, `createdBy`, pins, Updates, questions, the snapshot (nodes, edges, run history, viewport, Create draft). There are no per-project folders or files. The folders named by project id (moodboards, characters, styles) hold assets, not projects. So "re-add from disk" means the project records the damaged file (and any damaged copy) still holds. "Entries whose project data is gone get dropped" never applies: a record in the copy *is* the project's data.
- **The last good copy.** `catalog.json.bak` is written after every commit, from the bytes the commit wrote, and only when `_check` accepted that catalog (`prepare` already ran the check for the projection cache; the same check gates the copy). `catalog.json.bak.1` is rewritten from the committing catalog when it is missing or over an hour old. Both go through a private temp file, fsync, `os.replace`, then a directory fsync, after the commit's own rename and directory fsync. A failing copy write never fails the commit; the next commit writes it again. A read under the lock seeds the copy for a catalog saved before copies existed.
  - *Why two generations, not more:* each is a full copy (a catalog may be 128 MB). The second covers the newest copy being damaged too (same disk event, a sync tool); a third would add an older state that the damaged files can't add to. The older copy is written from a catalog that validated, never renamed from whatever the newer copy holds, so a damaged newer copy can't rotate into it.
  - *Cost:* every commit writes the catalog twice (autosave commits every ~600 ms). Accepted for now; see open items.
  - `prepare` now writes `version`, `activeProjectId`, `workspaceRevision`, `migratedProjectId` first, so a file cut short still says which project was open.
- **Reading a damaged catalog** (`ProjectStore._load` / `_recover` / `_restore`, `services/catalog_recovery.py`). `_load` raises `_Damaged` for not-JSON (`corrupt`), the wrong shape (`invalid`, including `TypeError` from a list where an id belongs), or a missing catalog.json while a copy exists (`missing`). A symlink, an oversize file, an I/O error and a failing params upgrade still refuse as before (they are not damage). Under the store's lock, the reader reads again (another request or process may have restored it), then:
  1. reads the copies newest first and takes the first that parses and validates;
  2. salvages each damaged file (the catalog, then any damaged copy newer than the one used): if it parses, each record on its own; if not, a scan for `"<32 hex>":{` keys decoded with `raw_decode`, validated per record (`entry_ok`: id matches, snapshot with node and edge lists, every field the listing reads, a tz-aware `deletedAt` for a trashed one). A key where a record belongs (first in its group, or right after a complete record) whose record won't decode is reported as `incomplete`;
  3. reconciles (`reconcile`): a record the copy lacks is added back (to Recently deleted when it carries `deletedAt`); a record the damaged file holds *newer* than the copy (latest of updatedAt, lastOpenedAt, deletedAt) replaces it (a commit whose copy never landed: an edit, a move to Recently deleted); an older or equal one never does (the copy is known good, the damaged file may carry the damage). Nothing the copy holds is dropped. Past `MAX_PROJECTS` or the size limit, a record is left out and reported (`limit`, `size`); if `prepare` still refuses, the copy alone comes back and every add-back is reported;
  4. the open project: the damaged file's when it says and that project came back live; none when it says one that didn't come back (the live canvas in state.json is that project's, and the next listing would overlay it onto whichever is open); otherwise the copy's;
  5. a new workspace revision (open tabs reload);
  6. keeps the damaged catalog as `catalog.json.damaged-<UTC>-<8 hex>` (a hard link, else a fsynced copy; reused if a failed attempt already kept the same file or bytes) and each damaged copy as `catalog.json.bak[.1].damaged-…`, *before* anything is written. Nebula never deletes them. A damaged older copy is taken out of use only after the commit lands;
  7. commits through the normal `prepare`/`commit_prepared` (which writes the new copy), then records the restore in `catalog-restore.json` (last 10) and announces it once the outermost lock hold lets go (`on_restore`).
  - *No good copy:* the same reconcile from an empty catalog, `kind: "rebuilt"`. When no damaged file holds a single complete project, it refuses with the existing 507 and changes nothing. Exception: catalog.json *missing* with only damaged, empty copies keeps them and starts from an empty list, as a missing catalog always did (a refusal there would never end).
  - Every step prints a `[projects]` line in the backend log.
- **Concurrency.** The store's existing `.lock` flock, now re-entrant per thread (`_locked`, a thread-local depth): a read inside a transaction that finds the file damaged recovers without waiting on its own lock. `projection()` and `read_unlocked()` take the lock only when the file is damaged. Restores are announced after the lock is let go, so the journal's own catalog read can't nest.
- **Telling the person.** `GET /api/projects` carries `catalogRestore` (the newest restore, until the person dismisses it). The Projects home shows GM's line as a `role="status"` notice with × (`aria-label="Dismiss"`); × posts `POST /api/projects/catalog-restore/dismiss {id}` (person only, 403 for agents) and hides it in that tab at once. The path never goes in the notice. The first time a tab sees a restore it adds an Agent log line (source `system`) with the copy and the damaged file's path.
- **Telling agents.** `catalogRestore` leads `start_here` (and `nebula context`), with the note, source, damaged path, up to 5 names; `list_projects` / `nebula projects` carry it in full with `note`; a `project.catalogRestored` journal event (actor `system`; file names plus `folder`, since the journal cuts strings at 160 characters). Documented in docs/MCP-SETUP.md ("A damaged project list", the start_here table note, the event table) and skills/nebula/SKILL.md.
- **A restore while a run is starting.** The revision changes, so a start that read the old one is refused as out of date (409, the canvas's own line; the tab reloads) and starts nothing, never a 507; the reloaded tab's start runs.
- **Decisions not in the brief.**
  - Overlap rule (newer from the damaged file wins, equal or older never) instead of "copy always wins" or "damaged always wins".
  - A project deleted for good in the window between a commit and its copy comes back (to delete again): the damaged file can't prove the purge.
  - A project restored from Recently deleted in that window stays in Recently deleted (restoring doesn't touch its dates).
  - "Every add-back failed" gets the first sentence of form 2 alone, marked as a placeholder (GM's rule: never "No projects were missing" then; form 1 needs at least one added).
  - Form 3 is built as GM wrote it, though "your project folders" isn't what a rebuild reads (see open items).
