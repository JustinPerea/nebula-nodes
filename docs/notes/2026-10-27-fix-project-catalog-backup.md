# 2026-10-27: a damaged project catalog restores its last good copy

Branch `fix/project-catalog-backup`, cut from origin/main at c1e7338c. Justin approved the fix on 2026-10-27; GM's brief: "keep a last good copy of the catalog and restore from it, with a line saying it did."

- **The problem.** `projects/catalog.json` is read fresh on every request. A file that wouldn't parse or validate answered 507 to every project read and run start, through restarts, and the person couldn't repair it.
- **What the layout is (it changes the brief).** Every project lives whole inside catalog.json: name, dates, cover and pin, `createdBy`, pins, Updates, questions, the snapshot (nodes, edges, run history, viewport, Create draft). There are no per-project folders or files. The folders named by project id (moodboards, characters, styles) hold assets, not projects. So "re-add from disk" means the project records the damaged file (and any damaged copy) still holds. "Entries whose project data is gone get dropped" never applies: a record in the copy *is* the project's data.
- **The last good copy.** `catalog.json.bak` is written after every commit, from the bytes the commit wrote, and only when `_check` accepted that catalog (`prepare` already ran the check for the projection cache; the same check gates the copy). `catalog.json.bak.1` is rewritten from the committing catalog when it is missing or over an hour old. Both go through a private temp file, fsync, `os.replace`, then a directory fsync, after the commit's own rename and directory fsync. A failing copy write never fails the commit; the next commit writes it again. A read under the lock seeds the copy for a catalog saved before copies existed.
  - *Why two generations, not more:* each is a full copy (a catalog may be 128 MB). The second covers the newest copy being damaged too (same disk event, a sync tool); a third would add an older state that the damaged files can't add to. The older copy is written from a catalog that validated, never renamed from whatever the newer copy holds, so a damaged newer copy can't rotate into it.
  - *Cost:* every commit writes the catalog twice (autosave commits every ~600 ms). Accepted for now; see open items.
  - `prepare` now writes `version`, `activeProjectId`, `workspaceRevision`, `migratedProjectId` first, so a file cut short still says which project was open.
- **Reading a damaged catalog** (`ProjectStore._load` / `_recover` / `_restore`, `services/catalog_recovery.py`). `_load` raises `_Damaged` for not-JSON (`corrupt`), the wrong shape (`invalid`, including `TypeError` from a list where an id belongs), or a missing catalog.json while a copy exists (`missing`). A symlink, an oversize file, an I/O error and a failing params upgrade still refuse as before (they are not damage). Under the store's lock, the reader reads again (another request or process may have restored it), then:
  1. reads the copies newest first and takes the first that parses and validates;
  2. salvages each damaged file (the catalog, then any damaged copy newer than the one used): if it parses, each record on its own; if not, a scan for `"<32 hex>":{` keys decoded with `raw_decode`, validated per record (`entry_ok`: id matches, snapshot with node and edge lists, every field the listing reads, a tz-aware `deletedAt` for a trashed one). A key where a record belongs (first in its group, or right after a complete record) whose record won't decode is reported as `incomplete`;
  3. reconciles (`reconcile`): a record the copy lacks is added back (to Recently deleted when it carries `deletedAt`); a record the damaged file holds *newer* than the copy (latest of updatedAt, lastOpenedAt, deletedAt) replaces it (a commit whose copy never landed: an edit, a move to Recently deleted); an older or equal one never does (the copy is known good, the damaged file may carry the damage). Nothing the copy holds is dropped. Past `MAX_PROJECTS` or the size limit, a record is left out and reported (`limit`, `size`); if `prepare` still refuses, the copy alone comes back and every add-back is reported;
  4. the open project: the damaged file's when it says and that project came back live; none when it says one that didn't come back (the live canvas in state.json is that project's, and the next listing would overlay it onto whichever is open); otherwise the copy's;
  5. a new workspace revision (open tabs reload);
  6. keeps the damaged catalog as `catalog.json.damaged-<UTC>-<8 hex>` (a hard link, else a fsynced copy; reused if a failed attempt already kept the same file or bytes) and each damaged copy as `catalog.json.bak[.1].damaged-…`, *before* anything is written. Nebula never deletes them. A damaged older copy is taken out of use only after the commit lands;
  7. commits through the normal `prepare`/`commit_prepared` (which writes the new copy), then records the restore in `catalog-restore.json` (last 10) and announces it once the outermost lock hold lets go (`on_restore`).
  - *No good copy:* the same reconcile from an empty catalog, `kind: "rebuilt"`. When no damaged file holds a single complete project, it refuses with the existing 507 and changes nothing. Exception: catalog.json *missing* with only damaged, empty copies keeps them and starts from an empty list, as a missing catalog always did (a refusal there would never end).
  - Every step prints a `[projects]` line in the backend log.
- **Concurrency.** The store's existing `.lock` flock, now re-entrant per thread (`_locked`, a thread-local depth): a read inside a transaction that finds the file damaged recovers without waiting on its own lock. `projection()` and `read_unlocked()` take the lock only when the file is damaged. Restores are announced after the lock is let go, so the journal's own catalog read can't nest.
- **Telling the person.** `GET /api/projects` carries `catalogRestore` (the newest restore, until the person dismisses it). The Projects home shows GM's line as a `role="status"` notice with × (`aria-label="Dismiss"`); × posts `POST /api/projects/catalog-restore/dismiss {id}` (person only, 403 for agents) and hides it in that tab at once. ## Fix round 2 (review 2: M1, M2, L1-L8; GM round 3)

- **M1: the strict parse is off the hot path.** Every read decodes with `parse_constant` (NaN and the infinities refuse, at no cost). A file this process committed or already read (its signature is the projection's) skips the `parse_float` and `writable()` checks: prepare wrote it with `allow_nan=False` as UTF-8. Any other file is read strictly, and `writable()` runs only when its bytes hold a `\u` escape. The byte regex (`_SUSPECT`) is gone: it matched every real catalog (any 1e-style number), so every read was strict. Measured interleaved in one process (A/B, median of 9, load about 20-30), worktree over pre-#199: 9 MB read 868/900 ms (0.96x), autosave 1,031/1,073 (0.96x); 45 MB read 5,068/5,022 (1.01x), autosave 5,537/5,980 (0.93x). On dcaafb82 (separate runs) the parse alone was 2.2x and 2.7x pre-#199's (340/153 ms at 9 MB, 2,080/762 at 45 MB). What's left of a transaction is the deep copy, as before #199.
- **M2: a record's id comes from the record.** Salvage files a whole record under its own `id` only when it equals its key; a key that isn't an id, or differs from the record's id, makes the file not complete (`damagedReadWhole: false`) and puts the record in `misfiled`. Reconcile then decides with the copy's ids: the key's id when the copy has it and not the record's (an id-field flip: the record's `id` is fixed back), otherwise the record's own (a key flip, or a project newer than the copy); when the copy has both, neither is taken (`invalid`). A record-holding section under a damaged name ("trasi") is read as records, group unknown, and `_check` refuses such a file (it would have hidden them). A damaged `activeProjectId` in a file that parses is unknown, not "missing". **The audit** found one more place salvage trusted structure: a record cut right after another cut record (no group opener, no whole record before it) was dropped, so it went unreported and, when it was the open project, its canvas was filed nameless. Its own members now count (its `id` is its key and it has a `name`); its group is told only by its `deletedAt`, and reconcile reads an unknown group conservatively (no "came back" or "back in Recently deleted" claim). A project-id key nested in a snapshot has neither, and is still not counted. Found by the live check (B), not the review.
- **L1: a tombstone decides only against older evidence.** The newest file that mentions an id decides (each salvage's records, then its tombstones, then the copy, then the base's `purged`); a record made after the delete (`createdAt` later than the tombstone: the same id made again, as `/api/projects/recover`'s retry does) wins. A tombstone that drops a record anything held is a `keptDeleted` row.
- **L2: the loop never restores or waits for one.** `ProjectStore.hand_off_restore` (main's `_hand_off_catalog_restore`): a loop reader that finds the file damaged starts the shared worker-thread read and answers the last projection. `read_in_flight` (main's `_catalog_read_in_flight`): while that worker read of the same file runs, a loop reader doesn't parse it too. The second hook came from the measure: with only the first, a 102 MB file cut in half still held the loop 1.6 s in the parse that finds the damage. Measured (`l2_block.py`, the file cut in half, a reader 50 ms after the worker starts): without hand-off 3.4 s / 14.1 s held at 31 / 102 MB (4.7 / 16.8 under heavier load); with both hooks 0.0 / 0.0. A worker thread, or a loop reader after the off-loop read failed on the same file, reads it itself and answers its own error. Still open: a transaction (save, create) waits on the lock while another process restores. Every read still goes through `ProjectStore._read` (the full suite's pins test counts it): projection() asks it to hand off (`hand_off=True`) and catches `_HandedOff`.
- **L3.** Where hard links fail, `.bak` is written from the commit's own bytes every time (the committed catalog, zero commits behind, logged once). The base is the valid copy whose content is newest (`catalog_freshness`: the newest date in it), `.bak` on a tie, never by name or mtime.
- **L4: filing at the limit.** Decided: the canvas is never filed past the project or byte limit, and never dropped. It stays the live canvas with no project open; the listing carries `canvasNotFiled` (`{reason, from, since}`) and keeps answering; open and create refuse with the limit's 413 (nothing can replace the canvas); the next listing with room files it. A filing whose commit still hits the limit is undone the same way. Why: every listing failing (the review's finding) locks the person out of freeing room; filing past the limit breaks the limit everything else relies on; dropping or overwriting the canvas loses work. This is the only option that loses nothing and keeps the app usable.
- **L5.** Every filing (listing, create, open, delete) goes through `_note_canvas_settled`: journaled as `project.canvasFiled` / `project.canvasNotFiled` (new EVENT_KINDS) and noted on the restore it belongs to only (`_restore_of`: that restore opened nothing, has no filing yet, and its missing open project is this canvas's owner), never an older one.
- **L6.** "Open Recently deleted" clears its request once used (`onOpened`), so a later list change can't reopen it; the button shows only while Recently deleted holds something. An agent's delete doesn't move focus (live-checked).
- **L7.** A kept damaged file is aged by the UTC time in its name (`_kept_at`, mtime only for names without one); the restore record's `setAside` names carry the time too.

The base choice also needs the commit number: `.bak.1` wins only when it is newer by dates and, when both carry one, by `commitSeq`. A whole record that loses to an older copy by dates is now reported (`reverted`, `by: "dates"`); its version stays in the kept damaged file (tested: "Alpha v2 (newer, clock corrected)" is still in it). The clock case can lose a version outright only for copies written before `commitSeq` existed (a legacy `.bak.1` whose ahead-dates have since passed); with numbered commits both signals are required.
