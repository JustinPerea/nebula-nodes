# 2026-10-21 — The open canvas drops wires the backend removed

Branch `fix/canvas-drops-agent-unwires`, based on PR #146's head (`fix/replicate-video-audio-ports`, a9b5bcd9), whose graphSync merge work (`keptOutputs`, `universalPortsHold`) is kept as it was.

- **The bug.** Found in the Q82 lane's live check: after an agent's undo the backend had no wires, but the person's canvas still drew e1 (n2 -> n1) until a reload. The graphSync merge in `frontend/src/store/graphStore.ts` kept every wire a sync didn't have as long as both its nodes were still there, so it couldn't tell a wire the backend had already confirmed from the person's own wire still on its way. Every agent unwire stayed on the canvas: MCP `disconnect` / `edit_canvas` unwire, `nebula disconnect`, `nebula apply --unwire`, an agent's `undo_canvas_edit` / `nebula undo`, a proposal accept that removes wires, the backend's own pruning when a node is re-typed.
- **Worse than a stale picture (checked live).** The canvas autosave writes the canvas's wires into the saved project. The backend counts a wire it doesn't have as one the tab drew itself, so it kept it. Before the fix, the isolated check's saved project ended with 2 wires the backend no longer had, the removed `e1` among them. (A save holding two wires with the same id is refused, so the base run's one 400 was most likely the canvas holding two wires both called `e1`; see Surprises.) That is the agent's removal silently undone in the saved project. The agent's unwire also never became an undo step, because the canvas didn't change, so the "Claude changed the canvas" notice never showed.
- **Justin's answer.** There was no question for Justin in this lane. The bug came from the Q82 lane's live check, and the target is the coordinator's brief: "the canvas shows exactly the backend's wires between backend nodes, plus only the person's own wires that are still on their way."
- **The rule (the fix).** A wire between two backend nodes (n1, n2, ...) belongs to the backend. A graphSync without it takes it off the canvas, and a sync with it draws it. The one exception is a wire write this tab has sent and not yet seen settle: a connect, a delete, or the wires an undo/redo restore puts back or takes off. For those, a sync that disagrees leaves the wire as the person has it. "Settled" means the backend answered and a sync agreed. The agreement sticks until this tab's next write on that wire: once a sync has agreed, the backend has the write, so a later sync that disagrees (an agent's unwire before the HTTP answer is back) is newer and wins. If the answer came first, the write settles at the next sync even when that sync disagrees: the backend sends its sync before its HTTP answer, so that sync is the write's own. This follows the precedent of the layout-write tracking (`layoutWritesInFlight`). Code: `wireWrites`, `sendWire`, `holdWire` and `heldWires` next to it; the merge uses `held`.
- **Every path that writes wires now goes through it:** onConnect (the wires it replaces, then the connect), onEdgesChange deletes, Cinema shot-port deletes (removeShot, updateScene), and `sendRestore` (undo/redo of the person's own steps and of foreign edits). Paste, duplicate and the Edit-node spawn make UUID nodes, so their wires stay frontend-only and keep today's behaviour. A dynamic node (OpenRouter, Replicate and the like) is drawn under a UUID until its create answers; wires the person drew to it in that window are now sent once it has its backend id (they never were before). The node-and-connect popup, the Create cluster and proposal accept add the backend's own nodes and wire (e-id) from their HTTP answer; they need no hold, but the answer now adds only what no sync has carried since the request went out (`watchGraphSyncs`), so a late answer can't bring back a node or wire an agent removed meanwhile.
- **Wires on nodes only this tab has** (a UUID end) keep today's behaviour: they stay while both ends do. The backend never sees them.
- **A refused write now says so.** Before, a connect the backend refused (409 while an approved run holds those nodes, say) left a ghost wire with no message. Now the wire comes off and the notice reads "Couldn't connect that wire. <reason>". A refused delete puts the wire back ("Couldn't remove that wire. <reason>"). A write that got no answer at all leaves it to the next sync.
- **Redundant rule removed.** The Cinema motion clause ("a confirmed server-owned motion wire omitted by newer canonical state was removed") was a special case of the new rule, so it is gone. Its test now draws the "optimistic" wire through a real onConnect with the connect in flight, the case it stands for.
- **Undo.** An agent's unwire is now one foreign undo step (before the fix it was none, because nothing changed on the canvas). The person's Undo puts the wire back, and the restore's wire is held until it lands, so a run's sync arriving meanwhile doesn't make it blink.
- **Nodes (point 5).** Already right: cli-id nodes come only from the sync, so a node an agent deleted (or an undo removed) leaves at once with its wires. Node deletes wait for the backend before leaving the canvas, and node creates add the node only after the answer, so there is no optimistic cli node to hold. A test pins the delete. Not changed: if a create's HTTP answer beat its own sync and an older sync landed in between, the new node would flicker. The backend sends the sync first, so this hasn't been seen.
- **Agents.** Nothing changes for agents, except that the person now sees their unwires (and can undo them as one step). No new tool, MCP INSTRUCTIONS unchanged. `docs/MCP-SETUP.md` ("The person can undo any agent edit") now lists `disconnect` and says the canvas draws exactly the backend's wires, with no reload.
- **Tradeoffs.** No graph revision numbers exist on graphSync, so "a sync that agrees, or one more after the answer" is a heuristic. It holds because the backend exports and broadcasts each sync before it answers the request, and the socket keeps order. A write whose answer is lost is dropped from tracking, and the next sync decides.
