# 2026-10-21 — Look up a node type by its name

Branch `fix/node-lookup-by-name` from origin/main 55bfee41 (#141). Backend, docs and the turn counter; no frontend file changed.

- **Why.** In the PR26 rerun after PR26b (`docs/agent-runs/2026-10-20-pr26-first-turn-measurement.md`, merged as #140), three of the four usage errors left were the same call: `nebula info moodboard`. The node's id is `nebula-moodboard` and its name is "Moodboard"; the error listed the id and the agent used it the next turn. That write-up names this fix as Next, toward PR26's approved target of no usage error. Justin gave no separate answer on this change; it is the next step of work he already approved (PR26/PR26b), and it spends nothing.
- **What changed: lookups.** `nebula info` (and its alias `nebula describe`) and MCP `describe_node(definition_id=...)` take a node type's exact display name, ignoring case and outer spaces, when exactly one node type has it. They answer as for the id and say which id they used in one line: `nebula info` prints "moodboard is the Moodboard node: nebula-moodboard" right after the start line; `describe_node`'s answer starts with a `lookup` field holding the same line. An exact id always wins and gets no line. A name two node types share is refused, listing both ids first ("Node 'moodboard' not found: 2 node types are named Moodboard. Did you mean: ..." / "No node type 'Moodboard': 2 node types are named Moodboard: a, b. Use one of those ids."). Unknown text keeps today's error; any exact-name match goes first in its list. The shared code is `backend/services/node_lookup.py`; `_suggest_node_ids` in main.py now uses it.
- **What changed: writes stay strict.** `edit_canvas`, `propose_change`, `nebula apply`/`propose` (also `--file`), imports and clusters (all through `_validated_ingress_node`), `nebula create` (`POST /api/graph/node`), `/api/graph/node-and-connect` and `nebula quick` (`/api/quick`) take ids only. Given a name they refuse with the id first: "unknown node definition 'moodboard': did you mean nebula-moodboard (Moodboard)?". With no name match they add close ids when there are some ("did you mean krea-moodboard or nebula-moodboard?"), else the plain line as before. Reason: these store and bill by id, and display names do change (we rename nodes to the provider's spelling) or could come to be shared, so a saved command or script that added "Moodboard" could later mean another node or stop working. A read can't do harm that way; a write can. The refusal costs one turn and names the fix.
- **Per place, as decided.** `nebula info`/`describe`, `describe_node`: resolve a unique name. `find_nodes`, `nebula nodes`/`find`: unchanged (a search; "moodboard" already finds it). `edit_canvas`, `propose_change`, `nebula apply`/`propose`/`create`/`quick`, imports: strict, error names the match. Style `modelId` (`style_create`/`style_update`, `nebula style new/set --model`): strict, error names the match (added in review, below). `run_nodes`/`nebula run`: unchanged, they take canvas node ids (n4), not types. Canvas undo restore (`POST /api/graph/restore`, the person's path): unchanged message. `start_here`/`nebula context`: untouched; no test of theirs depends on the error text.
- **Bug found on the way.** `nebula create <anything>` stored a node of any type it was given: `POST /api/graph/node` (and node-and-connect) never checked the registry, so `nebula create moodboard` added a node of type "moodboard" to the canvas and then failed on its lookup. `nebula quick moodboard` went on to try a run ("No handler registered for 'moodboard'"). Both now refuse up front. The canvas uses the same route; its node list is the registry (308 of 308 ids match, checked by bundling `NODE_DEFINITIONS`), so it is unaffected. Four `test_cli_api.py` tests built graphs from made-up types (`node-a`, `node-b`); they now use `text-input` and `preview`, and a new test pins the refusal.
- **Decisions not in the spec.** A case-insensitive id counts as naming that node too ("Nebula-Moodboard" resolves, with its line), and it counts toward "two nodes share it": if one node's name were another's id, the different-case form is refused rather than guessed. Outer spaces around an exact id are dropped silently. Both routes take a slash now (`{...:path}`), because two Jev nodes have one in their names ("Jev Decide (judge / classify / yes-no)"); the CLI client URL-encodes what it sends. The note keeps to the spec's example; it doesn't add "use the id to add it", since the write refusal says that if needed.
- **Counter.** `scripts/count_agent_turns.py` already classed `nebula info`'s "Node 'x' not found" as a usage error, and still does with the shared-name wording. It did not class two refusals that are usage errors just the same: `describe_node`'s "No node type 'x'" and the write paths' "unknown node definition 'x'". Both patterns are added, with tests. A resolved lookup stays a `lookup`. The raw transcripts aren't in the repo, so I couldn't recount past runs; the write-up's account of them mentions neither refusal, so their counts likely stand, and a recount at the next rerun would confirm it.
- **Tradeoffs.** An agent that writes `+mb=moodboard` in `nebula apply` still loses a turn; resolving it there would save that turn at the cost of display names becoming part of the write contract. `nebula info --help` keeps its `node_id` metavar so usage lines in other tests and docs stay the same; the help text says it takes a name.
