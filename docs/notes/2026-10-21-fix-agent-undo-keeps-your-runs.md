# 2026-10-21 — An agent's undo keeps a node someone else ran

Branch `fix/agent-undo-keeps-your-runs` from origin/main a330dc64 (after #118, the agent's canvas undo, and #139).

- **What changed and why.** Justin's answer to Q82: "a) Your run counts as changed since: the agent's undo leaves that node and says why. The agent's own runs don't count, so it can still undo its own experiments." Before, an agent undoing an edit that added a node removed that node even after the person had run it: the paid result stayed on disk and the person's Cmd+Z could bring it back, but the node and its output left the canvas. Now a run counts as a change. When the undo comes, every node the edit touched (added, changed, renamed, moved, or that one of its wires goes into) is checked for runs started after the edit. A node someone else ran stays whole and is reported as one `skipped` item: `{nodeId, part: "node", reason: "ran since", left: [...], ranBy: [{kind, name}], message: "n3 ran since (run by the person), so it stays"}`. The rest of the edit is undone as before.
- **Who counts.** The person, another agent ("run by Codex"), and a client that didn't name itself ("run by an unnamed client") all count. Only runs the undoing agent started are exempt, matched by its agent id (the same id that owns the undo token). Justin's option c ("any run counts, the agent's own too") was rejected only for the agent's own runs; another agent's paid result isn't this agent's experiment.
- **What "leaves that node" means.** The node isn't removed, its params, name and position aren't put back, and no wire into it is taken away or put back (those inputs made its result). The spec listed params, name and input wires; I also leave the position, so the rule is one sentence ("everything on that node stays") and the skip item reads true. Wires out of it follow the old rules: a wire from it to a node the undo removes goes with that node, and a wire the edit added from it into a node that didn't run is unwired.
- **Since when.** A run counts if it was asked for after the edit committed. The undo book has its own clock that only goes up (`CanvasUndoBook.mark`): the edit takes a mark right after it commits (`_canvas_undo_after`), each run takes one when it is asked for (`_note_run`, at every run entry: `/api/execute`, `/api/execute-node`, `/api/cinema/generate-shot`, `/api/graph/run`), and a node's `run.started` (ExecutingEvent) is recorded under its run's mark. So a run asked for before the edit doesn't count even if the engine reaches the node after. A run still going when the undo comes counts for every node it set out to run (`_note_run_nodes`), even ones the engine hasn't reached yet (the safe choice). Once a run ends, only nodes it actually started count, so a node a gate skipped doesn't.
- **One clear skip.** A node that changed and also ran is one item ("ran since"), not a "changed since" plus a "ran since". "ran since" wins because it says why the node matters.
- **Reply shape.** Backward compatible: `skipped` items keep `nodeId`, `part`, `reason`, `message`; `ranBy` and `left` are new. The undone reply gains `message` ("Undone: removed 1. Left as is: n2 ran since (run by the person), so it stays."), and the all-skipped reply's message now says "changed or run since" (after review it only promises a retry when a changed part could be put back; see Review). The edit's `undo.summary` says "Anything changed or run since is left as it is", and `nebula apply` prints "(for 60 minutes; parts changed or run since stay)".
- **Not changed.** The person's own Cmd+Z of an agent step: it goes through `/api/graph/restore` from the canvas, not `plan_undo`.
- **Agent support.** MCP `undo_canvas_edit` docstring and the INSTRUCTIONS line that names it, `nebula undo` help and `nebula apply` help text, `docs/MCP-SETUP.md` (tool list and "Undoing your own edit"), `skills/nebula/SKILL.md`. The CLI prints each skip's message under "Left as is:"; after review its first line comes from the same helpers as the server reply (see Review).
- **Tradeoffs.** Run tracking is memory-only and bounded (last 256 runs, 2000 project+node entries), like the rest of the undo book; a restart forgets it, but a restart also forgets every undo token. Clearing or loading a project drops its node-run entries along with its tokens, since node ids start again.
