## 2026-10-20 — Commons for agents now: reads, comment threads, curation as proposals (U13, Q63 b)

Justin's Q63 b ("Now", changed from waiting for the GM Commons trial) and audit U13, on the propose path in the entry below. Built on origin/main 0e6e645d in the same worktree. No paid call, no hosted Commons service, no brand data: tests and the live check use a local Commons store seeded with synthetic images.

- **What.**
  - *MCP reads* (`mcp_server.py`, grouped after `commons_borrow`): `commons_collections(brand)`, `commons_status()`, `commons_borrowings(asset, brand)`, `commons_concentration(brand)` (read-only) and `commons_fidelity(borrowing_id, brand)` (not read-only: it saves the check on the borrowing; idempotent). Each calls the route the Commons UI uses through `_commons_call`. `commons_comment` takes `membership_id`; `propose_asset_change` takes `brand`. All in `NEBULA_MCP_TOOLS`, INSTRUCTIONS, `commons/skill.md`, MCP-SETUP.
  - *Curation as proposals*: asset proposals take kind `commons` (`services/asset_proposals.py`); `services/commons_proposals.py` (new) parses one edit or `{"edits": [...]}` (≤8, one reference): `correction` (the fields the Commons detail lets the person correct, `summary` = `summary.value`), `region` (new, or label/note/status confirmed|deleted/box of one of the reference's), `membership` (role, why, `accept: true`). It checks scope as `commons_get` does (`routes/commons._asset_access`), drops parts already so (409 when nothing is left), records `before`, finds misfits, and applies each edit by calling the route function itself (`add_correction`, `add_region`, `patch_region`, `patch_membership`, `accept_membership`) as the person. main: `_commons_proposal_target/_misfit/_apply_commons_proposal`, and `_asset_proposal_person_view` for the browser-only messages.
  - *Journal*: `routes/commons.py` gets `curation_listeners`, called after each curation write; main journals `commons.corrected` / `commons.region` / `commons.membership` (ids and field names only, never Commons text) with the actor, "(accepted from <agent>)" when an accepted proposal made it, and sweeps the proposals on that reference from the route's worker thread. `get_proposal(wait)` wakes on `commons` events too.
  - *Concentration*: brand-scoped for every agent (it was only for workspace-bound ones; an outside client saw every brand's shares), with a `brand` query param.
  - *CLI*: `nebula commons collections|borrowings|fidelity|concentration|propose`, `comment --membership`; the formatter prints a commons proposal's edits and outcome.
  - *UI*: the strip renders a commons proposal's edits (field, now struck, proposed, reason; region and collection named from the detail) with **Don't** / **Apply** (**Apply all**); `CommonsDetail` shows it and reads the reference again when one is accepted (any tab); `CommonsProposalsLine` above the grid names each reference waiting with **Review**; tiles get a "proposal" badge.
- **Decisions not in the spec.**
  - *One kind, keyed on the reference.* Regions and memberships are named inside the edit, so every curation proposal shows on one reference's detail and one proposal can carry a reviewer's several edits (the 3-per-agent cap would otherwise stop at three fields). Accept is all of them; if an edit's target vanishes between the check and the write, earlier edits stay made and the proposal closes as invalidated (documented).
  - *`before` is person-only.* The reference's current values are Commons text (model- or person-written); the REST/MCP view carries only the agent's own edits, and `before` rides on `assetProposalOpened`/`Sync` (`person_values`).
  - *An accepted correction is the person's* (actor `human:justin`), so it outranks the model as the person's own does, and its reason (the agent's) reaches the reader's few-shot block like any person's reason. The person sees the reason in the strip before accepting.
  - *Parts already so are dropped* rather than refused, so "role neutral (already) + new why" proposes only the why.
  - *No proposal to clear a why or a note*: agent text is one line, 1..N characters.
  - *Evaluation and review stay human-only, unchanged* (no tool, no proposal); the answer changed only the timing. Said in MCP-SETUP, the skill and commons-integration.

- **Adversarial review (same day), fixed with tests that failed first.**
  - *Brand fence on proposals.* `GET /api/asset-proposals` and `GET`/`DELETE /api/canvas/proposals/{pa_...}` answered any caller, so a brand-bound in-app session could read another brand's agent's proposed edits and note about a reference the Commons hides from it. A commons proposal now records the scope it was proposed in (`before.scope`: the effective brand and the workspace, never sent anywhere) and `_commons_proposal_visible` lets through the person, the proposing session (same identity and workspace, so it still reads an invalidated outcome after the reference went) and callers who see the reference in that brand via `_asset_access`; others get 404 or an empty list. Outside agents may name any brand, as in the Commons itself, so the fence bites on Nebula-issued brand sessions.
  - *Journal and closed broadcast.* Every agent on the canvas reads `proposal.*` events and `assetProposalClosed`; for kind commons they no longer carry the agent's note or the person's reason (the proposer reads both with `get_proposal`).
  - *Repeated edits.* Two edits of the same field, keyword, region or membership in one proposal are refused (422): each was checked against the reference as it is now, so the second blurred or undid the first.
  - *Deleted regions.* An agent could propose edits (even "confirmed", i.e. restoring) on a region the person deleted, which `commons_get` no longer shows it: now 404.
  - *Empty listings over MCP.* `commons_collections` and `commons_borrowings` returned bare lists, which FastMCP sends as one text block per row and as no content at all when empty; they now return `{"collections": [...]}` / `{"borrowings": [...]}` (the CLI twins keep printing the route's list).
  - *Left open.* A proposed new region shows only its label in the strip, not where its box sits on the image; the person accepts a box they can't see. Drawing proposed boxes on the detail image needs a design pass.
- **Merged with #127.** After #127, the "Off the canvas" line is shorter (113 characters, without the `set_project_cover` aside, which its docstring and `propose_asset_change`'s carry) so the three batch-2 lanes fit the 3,000-character budget together. #127 moved the Send notes switch into the shared `boardFields` block, so the proposal strip now sits there and shows in both the List and the Board panel.

## 2026-10-20 — Proposals outside the canvas: project covers and Send notes (U16, Q60 a)

Justin's Q60 a: agents set a project's cover directly while the person hasn't pinned one; a cover the person pinned changes only through a proposal they accept. The same path (audit U16) makes the moodboard's "propose it" for Send notes real. Built on origin/main 0e6e645d. No paid call.

- **What.**
  - *`services/asset_proposals.py`* (new): `AssetProposalBook(ProposalBook)`, so the life cycle, caps, TTL and accept key are the canvas proposals' own; ids start `pa_`. `parse_change` takes `{kind, id, change, note}`; kinds `project` (`{"cover": url | "" }`) and `moodboard` (`{"sendNotes": true}`); `character` and `style` are refused by name.
  - *`main.py`*: `_set_project_cover` is the one cover write (the person's pin, an agent's direct set, an accepted proposal). It reads the open project's images from the live canvas, records `coverBy`, returns `previous`, journals `project.cover`, broadcasts `projectsChanged` and sweeps open proposals. The routes `POST/GET /api/asset-proposals`, `POST /api/asset-proposals/{id}/accept|reject`; `GET`/`DELETE /api/canvas/proposals/{id}` fall back to asset proposals, so `get_proposal`, `withdraw_proposal` and `nebula proposal` need no new tool. Accept applies through `_set_project_cover` and `update_moodboard` (the same code the UI's `PUT`s use), with the tab header removed so the person's own tab hears the change.
  - *MCP*: `list_project_covers`, `set_project_cover`, `propose_asset_change`, all through `_tool(...)`, listed in `NEBULA_MCP_TOOLS`, in INSTRUCTIONS and MCP-SETUP.
  - *UI*: `AssetProposalStrip` on the project's card (lazy, through `ProposalsFor`, so the entry chunk grows 4.3 KB, not 6.8) and under Moodboard Studio's Send notes switch. Keys arrive only over the person's socket (`assetProposalOpened` / `Sync`), as on the canvas. The card's title and the cover picker say "set by <agent> (agent)".
- **Decisions not in the spec.**
  - *Who owns a cover.* `coverBy` (`actor_record`) is saved with the pin. A pin saved before today has none and counts as the person's, the safe reading. An accepted proposal saves the person as owner, so the next agent change asks again.
  - *Anyone not the person* (an agent, a script with no name) may set or reset an unpinned cover. Only a person-owned pin is guarded, with the person gate's own codes and a hint naming `propose_asset_change`.
  - *Agents may propose even when they could set it*, e.g. to ask first; refused only when the change is already so (409).
  - *Covers by url only*, not by number: `list_project_covers`' order follows the newest image and shifts between the proposal and the decision.
  - *Invalidation.* A proposal records the target as proposed (the cover and its owner, notes off). Any read, decision or cover change sweeps; the strip relists when its project or board changes. Accept checks once more against the live canvas (a test caught the export-less check invalidating a cover only on the open canvas).
  - *Board cover vs project cover.* The board-cover lane (read only, `nebula_nodes-board-cover`) sets a board's `coverImageId` directly, journaled `board.cover` with `previous`; a board has no person pin, so no proposal. A project cover takes the same shape for an agent (a `cover` value, `previous` to undo, a journal event), and differs only in having an owner.
