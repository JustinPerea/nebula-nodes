## Round 2 (2026-10-26): review 1's findings, as the coordinator decided them

- **Why.** Review 1 found that a push could lift the gate on a change turn still running, so that turn could edit. The fact behind the fix comes from Claude Code's channels reference: pushes that arrive while Claude is busy are "delivered together on the next turn", so a running turn never sees a push sent during it. Sending a push into a gated window therefore never reached that turn; it only freed it. The decisions built here, in order:
  - *H1 + H2: "no push (pins included) ever closes or shortens a gate window. An ungated push goes only once the window has ended on its own terms (60 s minimum, then 20 s with no call, nothing in flight); next_check waits for the window's end."* `ChannelState._window_end` computes the end: inf while a call runs, else max(push + 60 s, last call + 20 s). `_window_open` reads it. `_ready` lets a pin, an accept or its own run's end go only when no window is open. `take_push` takes pins only then, and it refuses an ungated batch while a window is open before it takes anything off the queue, so the rule holds even if `_ready` changes. An ungated push no longer touches `_window_at`. `next_check` sleeps until the end plus 1 ms.
  - *H3: "keep a set of runs this process started (run_nodes results + its own accepted proposals' runs); get_run may refresh or drop only runs in that set, never add."* That set is `own_runs`, an insertion-ordered set capped at 256. `tool_finished` returns early when `get_run` reads a run outside it.
  - *M1: keep the timing.* The window is still timed from when the push is sent. MCP-SETUP.md's gaps now name both directions: a typed turn can be refused, and a change turn delivered late (Claude busy elsewhere for more than a minute, or a pause of more than 20 s after the first minute) can go ungated.
  - *M2 (a): the channel stops cancelling the HTTP request.* The listener now runs three kinds of task: the events long-poll (always `wait=25`), one watcher per followed run, and a pusher that sleeps on a "changed" event (new events, a run end, any tool call finishing) or until `next_check`. Nothing but the end of listening cancels a poll. `_fetch_events_or_wake` and its `_wake` are gone.

Connected clients see no change, and a wait of 0 doesn't start a disconnect watch.

## Round 3 (2026-10-26): review 2's findings, as the coordinator decided them

Branch `feat/mcp-channel-experiment` at c4332444, on main through #194.

- **Why.** Review 2 found one medium and three low findings, with no gate escape and no change to spend or approvals. The decisions built here:
  - *M1: "while a pin waits, hold gated pushes (in _ready return nothing for "change" and gated "proposal" when pins are waiting; next_check counts only the pin's ready time). The pin batch then carries the edits and decisions at the window's end as an ungated pin wake (Q51 a: a batch holding a pin counts as a pin wake)."* Before, a pin that came during a gated window waited for the window's end, but a gated push could still go meanwhile whenever the agent was quiet, and each one started a new window. In the review's probe the person kept editing every 5 s, the pin sat behind 17 gated pushes and first went 650 s later. Now `_ready` lets a gated decision or a change go only when no pin waits, and `next_check` leaves their times out while one does. The pin goes when the window ends (at least 60 s after the last gated push), as a pin wake that isn't gated, with the edits and the rejection that came meanwhile. Accepts and its own run ends were already held by the window, so they are unchanged.
  - *L1: "_apply_asset_proposal passes proposalId into _journal_board_change; the channel skips board.* events carrying a proposalId that is its own."* `update_moodboard` is now a thin route over `_update_moodboard(..., proposal_id=None)`, and only `_apply_asset_proposal` passes one, so no request can set it (a PUT body that tries is a 422: `MoodboardUpdate` forbids extra fields; `/edits` builds `data` from fixed keys). `_journal_board_change` is the only writer of `board.*` events, so every board write an accept makes carries the mark. The channel drops a `board.*` event whose `data.proposalId` is one of its own proposals (`_from_own_proposal`). The other writes an asset accept journals, `project.cover` and `commons.*`, aren't edits the channel reads at all (a pin test now says so).
  - *L2: "track its ids (decision pushes like a canvas proposal's: accept ungated, reject/expire/invalidate gated) and allow propose_asset_change (and withdraw/get for asset proposals, if they exist) in a gated turn."* `tool_finished` now records `propose_asset_change` ids as it does `propose_change` ids. `get_proposal` and `withdraw_proposal` already read and withdraw asset proposals (`pa_...`) and were already allowed, so only `propose_asset_change` joined `CHANGE_TURN_TOOLS`. - **Facts it rests on**, read from Claude Code's pages on 2026-10-20 (code.claude.com/docs/en/channels, /channels-reference, /mcp, /permissions) and checked live on 2.1.304: the server declares `capabilities.experimental['claude/channel'] = {}`; a push is `notifications/claude/channel` `{content, meta}` and arrives as `<channel source="<server name>" k="v">`; meta keys must be identifiers (others are dropped silently); no acknowledgement, and an unregistered server's pushes vanish; several pushes during a busy turn arrive together; the flag is `--dangerously-load-development-channels server:<name>`, interactive only (ignored under `-p` and the Agent SDK); `channelsEnabled` blocks it on Team/Enterprise until an Owner turns it on; server instructions are cut at 4,096 characters; a server that negotiates revision 2026-07-28 isn't registered on the v2 runtime.
- **Two things the SDK (mcp 1.27.0) doesn't offer.** FastMCP's runner can't declare an experimental capability (`run_stdio_async` calls `create_initialization_options()` bare), so `serve_channel` (`backend/mcp_server.py`) runs the low-level server itself with `experimental_capabilities={"claude/channel": {}}` and the channel paragraph in front of the instructions (a copy of the options, so nothing global changes). `ServerNotification` is a closed union, so the push writes a raw `JSONRPCNotification` to the same write stream the session uses (what `send_notification` does after its typing). The session object is private to `Server.run`, so a tap on the read stream catches `initialize` (the client's name) and `notifications/initialized` (nothing is pushed before it).
- **Without the flag nothing changes.** `mcp.run()` is still the entry point. Every tool goes through one `_through_channel` call that is a plain `await` when `_channel` is None; the two `async def` tools are now wrapped too (with `functools.wraps`). Checked by dumping `initialize` and `tools/list` from a real stdio process before and after: byte-identical (68,939 bytes). With `--channel`, tools/list is the same and only the capability and instructions differ.
- **Design changes from the researched design, and why.**
  - *The listener's HTTP is async (`httpx.AsyncClient`), not `_offload(..., waits=True)`.* A worker thread can't be cancelled, so a 25 s long-poll on one held shutdown (and Reconnect) for up to 35 s; a mutation run with the threaded poll made three tests fail and the file take 78 s instead of 5. Async I/O on the loop never blocks it and stops at once. Only `_current_url` (NEBULA_URL_FILE's 3 s probe) still goes through `_offload`.
  - *Own events: `self=0`, not `self=1` plus local filtering.* The listener long-polls under the tools' own `X-Nebula-Agent` name and token, so the backend's own identity rule (`identify`, `matches`) leaves this agent's events out. Matching ids locally would have needed the agent's id, which the server can't compute for a verified token.
  - *Run ends come from `GET /api/graph/runs/{id}?wait=25`, not the journal.* `run.finished` is per node, so "the run ended" isn't an event, and with `self=0` the agent's own run events are left out anyway. One async watcher per tracked run; the push carries only status, node count and error count.
  - *A change push also waits while a Nebula call is in flight* (not only 20 s after the last one): a running call means a turn is under way, and gating it would refuse the person's own request.
  - *Accepted-proposal nodes are recognised by the " (accepted from X)" note every cluster event's summary carries, and by `idMap` within the same answer only* (node ids restart with a new canvas).
- **Q42 a, the experiment's choice: a gate in this process.** A change push opens a window (at least 60 s, then until 20 s without a Nebula call). Inside it only `CHANGE_TURN_TOOLS` run; everything else (and any tool added later) raises with "propose it instead". A pin push closes the window. Proposal and run wakes act like any turn. Not covered: the `nebula` CLI (told in the instructions only), and the person's own typed turn inside the window, which the live check hit (below). The backend gate keyed on identity (option 3) or a Claude Code `UserPromptSubmit` hook (option 4) would close those.
- **Q41 a limits** (`mcp_channel.Limits`, env overrides for tests only): 20 pushes in a rolling hour, 30 s between push starts, nothing dropped (held events go with the next push, `held="N"`; past 100 pending only a count), auto-off after 2 h with no person event (selections and moves count), a one-time `channelNote` on the next dict result, and a "wrap up" note 5 minutes into a change turn. No model is involved anywhere in deciding what to push (Justin's Q41 note about Haiku/Luna or algorithmic tracking: it is all algorithmic here; only the woken turn uses the session's model).
- **Redaction.** A push is built only from the `/api/canvas/events` answer the tool already gets (summaries, never `data.values`; pin text; a proposal's note and the person's reason) and the run status. `clean_text` normalises, strips hidden characters and replaces `< > "`. Meta values are ids or numbers.
