## Earlier entry: 2026-10-20 — `nebula-mcp --channel`: Claude Code channels, as an experiment (plan v2.7 Q43 b)

Branch `feat/mcp-channel-experiment`, on `fix/mcp-tools-nonblocking` (7cb55852). Justin approved building it on 2026-10-20 (Q43 b); Q39-Q42 are his answers of the same day (Q40 c: any change after the quiet time). This does not start §5.11.

- **Facts it rests on**, read from Claude Code's pages on 2026-10-20 (code.claude.com/docs/en/channels, /channels-reference, /mcp, /permissions) and checked live on 2.1.304: the server declares `capabilities.experimental['claude/channel'] = {}`; a push is `notifications/claude/channel` `{content, meta}` and arrives as `<channel source="<server name>" k="v">`; meta keys must be identifiers (others are dropped silently); no acknowledgement, and an unregistered server's pushes vanish; several pushes during a busy turn arrive together; the flag is `--dangerously-load-development-channels server:<name>`, interactive only (ignored under `-p` and the Agent SDK); `channelsEnabled` blocks it on Team/Enterprise until an Owner turns it on; server instructions are cut at 4,096 characters; a server that negotiates revision 2026-07-28 isn't registered on the v2 runtime.
- **Two things the SDK (mcp 1.27.0) doesn't offer.** FastMCP's runner can't declare an experimental capability (`run_stdio_async` calls `create_initialization_options()` bare), so `serve_channel` (`backend/mcp_server.py`) runs the low-level server itself with `experimental_capabilities={"claude/channel": {}}` and the channel paragraph in front of the instructions (a copy of the options, so nothing global changes). `ServerNotification` is a closed union, so the push writes a raw `JSONRPCNotification` to the same write stream the session uses (what `send_notification` does after its typing). The session object is private to `Server.run`, so a tap on the read stream catches `initialize` (the client's name) and `notifications/initialized` (nothing is pushed before it).
- **Without the flag nothing changes.** `mcp.run()` is still the entry point. Every tool goes through one `_through_channel` call that is a plain `await` when `_channel` is None; the two `async def` tools are now wrapped too (with `functools.wraps`). Checked by dumping `initialize` and `tools/list` from a real stdio process before and after: byte-identical (68,939 bytes). With `--channel`, tools/list is the same and only the capability and instructions differ.
- **Design changes from the researched design, and why.**
  - *The listener's HTTP is async (`httpx.AsyncClient`), not `_offload(..., waits=True)`.* A worker thread can't be cancelled, so a 25 s long-poll on one held shutdown (and Reconnect) for up to 35 s; a mutation run with the threaded poll made three tests fail and the file take 78 s instead of 5. Async I/O on the loop never blocks it and stops at once. Only `_current_url` (NEBULA_URL_FILE's 3 s probe) still goes through `_offload`.
  - *Own events: `self=0`, not `self=1` plus local filtering.* The listener long-polls under the tools' own `X-Nebula-Agent` name and token, so the backend's own identity rule (`identify`, `matches`) leaves this agent's events out. Matching ids locally would have needed the agent's id, which the server can't compute for a verified token.
  - *Run ends come from `GET /api/graph/runs/{id}?wait=25`, not the journal.* `run.finished` is per node, so "the run ended" isn't an event, and with `self=0` the agent's own run events are left out anyway. One async watcher per tracked run; the push carries only status, node count and error count.
  - *A change push also waits while a Nebula call is in flight* (not only 20 s after the last one): a running call means a turn is under way, and gating it would refuse the person's own request.
  - *Accepted-proposal nodes are recognised by the " (accepted from X)" note every cluster event's summary carries, and by `idMap` within the same answer only* (node ids restart with a new canvas).
- **Q42 a, the experiment's choice: a gate in this process.** A change push opens a window (at least 60 s, then until 20 s without a Nebula call). Inside it only `CHANGE_TURN_TOOLS` run; everything else (and any tool added later) raises with "propose it instead". A pin push closes the window. Proposal and run wakes act like any turn. Not covered: the `nebula` CLI (told in the instructions only), and the person's own typed turn inside the window, which the live check hit (below). The backend gate keyed on identity (option 3) or a Claude Code `UserPromptSubmit` hook (option 4) would close those.
- **Q41 a limits** (`mcp_channel.Limits`, env overrides for tests only): 20 pushes in a rolling hour, 30 s between push starts, nothing dropped (held events go with the next push, `held="N"`; past 100 pending only a count), auto-off after 2 h with no person event (selections and moves count), a one-time `channelNote` on the next dict result, and a "wrap up" note 5 minutes into a change turn. No model is involved anywhere in deciding what to push (Justin's Q41 note about Haiku/Luna or algorithmic tracking: it is all algorithmic here; only the woken turn uses the session's model).
- **Redaction.** A push is built only from the `/api/canvas/events` answer the tool already gets (summaries, never `data.values`; pin text; a proposal's note and the person's reason) and the run status. `clean_text` normalises, strips hidden characters and replaces `< > "`. Meta values are ids or numbers.

- **Adversarial review, 2026-10-20 (fixed, each with a test that failed first).**
  - *A wait outlasted the gate.* The change turn's window closed 20 s after the last call even while a call was still running, so in a change turn `propose_change` then `get_proposal(wait_seconds=120)` (what its docs say to do) closed the window at the first check during the wait (a parallel look, a subagent), and the turn could then edit after a rejection. A call in flight now keeps the window open (`_window_open`).
  - *A decision or run push gated the running turn.* A proposal or run push took the person's waiting edits along whenever they were quiet, ignoring the in-flight and 20 s checks, and opened the gate on the turn under way. Edits now ride along with a pin, or with a decision or run end only when no turn seems under way (`_agent_idle`); otherwise they wait for their own push.
  - *A pile of edits crowded out pins.* The 100-event cap was shared, so with 100 edits held (an hour at the wake limit) a new pin went into the overflow count and was pushed as a gated change. Pins and changes are now capped each on their own, and a pin overflow is counted under the pins.
  - *A listener failure took the tools down.* An exception escaping the listener (an answer it can't read) cancelled `serve_channel`'s task group and ended the whole MCP server. It is now caught: a stderr line, listening stops, the next dict result says so once (`ChannelState.stop`), and the tools keep working.
  - *`NEBULA_CHANNEL_PER_HOUR=0` crashed the limiter* (an empty history indexed); int limits are now at least 1.
  - *A wiring test flaked under load.* `test_a_pin_and_an_edit_reach_the_session_and_the_gate_holds` failed once in the full suite at load average ~70 (passes alone): with `WINDOW_MIN=1` the change turn could close before the test's `edit_canvas` call. The wiring fixture now keeps the window 30 s; nothing in those tests needs it to close (the closing is covered by the `ChannelState` tests).
  - Docs: the quoted warning is now the channels reference's own sentence ("Don't use it to run channels from untrusted sources"); the old quote isn't on the channels, channels-reference or CLI-reference pages (read 2026-10-20; it may be the startup dialog's text). The live check's account details are reduced to "an individual (non-Team) subscription".
