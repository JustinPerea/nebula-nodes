# Cinema shot rail and grade ownership — 2026-10-08

- Shot selection is a native button, separate from removal and reorder controls. Enter and Space use the browser's native activation; the key handler does not manufacture a second click. Focus alone does not select, delete, or generate.
- The selected shot is the rail's single selection tab stop. Unmodified arrows select and focus the neighboring shot, Home/End choose the first/last, and navigation clamps at the ends. Both horizontal and vertical arrows work as the layout changes.
- Plain Alt + arrows and the selected shot's explicit Move earlier/later buttons reorder by stable shot ID. Additional Ctrl, Meta, or Shift modifiers remain outside the rail's shortcut ownership. The host already applies the returned IDs to current shot objects, preserving more recent authoring/results. Pointer drag reorder remains; cancelled drag clears its identity.
- Selection or ordered shot-ID changes scroll into view. Prompt, override, and generated-output edits retain the editor's scroll position when selection/order are unchanged; depending on the whole shots array would scroll compact layouts back to the rail while typing. Keyboard reorder restores focus to the same stable selector after its position changes. Removal waits for the shot to disappear, then focuses the next surviving selector (previous at the end), or Add shot when empty. The host owns neighboring selection and keys the rail by source node ID.
- Backend `_merge_look` now treats a known named shot preset as owning its complete grade. It discards inherited scene scalar/LUT fields so `apply_look` resolves the preset's actual bundle. Explicit non-null shot fields, including numeric zero and a shot LUT, remain authoritative. Partial overrides without a known named preset retain inheritance; custom/unknown presets keep the established raw-slider behavior.
- Reset remains removal of authoring overrides. It therefore follows current shared palette/look settings on the next explicit generation. This change neither rewrites earlier image files nor edits frozen run recipes. The handler still records the newly generated output using its existing execution path.
