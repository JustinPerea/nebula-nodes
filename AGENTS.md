# Nebula Nodes — Agent Instructions

AI creation studio: FastAPI backend + React 19/Vite frontend around a node graph. 308 nodes, written in `frontend/src/constants/nodeDefinitions.ts` and mirrored in `backend/data/node_definitions.json`, which the backend and every script read. `scripts/export-node-defs.ts` writes the JSON from the TS, but four existing nodes (`gemini-tts`, `veo-3`, `gemini-omni-flash`, `quiver-arrow-generate`) carry JSON-only fixes it would undo, so check its diff before keeping it. `docs/MODEL_REFERENCE.md` is generated from it via `node scripts/generate-model-reference.mjs` — never edit it by hand.

## Where tests run

- Run the full suites in a Claude Code cloud session or in GitHub CI on a pushed branch. That covers the backend's pytest, the frontend's vitest, lint and build, and the contract scripts. On a machine you share with other agents, such as the maintainer's Mac, run only the focused tests for what you changed. Outside contributors without either can run [CONTRIBUTING.md's checks](CONTRIBUTING.md#development-checks) locally.
- A cloud session installs what CI installs on its own. `.claude/settings.json` runs `scripts/cloud-session-setup.sh` whenever a session starts, resumes, clears, compacts or forks, through `scripts/cloud-session-setup.mjs`, which does nothing outside a Linux cloud session (on Windows too). It installs at start and resume. After a clear, compaction or fork it only puts the venv back on `PATH`, so nothing is reinstalled under work in progress; it says when the dependencies changed since the last install.
  - The script does nothing unless `CLAUDE_CODE_REMOTE` is `true` (Claude Code sets it only in cloud sessions) and the machine is Linux.
  - It makes `backend/.venv` and runs `npm ci` in `frontend`, then puts the venv first on `PATH`, so CI's own commands work as written. Its first lines in the session say what's ready.
  - Run the checks one after another there, not at once (the backend suite, the frontend suite, lint and build, the contract scripts): together they compete for the session's 4 vCPUs, and tests that wait on timing fail.
  - Cloud sessions run as root, which ignores file permissions. A test that takes a file's read or write permission away with chmod carries `@pytest.mark.unprivileged` and skips as root; CI runs it as a normal user. `backend/tests/test_unprivileged_marker.py` fails on any such test left unmarked.
  - A cloud session may have no GitHub write access ("GitHub access to this repository is not enabled for this session", a 403 on a PR comment), so report results in the session itself.
  - A cloud session with several repositories, or a project's cloud thread, doesn't run repository hooks. In such a session only, run `CLAUDE_CODE_REMOTE=true bash scripts/cloud-session-setup.sh` by hand from this repository's root. Bash commands don't keep `PATH` from one call to the next, so start each backend command with the `export PATH=... &&` it prints, or call `backend/.venv/bin/python` directly.
- These stay on the maintainer's Mac:
  - driving the person's live canvas with the `nebula` CLI, and the person's own Nebula instance and `~/.nebula`;
  - the desktop app (Electron, the Keychain);
  - paid generation runs and anything that needs the person's own keys;
  - optional local model nodes;
  - Flora MCP work and the Codex runner.

## Standing task: Flora gap audit

We also produce content in Flora (app.flora.ai, via the `user-flora` MCP). Flora's catalog (~369 models) is a scouting list for Nebula's roadmap.

**Whenever you work in Flora and use or notice a model or capability that Nebula Nodes lacks as a first-class node, log it in `docs/flora-gap-audit.md` (Running Log table: date, gap, context, priority).**

Before logging, check it's a real gap:

1. Search `backend/data/node_definitions.json` — including `params` model enums. Several nodes are multi-model: `nano-banana` covers the whole Nano Banana family incl. Pro; `runway-video` covers Gen-4.5 / Gen-4 Turbo / Seedance 2.0 (+ Fast, Mini) / Seedance 2.5 / Happy Horse / Veo 3.1; `runway-image` covers Seedream 5.0 Pro / Lite (via Runway, a reseller); `minimax-*` covers Hailuo 2.3; the `veo-3` node is actually Veo 3.1. Route-table nodes cover one model on several providers: `flux-3-video`, `flux-video-edit` and `flux-video-upscale` also cover Krea's "Flux 3 Video", "Flux Video Edit" and "Flux Video Upscale", `krea-3` is Krea 3 on Krea or fal, and `flux-2-pro` ("FLUX.2") covers FLUX.2 [pro] / [max] / [flex] / [klein] 9B / [klein] 4B on BFL or fal, plus fal's FLUX 2 Flash.
2. Reachability through universal nodes (`fal-universal`, `replicate-universal`, `openrouter-universal`, `nous-portal-universal`) does **not** count as coverage — log it anyway, noting the universal fallback.

The full baseline comparison (2026-07-25) lives in `docs/flora-gap-audit.md`. Known top gaps: Enhancor skin-realism i2i, audio-driven lipsync/avatar models, first/last-frame video category, Kling Pro/Edit/Motion tiers, Magnific/Topaz upscalers.

### Closing gaps (separate chat)

Implementation work to add missing nodes should run in a **dedicated Cursor chat** rooted on this repo, not mixed into Nari/Flora character sessions. Paste-ready kickoff: `docs/NEBULA-GAP-HANDOFF.md`.

## Other conventions

- Notes: each change writes its decisions, tradeoffs and surprises to its own file, `docs/notes/<YYYY-MM-DD>-<branch>.md`: the date the branch starts, and the branch name with `/` as `-`. Don't add to `implementation-notes.md` or to the older per-feature notes files (`docs/*-notes.md`, `implementation-notes-*.md`): they keep their entries up to 2026-10-21, when one shared file was making every open PR conflict whenever another merged. A branch that still has an entry at the top of `implementation-notes.md` moves it into its own `docs/notes/` file when it next takes main in, instead of resolving the conflict there.
- Repo-backed agent skills live in `.agents/skills/` (indexed by the backend Codex runner). Keep them free of secrets and user outputs.
- `skills/nebula/` is the `nebula` CLI skill for agents outside Nebula (Claude Code, Codex). `nebula skill install` links it into `~/.claude/skills` and `~/.agents/skills`. Keep it out of `.agents/skills/`, which Nebula's own chats read. Update it when a CLI command changes.
- Dual-route nodes (a fal or Krea copy that also runs on the maker's API with the person's key) pick their route through `backend/services/node_route.py` (mirrored by `frontend/src/lib/directRoute.ts`): Krea plan, else maker key, else the fal/Krea key. Krea maker routes are declared in `scripts/sync-krea-catalog.py` `DIRECT_ROUTES`; never hand-edit generated Krea nodes.
- One node per model, with a provider switcher in the node. A new model goes in as **one node with a `routes` table**, never one node per provider. The maker's own API is the first route (source-direct), then the other providers in the order Auto tries them. A hidden `_provider` param saves the choice (a route id, or `auto`: the first route whose key is set). Auto never switches provider because of a setting; the run stops and names the routes that could run it. Each route lists only the values and ranges that provider takes (`route_param_definitions` / `routeParamDefinitions`), and every route takes every default. Changing `_provider`, like `_kreaAuth`, is the person's call: agents propose it. Verify each route's request shape and price against the provider's own schema and pricing page (`backend/tests/fixtures/provider_schemas/`, `model_pricing.json` per-route entries, `unconfirmed` when the page isn't exact), and leave out what you can't verify. Only new nodes use `routes`; the dual-route nodes above stay as they are. A Krea catalog model that becomes a route of such a node goes in `FOLDED` in `scripts/sync-krea-catalog.py`, and saved graphs move over through `MERGED` in `backend/services/retired_nodes.py`. See `docs/PROVIDER-ROUTES.md`, and after changing a node's routes or params run `backend/.venv/bin/python scripts/generate-route-tables.py`.
- A node with a `moodboard` input port (`dataType: "Moodboard"`) needs a moodboard adapter entry in `backend/data/moodboard_adapters.json` (or, for a Krea catalog node, from `scripts/sync-krea-catalog.py`) saying how it takes a board, with dated sources; a generator with a prompt and no port is listed in that file's `census`. `node scripts/check-node-contracts.mjs` and `backend/tests/test_moodboard_adapters.py` refuse it otherwise. See contract 07 section 1.16 and `docs/PROVIDER-ROUTES.md`.
- Canvas cards never subscribe to the whole `nodes` or `edges` array, `selectedNodeId` or other per-canvas values: select a primitive of what the card draws through `frontend/src/lib/graphIndex.ts` / `cardSelectors.ts` / `hooks/useCardSelection.ts`, and keep store updates structurally shared (`lib/structuralShare.ts`), or every card re-renders on every change. `frontend/tests/canvasRenderScope.test.tsx` holds the render counts.
- The frontend's startup entry has a budget (512,000 bytes raw, `frontend/scripts/check-build-budget.mjs`, run in CI). New panels, menus, pickers and modals are deferred by default: a `lazyWithPreload` in `frontend/src/lib/deferredChunks.ts` with a preload, and their files in `DEFERRED_MODULES` (`frontend/tests/entrySplit.test.ts` fails if the startup path imports them). Code used only inside an action goes through `deferredModule`. That file's header says when something may stay eager.
- A node run error the handler words itself carries the person's line (error copy round 3c-2, `backend/execution/person_line.py`): `raise as_person_line(ValueError("..."))` when the text names no id, file path, record name, env var, parameter key or provider text, else `raise with_person_line(ValueError("..."), line)` with an id-free line that names the node's field by its label (`missing_file_line`, `key_line`; a plain `"<KEY> is required"` `MissingCredentialError` gets its line by itself). Never change the exception text: agents read it. Provider text, moderation blocks and developer-only states keep no line (the card shows the classifier's line or GM's general one with Details). A route client's refusal names the node on its provider, not the provider's id: `raise refuse(where, text, person_tail)` with a `Where` (`backend/execution/route_clients.py`). `backend/tests/test_error_copy_round3c2.py` counts the raises with no line per file (handlers, execution and the services listed in its `RUN_TIME_SERVICES`; add a new run-time service there) and fails when one is added; when you add a line on purpose, lower its count there.
- A pre-run check gets the same split (round 3e): every `ValidationErrorDetail` in `execution/engine.validate_graph` sets `person=` (`missing_key_line`, `port_line`, `route_unavailable_line`, `person_line`, or a written line) beside its unchanged `message`; `backend/tests/test_error_copy_round3e.py` fails on one without it. Agents' answers (`/api/graph/run`, MCP `run_nodes`, `nebula run`) never carry `person`. The provider switcher's stop line (`frontend/src/lib/directRoute.ts` `routeUnavailableMessage`, also the run-cost summary's) is `route_unavailable_line` word for word, and `route_cases.json` `unavailableLine` pins both, so change them together; the agents keep `route_unavailable`'s text. What the Agent Log says about a refused run (`publish_action`) is the card's line too, never the key or the node id.
- The frontend never renders an Error's own message (round 3e). In a catch, show `failureMessage(error, "Couldn't {verb} {object}.")` or `failureCopy(error, { heading })` from `frontend/src/lib/errorCopy.ts` (`failureUnder` when the action's heading must win over the request's); a line written in the browser is thrown as a `FailureNotice(heading, reason)` (heading `''` when the surface adds its own), or `writtenLine(line)` for a step that reads on its own ("The project didn't open. Try again."), never `new Error(line)`: a catch shows a plain Error as GM's general line. Test mocks of a refusal throw the API's typed error (`RequestFailedError`), not `new Error(reason)`. Every node card shows its run error (`NodeRunError` in `components/nodes/NodeError.tsx`). No "Could not", "failed:" or "Failed to" in UI strings. `frontend/tests/errorCopy.rawMessageGuard.test.ts` and `frontend/tests/errorCopy.round3e.sweep.test.ts` scan `src/` and fail on a new one; a site that is never shown goes in their `ALLOWED` with its reason, and `frontend/tests/errorCopy.round3e.cards.test.tsx` fails on a card type that doesn't show its error.
- When adding a node, regenerate `docs/MODEL_REFERENCE.md` and check the corresponding entry off in `docs/flora-gap-audit.md` if it closes a logged gap.
- Running a second, isolated dev instance (tests, screenshots, agent checks): start the backend with a temp `HOME`, `NEBULA_SETTINGS_PATH`, `NEBULA_STATE_DIR` and `NEBULA_OUTPUT_ROOT` on its own port, and start Vite with `VITE_NEBULA_BACKEND_PORT=<that port>` so its proxy and the page talk to that backend only. Never let a browser test reach ports 8000-8010, which is the person's own backend. Recipe: [CONTRIBUTING.md](CONTRIBUTING.md#running-a-second-isolated-dev-instance).
